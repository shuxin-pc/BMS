# 出库功能设计

> 创建日期: 2026-07-29
>
> 背景: 入库功能已完整实现（POST /api/store/InventoryLogs/inbound 语义化端点 + 事务内三表写入 + 前端 Mock 替换为 HTTP 调用）。出库功能当前仍为前端 Mock 实现，后端缺少语义化出库端点、缺少 FEFO 批次扣减逻辑。本期实现出库功能完整闭环，与入库功能对称。

## 一、架构与端点

### 新增端点

`POST /api/store/InventoryLogs/outbound`（语义化出库，与 `/inbound` 对称，现有通用 `POST /InventoryLogs` 保留不动）

### 请求体 `OutboundCreateDto`（支持两种模式互斥）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `ProductId` | long | 是 | 商品ID |
| `SourceType` | int | 是 | 出库来源，取值见 §2 |
| `Quantity` | decimal? | 二选一 | FEFO 自动模式：总出库量，>0（后端按 FEFO 顺序自动分配到各批次） |
| `BatchItems` | List\<BatchOutboundItem\>? | 二选一 | 手动模式：批次扣减明细，提供时按用户指定批次扣减，不走 FEFO |
| `UnitPrice` | decimal? | 否 | 单价（仅记录到流水，不覆盖批次原值；手动模式下若填则所有批次流水统一用此值，不填取各批次原值） |
| `Remark` | string? | 否 | 备注 |

`Quantity` 与 `BatchItems` 互斥：只能填一个。`Quantity` 有值且 `BatchItems` 为空 -> FEFO 自动模式；`BatchItems` 有值且 `Quantity` 为空 -> 手动模式。

### `BatchOutboundItem`

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `BatchId` | long | 是 | 批次ID（InventoryBatch.Id） |
| `Quantity` | decimal | 是 | 该批次扣减数量，>0 |

### 响应 `ApiResponseDto<OutboundResultDto>`

```csharp
public class OutboundResultDto
{
    /// <summary>商品ID</summary>
    public long ProductId { get; set; }
    /// <summary>商品名称（显示字段）</summary>
    public string? ProductName { get; set; }
    /// <summary>商品编码（显示字段）</summary>
    public string? ProductCode { get; set; }
    /// <summary>出库来源类型</summary>
    public int SourceType { get; set; }
    /// <summary>总出库数量（正数）</summary>
    public decimal TotalQuantity { get; set; }
    /// <summary>操作前库存</summary>
    public decimal BeforeQuantity { get; set; }
    /// <summary>操作后库存</summary>
    public decimal AfterQuantity { get; set; }
    /// <summary>操作人</summary>
    public string? OperatorName { get; set; }
    /// <summary>批次扣减明细列表（每条对应一个批次的扣减流水）</summary>
    public List<InventoryLogDto> BatchDetails { get; set; } = new();
}
```

明细复用 `InventoryLogDto`，包含每条流水的 `BatchNo` / `ExpirationDate` / `UnitPrice` / `Quantity`（负数）等完整字段。

### 与现有端点的关系

- 现有 `POST /InventoryLogs` 通用端点保留不动
- 销售出库（SourceType=0）与疗程卡核销出库（SourceType=8）仍由 `OrderAppService` / `TreatmentCardVerifyAppService` 事务内绑定订单写入，**禁止手动创建**
- 入库功能已实现的部分不动

## 三、FEFO 批次扣减算法

### FEFO 排序规则

依据 `docs/通用需求规格.md` 与 `docs/效期可选需求修复方案.md`：

```sql
ORDER BY
    CASE WHEN ExpirationDate IS NULL THEN 1 ELSE 0 END,  -- 有效期批次优先
    ExpirationDate ASC,                                    -- 早过期先出
    PurchaseDate ASC,                                      -- 同效期按采购日期 FIFO
    CreatedTime ASC                                        -- 同采购日期按创建时间 FIFO
```

### FEFO 自动模式扣减流程

```
输入：ProductId, Quantity（总出库量）

1. 查询商品在当前门店的所有在库批次：
   WHERE ProductId = dto.ProductId
     AND TenantId = tenantId AND StoreId = storeId
     AND Status = 1 AND Quantity > 0
   ORDER BY FEFO 排序规则

2. 预检查：汇总所有批次 Quantity
   - 若 总量 < dto.Quantity -> 返回 400 "库存不足，当前库存: {总量}"

3. 查 Inventory 汇总表，记录 beforeQuantity
   - 若 Inventory 记录不存在 -> 返回 400 "库存不足"（批次存在但汇总缺失属数据不一致，拒绝出库避免产生负数汇总记录）

4. 逐批次扣减（EF Core 跟踪）：
   remaining = dto.Quantity
   FOR EACH batch（FEFO 顺序）:
     if remaining <= 0: break
     deductQty = min(remaining, batch.Quantity)

     // 写 InventoryLog（每批次一条）
     log = new InventoryLog {
         ProductId, Type=2, SourceType=dto.SourceType,
         Quantity = -deductQty,  // 负数
         BeforeQuantity = currentInventoryQuantity,  // 基于 Inventory 汇总实时算
         AfterQuantity = currentInventoryQuantity - deductQty,
         BatchNo = batch.BatchNo,
         ExpirationDate = batch.ExpirationDate,
         UnitPrice = dto.UnitPrice ?? batch.UnitPrice,  // DTO 优先，否则取批次原值
         Remark = dto.Remark,
         OperatorName = currentUser.RealName ?? UserName,
         ...TenantId/StoreId/CreatedTime
     }
     _dbContext.InventoryLogs.Add(log)

     // 扣减批次
     batch.Quantity -= deductQty
     if batch.Quantity == 0: batch.Status = 2  // 已用完

     remaining -= deductQty
     currentInventoryQuantity -= deductQty

5. 更新 Inventory 汇总表：Quantity -= dto.Quantity

6. SaveChanges + Commit
```

### 手动指定模式扣减流程

```
输入：ProductId, BatchItems[{BatchId, Quantity}]

1. 查 Inventory 汇总表，记录 beforeQuantity
   - 若 Inventory 记录不存在 -> 返回 400 "库存不足"（与 FEFO 模式语义一致）

2. 逐项校验 + 扣减（EF Core 跟踪）：
   currentInventoryQuantity = beforeQuantity
   FOR EACH item in BatchItems:
     // 校验批次
     batch = 查 InventoryBatches WHERE Id=item.BatchId
              AND ProductId=dto.ProductId AND TenantId AND StoreId AND Status=1
     if batch == null -> 返回 400 "批次不存在或已用完"
     if batch.Quantity < item.Quantity -> 返回 400 "批次 {BatchNo} 库存不足"

     // 写 InventoryLog
     log = new InventoryLog {
         ..., Quantity = -item.Quantity,
         BatchNo = batch.BatchNo,
         ExpirationDate = batch.ExpirationDate,
         UnitPrice = dto.UnitPrice ?? batch.UnitPrice,
         BeforeQuantity = currentInventoryQuantity,
         AfterQuantity = currentInventoryQuantity - item.Quantity,
         ...
     }
     _dbContext.InventoryLogs.Add(log)

     // 扣减批次
     batch.Quantity -= item.Quantity
     if batch.Quantity == 0: batch.Status = 2

     currentInventoryQuantity -= item.Quantity

3. 更新 Inventory 汇总表：Quantity -= sum(BatchItems.Quantity)

4. SaveChanges + Commit
```

### 两种模式校验对比

| 校验 | FEFO 自动模式 | 手动指定模式 |
|------|--------------|-------------|
| 汇总预检查（总量 < 出库量 -> 400） | ✅ 有 | ❌ 没有 |
| 单批次校验 `batch.Quantity >= item.Quantity` | ❌ 不需要（FEFO 逐批次扣减自然不会超） | ✅ 必须 |

两个模式的校验逻辑各自独立，没有叠加关系。手动模式不需要汇总预检查，因为用户已明确指定扣哪些批次、各扣多少，只要每个批次扣减量 <= 该批次 Quantity 就能成功。

### 关键说明

- **流水记录粒度**：每扣减一个批次写一条 `InventoryLog`，与入库"1 批次 1 条流水"对称。每条流水的 `BatchNo` / `ExpirationDate` / `UnitPrice` 精确记录该批次信息，完全可追溯。
- **`BeforeQuantity` / `AfterQuantity`**：每条流水记录扣减该批次后的库存汇总实时值（`Inventory` 汇总表的值，不是批次库存）。同一次出库的多条流水，`AfterQuantity` 逐条递减。
- **`UnitPrice`**：`dto.UnitPrice` 有值时所有流水统一用此值；否则取各批次原 `UnitPrice`（FIFO 成本真实值）。
- **手动模式不走 FEFO**：用户自行决定扣减哪些批次，后端只校验批次有效性。
- **批次扣减到 0**：`Status` 置 `2`（已用完）；部分扣减保持 `Status=1`（在库）。

## 四、事务边界与错误处理

### 事务边界

`OutboundAppService.CreateAsync` 全程在 `IDbContextTransaction` 内执行（与入库对称）：

```
BeginTransaction
  ├─ 校验商品存在
  ├─ [FEFO模式] 预检查批次总量 / [手动模式] 逐批次校验
  ├─ 查 Inventory 汇总表（beforeQuantity）
  ├─ 逐批次扣减 + 写 InventoryLog（多条）
  ├─ 更新 Inventory 汇总表
  ├─ SaveChanges
CommitTransaction
  └─ post-commit 重查询填充显示字段（移出 try 块，失败时 fallback）
```

### 错误处理表

| 场景 | HTTP | 错误信息 |
|------|------|---------|
| 未登录 / 无门店上下文 | 401 | "无法确定当前租户或门店" |
| `SourceType` 不在允许集合 | 400 | "出库来源类型不合法" |
| `Quantity` 与 `BatchItems` 同时为空或同时有值 | 400 | "请指定出库数量或选择批次" |
| `Quantity <= 0`（FEFO 模式） | 400 | "出库数量必须大于0" |
| `BatchItems` 为空 / 重复 BatchId / 项 Quantity<=0（手动模式） | 400 | "批次扣减明细不合法" |
| 商品不存在 | 400 | "商品不存在" |
| [FEFO] 批次总量 < 出库量 | 400 | "库存不足，当前库存: {总量}" |
| [手动] 批次不存在 / Status≠1 | 400 | "批次 {BatchNo} 不存在或已用完" |
| [手动] 批次.Quantity < item.Quantity | 400 | "批次 {BatchNo} 库存不足" |
| Inventory 汇总记录不存在（数据不一致） | 400 | "库存不足" |
| 数据库写入失败 | 500 | "出库失败，请重试" |

### 并发处理

与入库一致：事务内串行写入，依赖数据库事务隔离级别。`Inventory` 表不加 `[Timestamp]` 乐观锁。若并发冲突由 `DbUpdateException` 捕获返回 500，前端提示重试。

### post-commit 重查询

与入库对称：事务提交后重新查询所有本次出库产生的 `InventoryLog` 记录（按 ID 列表），`Include(Product)` + `Include(Supplier)` 填充显示字段，组装为 `OutboundResultDto` 返回。若重查询失败，数据已落库，返回 fallback DTO（缺少显示字段但包含核心数据），避免用户误重试导致重复出库。

## 六、入库遗留 Suggestion 修复

文档原 §2.1 列出的入库遗留项：`InventoryLogAppService.GetByIdAsync` 补齐显示字段。

当前 `InventoryLogAppService.cs:114`：

```csharp
var entity = await _dbContext.InventoryLogs
    .FirstOrDefaultAsync(l => l.Id == id ...);  // 未 Include
return ApiResponseDto<InventoryLogDto?>.Ok(entity.Adapt<InventoryLogDto>());
```

修改为与 `GetPagedListAsync` 一致：

```csharp
var entity = await _dbContext.InventoryLogs
    .Include(l => l.Product)
    .Include(l => l.Supplier)
    .FirstOrDefaultAsync(l => l.Id == id ...);
if (entity == null) return ...;
var dto = new InventoryLogDto {
    ...entity.Adapt<InventoryLogDto>(),
    ProductName = entity.Product?.Name,
    ProductCode = entity.Product?.Code,
    SupplierName = entity.Supplier?.Name,
    OperatorName = entity.OperatorName
};
```

**理由**：出库功能新增的 `/outbound` 端点不依赖 `GetByIdAsync`（有自己的 post-commit 重查询）。但 `GetByIdAsync` 是流水详情查询的公共入口，入库遗留的显示字段缺失会影响所有流水详情展示。顺手修复成本低，且文档已明确列出。
