## 三、关键设计考虑

### 3.1 OutboundCreateDto 字段设计

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `ProductId` | long | 是 | 商品ID |
| `SourceType` | int | 是 | 出库来源，取值见 §3.2 |
| `Quantity` | decimal | 是 | 出库数量，>0（后端转为负数写入 InventoryLog） |
| `UnitPrice` | decimal? | 否 | 单价（用于成本记录） |
| `Remark` | string? | 否 | 备注 |

注：出库不需要 `BatchNo` / `ProductionDate` / `ShelfLifeDays` / `ExpirationDate`（这些由 FEFO 扣减逻辑自动选择批次，不由用户指定）。`SupplierId` 在出库场景不适用（采购退货出库的供应商关联由采购退货单维护）。

### 3.2 允许的出库来源类型

手动出库端点允许的 SourceType 集合（与 `InventoryLogAppService.CreateAsync` 的销售出库类禁止逻辑一致）：

| SourceType | 常量 | 说明 | 允许手动 |
|------------|------|------|----------|
| 0 | SalesOutbound | 销售出库 | 禁止（订单触发） |
| 3 | CheckAdjustment | 盘点盘亏 | 允许 |
| 5 | TransferOutbound | 调拨出库 | 允许 |
| 6 | Other | 其他 | 允许 |
| 7 | PurchaseReturnOutbound | 采购退货出库 | 允许 |
| 8 | TreatmentCardOutbound | 疗程卡核销出库 | 禁止（核销触发） |
| 9 | SampleGiftOutbound | 样品/赠品出库（历史值） | 允许（兼容历史） |
| 10 | SampleReceiveOutbound | 样品领用出库 | 允许 |
| 11 | GiftOutbound | 赠品活动出库 | 允许 |

`OutboundCreateDtoValidator` 的 `ValidOutboundSourceTypes` 集合：`{3, 5, 6, 7, 9, 10, 11}`。

### 3.3 FEFO 批次扣减逻辑

出库时按 FEFO（First Expired First Out）顺序扣减 `InventoryBatch` 记录，排序规则（依据 `docs/效期可选需求修复方案.md` 与 `docs/通用需求规格.md`）：

```
ORDER BY
    CASE WHEN ExpirationDate IS NULL THEN 1 ELSE 0 END,  -- 有效期批次优先
    ExpirationDate ASC,                                    -- 早过期先出
    PurchaseDate ASC,                                      -- 同效期按采购日期 FIFO
    CreatedTime ASC                                        -- 同采购日期按创建时间 FIFO
```

扣减算法：
1. 查询商品在当前门店的所有在库批次（`Status=1` 且 `Quantity > 0`），按上述 FEFO 排序
2. 逐批次扣减：若剩余出库量 >= 批次 Quantity，扣完该批次（Quantity 置 0，Status 置 2 已用完）；否则部分扣减（Quantity -= 剩余出库量）
3. 若所有批次扣完仍有剩余出库量，返回 400 "库存不足"
4. 记录每个被扣减批次的 `BatchNo` / `ExpirationDate` / `UnitPrice`（若需要多条流水记录，见 §3.4）

### 3.4 流水记录粒度

两种方案，需在 brainstorming 阶段确定：

**方案 A：单条流水**（推荐）
- 一笔出库写一条 `InventoryLog`，`Quantity` 为负数（总出库量）
- `BatchNo` / `ExpirationDate` 取第一个被扣减批次的信息（或留空）
- 优点：流水表简洁，与入库对称
- 缺点：无法从流水反查具体扣了哪些批次

**方案 B：多条流水**
- 每扣减一个批次写一条 `InventoryLog`
- 优点：可精确追溯每批次的扣减记录
- 缺点：流水表膨胀，与入库不对称（入库是一批一条流水）

### 3.5 事务边界

`OutboundAppService.CreateAsync` 全程在 `IDbContextTransaction` 内执行：
1. 校验商品存在 + 库存充足
2. 按 FEFO 扣减 `InventoryBatch`（可能多条）
3. 写 `InventoryLog`（Type=2，Quantity 为负数）
4. 更新 `Inventory` 汇总表（Quantity -= 出库量）
5. 提交事务

与入库对称：post-commit 重查询填充显示字段移出 try 块，失败时返回 fallback DTO 避免重复出库。

### 3.6 库存不足处理

- 查询所有在库批次总量 < 出库量时，返回 400 "库存不足，当前库存: {X}"
- 不允许负库存（与现有 `createOutbound` Mock 的 `if (afterQuantity < 0) throw new Error('库存不足')` 一致）

### 3.7 前端 createOutbound 替换

```typescript
export async function createOutbound(data: OutboundRequest): Promise<InventoryLog> {
  return request<InventoryLog>('/inventorylogs/outbound', {
    method: 'POST',
    body: JSON.stringify(data)
  })
}
```

`OutboundRequest` 接口当前字段（`productId` / `quantity` / `remark`）需扩展为与 `OutboundCreateDto` 对齐（增加 `sourceType` 必填字段）。

### 3.8 outbound/index.vue 联调

- 确认表单是否有"出库来源"选择器；若无，需新增（参考 `inbound/index.vue` 的来源选择器）
- 确认 `OutboundSourceType` 与 `outboundSourceTypeMap` 定义
- 确认库存查询逻辑（当前 `getProductStock` 已在入库功能中实现为 HTTP 调用，可直接复用）
