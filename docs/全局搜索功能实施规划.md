# 全局搜索功能实施规划

> **执行说明**：本规划基于需求讨论共识编写。执行前请先阅读「背景与共识」，实施过程中如发现与现状不符，先向用户确认再调整。

**目标**：将框架顶部占位搜索框升级为完整的命令面板式全局搜索——功能导航（跨子系统）+ 业务数据搜索（顾客/订单/商品/项目卡/储值/预约/用户），一次到位，新子系统未来零改动接入。

**架构**：统一搜索端点规范——每个子系统后端暴露 `GET /api/{service}/search`，服务端内部并行查表 + 权限校验 + 租户/门店隔离，按分组返回 top N；前端按"服务"注册搜索源（注册表 + 权限过滤 + 意图加权），面板并行请求已授权服务源并分组渲染。搜索契约 DTO 放共享层 `Bms.BuildingBlocks.Core`。

**技术栈**：.NET 10 / EF Core 10（后端）、Vue 3 + TypeScript + Element Plus（前端）。前后端当前均无测试设施，本规划以构建验证 + 手动验收替代 TDD（如需补测试设施，另行与用户确认，不在本范围内）。

## 一、背景与共识（需求讨论结论）

1. **产品定位**：命令面板（混合模式）——输入关键词，同时返回「功能入口匹配」与「业务数据匹配」分组结果
2. **不做输入路由**：源集合由权限预决定，不由输入决定。意图识别只做「结构特征 → 排序加权」（手机号→顾客置顶），识别错误零伤害
3. **按权限预注册**：用户没有某权限码 → 对应搜索源不注册、不请求、UI 不出现分组。租户未开通门店子系统时搜索自动退化为其余子系统搜索，不出错、不浪费
4. **一期完整**：交互形态（面板、键盘、跨子系统跳转、最近搜索）+ 架构（统一端点契约）+ 核心实体全接入，一次做完
5. **覆盖面**（已与用户确认）：

| 服务 | 实体 | 匹配字段 | 分组名 |
|------|------|---------|--------|
| Store | 顾客 Customer | Name、Phone | 顾客 |
| Store | 订单 Order | OrderNo、CustomerName | 订单 |
| Store | 商品主档 ProductMaster | Name、Code | 商品 |
| Store | 项目卡销售 TreatmentCardSale | SaleNo + 关联顾客 Name/Phone | 项目卡 |
| Store | 储值账户 StoredValueAccount | 关联顾客 Name/Phone | 储值 |
| Store | 预约 Appointment | AppointmentNo、CustomerName | 预约 |
| System | 用户 User | UserName、RealName、Phone | 用户 |
| 前端本地 | 全部已授权子系统菜单 | 菜单名称 | 功能 |

6. **非目标**：租户搜索、技师/房间/设备/供应商搜索（二期）；全文检索引擎、搜索日志表、新数据表字段（一期均不需要）
7. **跳转行为**：数据结果点击 → 跳对应列表页并携带 `?keyword=` 预填；功能结果点击 → 直接跳菜单路由。跳转映射由**前端注册表**维护，服务端不感知路由

## 二、架构设计

### 2.1 数据流

```
用户输入(≥2字符, debounce 300ms)
  ├─ 功能源：本地过滤 allSubsystemsMenus（即时，无请求）
  └─ 远程源（并行，仅已授权服务）：
       GET /api/store/search?keyword=xx&limit=5
       GET /api/system/search?keyword=xx&limit=5
            服务端：权限码校验 → 全局租户过滤器(自动) → StoreId 手动过滤
            → 各实体并行 top-5 查询 → 非空分组返回
  ↓
前端汇总：意图加权排序 → 分组渲染 → 点击跳转
  （跨子系统：先 switchSubsystem 再 router.push）
```

### 2.2 统一搜索契约（共享层 DTO，两个服务复用）

新建 `src/BuildingBlocks/Bms.BuildingBlocks.Core/Search/GlobalSearchDtos.cs`：

```csharp
namespace Bms.BuildingBlocks.Core.Search;

/// <summary>全局搜索请求</summary>
public class GlobalSearchRequestDto
{
    /// <summary>搜索关键字（服务端校验：必填、 Trim 后长度 ≥ 1 且 ≤ 50）</summary>
    public string Keyword { get; set; } = string.Empty;

    /// <summary>每组返回条数上限，默认 5，最大 10</summary>
    public int Limit { get; set; } = 5;
}

/// <summary>搜索结果项</summary>
public class SearchResultItemDto
{
    /// <summary>主标题（顾客姓名 / 单号 / 菜单名等）</summary>
    public string Title { get; set; } = string.Empty;

    /// <summary>辅助信息（手机号 / 金额 / 日期等）</summary>
    public string? Subtitle { get; set; }
}

/// <summary>搜索结果分组（仅返回有命中的分组）</summary>
public class SearchResultGroupDto
{
    /// <summary>分组名：顾客 / 订单 / 商品 / 项目卡 / 储值 / 预约 / 用户</summary>
    public string Group { get; set; } = string.Empty;

    public List<SearchResultItemDto> Items { get; set; } = new();
}
```

响应统一为各服务现有的 `ApiResponseDto<List<SearchResultGroupDto>>`（只返回非空分组）。

### 2.3 前端搜索源契约

```typescript
// src/utils/globalSearch/types.ts
export interface SearchResultItem {
  title: string
  subtitle?: string
  group: string            // 与后端 Group 一致
}

export interface SearchProvider {
  id: string                       // 'menu' | 'store' | 'system'
  permission: string | null        // 权限码，null 表示菜单源（菜单已按权限裁剪）
  subsystemId: () => string        // 返回该源数据所属子系统（跨子系统跳转用）；menu 源动态判定
  search: (kw: string) => Promise<SearchResultItem[]>
}
```

- **menu 源**：本地过滤全量授权菜单（含所有已授权子系统），每条命中项自带 `subsystemId + path`
- **store / system 源**：调用对应服务 `/search` 端点，将返回的 `SearchResultGroupDto[]` 摊平为 item 数组（group 字段保留）

### 2.4 权限码约定（源注册门槛）

| 源 | 权限码 | 说明 |
|----|--------|------|
| store 服务源 | `store:customer:view` | 任一 store 数据查看权限即可视为该租户开通门店子系统；服务端各分组再按各自权限码过滤 |
| system 服务源 | `system:user:view` | 同上 |
| menu 源 | 无 | 菜单数据本身已按授权裁剪 |

服务端分组级权限过滤矩阵（Store 服务示例）：

| 分组 | 校验权限码 |
|------|-----------|
| 顾客 | `store:customer:view` |
| 订单 | `store:order:view` |
| 商品 | `store:product:view` |
| 项目卡 | `store:treatment:view` |
| 储值 | `store:storedvalue:view` |
| 预约 | `store:appointment:view` |

> 执行时以各服务权限码实际定义核对（参照 `Menus.json` 的 PermissionCode / StoreMenuSeedData.cs），不一致时以代码现状为准并在 commit message 中注明。

### 2.5 意图规则（前端纯函数，`src/utils/globalSearch/intent.ts`）

```typescript
// 返回分组加权分，默认 1.0
export function getIntentBoost(keyword: string): Record<string, number> {
  const boost: Record<string, number> = {}
  if (/^1[3-9]\d{9}$/.test(keyword)) boost['顾客'] = 2.0      // 手机号
  else if (/^\d{4,}$/.test(keyword)) boost['顾客'] = 1.3      // 纯数字串可能为号码
  // 单号格式规则：执行时按实际 OrderNo/SaleNo 生成规则补充（如前缀特征）
  return boost
}
```

排序：组间按 `max(组内条目基础权重, 意图加权)` 降序；无命中分组自动消失。

```csharp
public class GlobalSearchAppService : IGlobalSearchAppService
{
    private readonly StoreDbContext _dbContext;
    private readonly ICurrentUser _currentUser;

    public GlobalSearchAppService(StoreDbContext dbContext, ICurrentUser currentUser)
    {
        _dbContext = dbContext;
        _currentUser = currentUser;
    }

    public async Task<ApiResponseDto<List<SearchResultGroupDto>>> SearchAsync(GlobalSearchRequestDto request)
    {
        if (!_currentUser.TenantId.HasValue)
            return ApiResponseDto<List<SearchResultGroupDto>>.Fail("登录状态异常，请重新登录", 401);

        var kw = request.Keyword?.Trim() ?? string.Empty;
        if (kw.Length == 0 || kw.Length > 50)
            return ApiResponseDto<List<SearchResultGroupDto>>.Fail("搜索关键字无效");
        var limit = Math.Clamp(request.Limit, 1, 10);
        var tenantId = _currentUser.TenantId.Value;
        var storeId = _currentUser.StoreId ?? 0;

        // 六个分组查询并行执行；租户隔离由 EF 全局过滤器自动生效，
        // 门店隔离按现有 AppService 惯例手动加 StoreId 条件
        var customersTask = SearchCustomersAsync(kw, limit);
        var ordersTask = SearchOrdersAsync(kw, limit);
        var productsTask = SearchProductsAsync(kw, limit);
        var treatmentTask = SearchTreatmentCardSalesAsync(kw, limit);
        var storedValueTask = SearchStoredValueAccountsAsync(kw, limit);
        var appointmentsTask = SearchAppointmentsAsync(kw, limit);
        await Task.WhenAll(customersTask, ordersTask, productsTask, treatmentTask, storedValueTask, appointmentsTask);

        // 仅收集非空分组（分组名与 §2.4 矩阵一致）
        var groups = new List<SearchResultGroupDto>();
        void Add(string group, List<SearchResultItemDto> items)
        { if (items.Count > 0) groups.Add(new SearchResultGroupDto { Group = group, Items = items }); }

        Add("顾客", await customersTask);
        Add("订单", await ordersTask);
        Add("商品", await productsTask);
        Add("项目卡", await treatmentTask);
        Add("储值", await storedValueTask);
        Add("预约", await appointmentsTask);

        return ApiResponseDto<List<SearchResultGroupDto>>.Ok(groups);
    }

    // 示例：顾客分组——Name 模糊 + Phone 模糊（含后四位场景），项目暂无权限码服务端矩阵设施时
    // 分组级权限过滤先按 §2.4 通过 ICurrentUser 权限声明判断；若现状无此设施，则一期退化为
    // 「登录即可见分组」，在 commit message 注明，待权限中间件支持后补齐。
    private async Task<List<SearchResultItemDto>> SearchCustomersAsync(string kw, int limit)
    {
        var items = await _dbContext.Customers
            .Where(c => (c.Name.Contains(kw) || (c.Phone != null && c.Phone.Contains(kw))))
            .OrderBy(c => c.Name)
            .Take(limit)
            .Select(c => new SearchResultItemDto { Title = c.Name, Subtitle = c.Phone })
            .ToListAsync();
        return items;
    }

    // 其余分组查询方法按相同模式实现：
    // 订单：OrderNo.Contains(kw) || CustomerName.Contains(kw)，Subtitle = 下单时间/金额
    // 商品：ProductMasters 的 Name/Code.Contains(kw)，Subtitle = 编码
    // 项目卡：TreatmentCardSales 的 SaleNo.Contains(kw)，或 join Customers 按顾客 Name/Phone 匹配，Subtitle = 顾客姓名
    // 储值：StoredValueAccounts join Customers 按顾客 Name/Phone 匹配，Subtitle = 余额
    // 预约：AppointmentNo.Contains(kw) || CustomerName.Contains(kw)，Subtitle = 预约时间
}
```

> 注：以上为骨架，`join Customers` 的分组需 `await _dbContext.Customers.Where(...).Select(c => c.Id).Take(limit*2)` 先取顾客 Id 集再查主表，或直接 `from a in Accounts join c in Customers on a.CustomerId equals c.Id` 联查——由执行者按 EF 惯例实现，保持单次往返优先。
