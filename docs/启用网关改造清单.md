# 启用网关改造清单

## 一、背景与目标

### 背景
当前项目前端（mes-admin）在开发环境直连各后端服务端口（5000/5010/5030），绕过网关（5020）。导致：
- 网关限流配置（`ocelot.json` 60 req/min）形同虚设
- 端口硬编码散落在前端 5 个 API 文件共 6 处
- CORS 需在每个后端服务重复维护
- Vite 代理配置目标错误（`5000` 而非 `5020`），是潜伏的 404 陷阱
- 网关的子系统权限中间件（`UseSubsystemAccess`）在开发环境不生效

### 目标
开发环境启用网关，前端统一走 `http://localhost:5020/api/*`，让限流、CORS、子系统权限验证在开发环境真正生效，并与生产环境保持一致。

### 原则
- 内部服务调用（Store.Api -> System.Api）**保持直连**，不走网关
- 改造分两期：一期达成"走网关可达"，二期做"鉴权下沉"
- 每一步可独立验证、可回滚

## 三、修改清单

### 一期：走网关可达（必做）

#### G-1 网关补 CORS 配置
- **位置**：`src/Gateway/Bms.Gateway.Api/Program.cs` + `appsettings.json`
- **现状**：网关无 CORS，前端 3000 跨域请求会被拦截
- **改法**：
  1. `appsettings.json` 添加 `Cors:AllowedOrigins: ["http://localhost:3000"]`
  2. `Program.cs` 添加 `AddCors` + `UseCors`（参照 `Store.Api/Program.cs:31-51` 模式）
- **验证**：浏览器从 3000 访问 `http://localhost:5020/api/system/...` 无 CORS 报错
- **优先级**：P0
- **状态**：[ ] 未开始

#### G-2 网关补 customer 路由
- **位置**：`src/Gateway/Bms.Gateway.Api/ocelot.json`
- **现状**：前端 `api/customer/index.ts` 调用 `/api/customer/*`，但网关无此路由，走网关后 404
- **改法**：在 `Routes` 数组追加：
  ```json
  {
    "DownstreamPathTemplate": "/api/customer/{everything}",
    "DownstreamScheme": "http",
    "DownstreamHostAndPorts": [{ "Host": "localhost", "Port": 5030 }],
    "UpstreamPathTemplate": "/api/customer/{everything}",
    "UpstreamHttpMethod": [ "Get", "Post", "Put", "Delete" ]
  }
  ```
- **验证**：通过网关访问 customer 接口返回正常业务数据
- **优先级**：P0
- **状态**：[ ] 未开始

#### G-3 开发环境限流区分
- **位置**：新建 `src/Gateway/Bms.Gateway.Api/ocelot.Development.json`
- **现状**：`ocelot.json` 全局限流 60 req/min，开发联调会误伤
- **改法**：
  1. 新建 `ocelot.Development.json`，移除或调高 `RateLimitOptions.Limit`（建议 600+）
  2. `Program.cs:10` 改为按环境加载：先加载 `ocelot.json`，开发环境再叠加 `ocelot.Development.json`
- **验证**：开发环境连续刷新 100 次不被限流
- **优先级**：P0
- **状态**：[ ] 未开始

#### G-4 修复 UseHttpsRedirection 硬编码
- **位置**：`src/Gateway/Bms.Gateway.Api/Program.cs:30`
- **现状**：`app.UseHttpsRedirection()` 无条件执行，但网关是 http（5020），会导致请求被重定向到 https 失败
- **改法**：按 `FeatureFlags:UseHttpsRedirection` 配置开关，或直接删除该行（网关在开发环境用 http）
- **验证**：http 请求直达网关不被重定向
- **优先级**：P0
- **状态**：[ ] 未开始

#### G-5 网关确保 X-Forwarded-For 传递（解决审计日志 IP 溯源）
- **位置**：`src/Gateway/Bms.Gateway.Api/Program.cs` + `ocelot.json`
- **现状**：走网关后下游服务 `RemoteIpAddress` = 网关 IP（127.0.0.1），审计日志 `RequestIp` 记录的是网关 IP 而非真实客户端 IP，丢失溯源能力
- **改法**：
  1. `Program.cs` 添加 `UseForwardedHeaders` 中间件（在 `UseOcelot` 之前）：
     ```csharp
     using Microsoft.AspNetCore.HttpOverrides;
     // builder.Services 配置
     builder.Services.Configure<ForwardedHeadersOptions>(options =>
     {
         options.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
         options.KnownNetworks.Clear();
         options.KnownProxies.Clear();
     });
     // app 管道，在 UseOcelot 之前
     app.UseForwardedHeaders();
     ```
  2. `ocelot.json` 的 `GlobalConfiguration` 添加 `DownstreamHeaderTransform`，显式传递客户端 IP：
     ```json
     "GlobalConfiguration": {
       "BaseUrl": "http://localhost:5020",
       "DownstreamHeaderTransform": {
         "X-Forwarded-For": "{RemoteIpAddress}"
       }
     }
     ```
- **原理**：Vite 代理（http-proxy）默认设置 `X-Forwarded-For: <浏览器IP>`；网关 `UseForwardedHeaders` 解析该 header 让 `RemoteIpAddress` 反映真实 IP；Ocelot `DownstreamHeaderTransform` 将真实 IP 写入下游请求的 `X-Forwarded-For`；下游 `AuditLogMiddleware.cs:245-250` 优先读 `X-Forwarded-For` 获取真实 IP
- **验证**：V-1.11 审计日志记录的 `RequestIp` 为真实浏览器 IP 而非 127.0.0.1
- **优先级**：P0
- **状态**：[ ] 未开始

#### F-1 前端统一走相对路径
- **位置**：上述 6 处直连点（F-1 ~ F-6）
- **现状**：开发环境用绝对 URL 直连各服务端口
- **改法**：6 处统一改为相对路径：
  ```ts
  // 改前
  const API_BASE = import.meta.env.DEV ? 'http://localhost:5030/api/product' : '/api/product'
  // 改后
  const API_BASE = '/api/product'
  ```

  - `api/system/index.ts:35` -> `'/api/identity'`
  - `api/product/index.ts:24` -> `'/api/product'`
  - `api/customer/index.ts:47` -> `'/api/customer'`
  - `api/store/index.ts:22` -> `'/api/store'`
  - `api/shared/storeRequest.ts:21` -> `'/api/store'`
- **验证**：浏览器 Network 面板看到请求目标是 `/api/...`（同源，经 Vite 代理转发）
- **优先级**：P0
- **状态**：[ ] 未开始

#### F-2 修复 Vite 代理目标
- **位置**：`src/Admin/mes-admin/vite.config.ts:17`
- **现状**：代理目标 `http://localhost:5000`（System.Api，错误）
- **改法**：改为 `http://localhost:5020`（网关）
- **验证**：前端 `/api/system/*`、`/api/product/*`、`/api/customer/*` 均通过代理到达网关再转发到正确服务
- **优先级**：P0
- **状态**：[ ] 未开始

#### S-1 更新本地启动脚本
- **位置**：`runLocal.bat`
- **现状**：只启动前端 `npm run dev`
- **改法**：改为先启动网关（`dotnet run --project src/Gateway/Bms.Gateway.Api`），再启动前端。可用 `start` 命令开两个窗口，或用 `&&` 串行

### 二期：鉴权下沉（解决子系统权限 + 鉴权收敛）

#### G-6 网关注册鉴权并配置路由级验证（解决子系统权限形同虚设问题）
- **位置**：`Program.cs` + `ocelot.json`
- **现状**：网关无 `AddAuthentication`/`UseAuthentication`，`context.User` 为空。`SubsystemAccessMiddleware` 因租户解析全失败而碰巧放行，子系统级权限保护形同虚设
- **改法**：
  1. `Program.cs` 注册 JWT 鉴权（复用 `System.Api/appsettings.json:19-24` 的 Jwt 配置）
  2. `Program.cs` 添加 `UseAuthentication`（在 `UseSubsystemAccess` 之前），让网关 `context.User` 被填充
  3. `ocelot.json` 每条路由加 `AuthenticationOptions: { AuthenticationProviderKey: "Bearer" }`
  4. 路由加 `AddHeadersToRequest` 把 claims（tenantId/userId/roleIds）传给下游
- **解决效果**：网关 `context.User` 被填充后，`ClaimTenantResolver` 从 `tenant_id` claim 拿到租户，`SubsystemAccessMiddleware` 真正执行子系统权限校验
- **验证**：带 token 访问网关通过，无 token 返回 401；未授权租户访问子系统返回 403；下游服务能从 header 拿到 claims
- **优先级**：P2
- **状态**：[ ] 未开始

#### B-1 下游服务改读网关 header
- **位置**：`System.Api`、`Identity.Api`、`Store.Api` 的鉴权中间件
- **现状**：各服务自己解 JWT 提取 claims
- **改法**：改为信任并读取网关传入的 header（`X-Tenant-Id`、`X-User-Id` 等），移除重复验签
- **验证**：服务端日志显示从 header 获取到正确的用户/租户信息
- **优先级**：P2
- **状态**：[ ] 未开始

### 不需要改动（说明性）

#### B-0 内部服务调用保持直连
- **位置**：`Store.Api/appsettings.json:26-27` 的 `SystemApi:BaseUrl`
- **说明**：Store.Api 调 System.Api 走 InternalServiceKey 直连 5000，**不走网关**。网关是外部入口，内部调用走网关会引入循环依赖。此项无需改动，但需在二期鉴权下沉时确认内部调用仍走 InternalServiceKey 而非网关 header。

## 六、鉴权与审计影响分析

### 结论：一期改造不破坏现有鉴权与审计功能

以下分析基于当前代码链路（已确认）：

| 关注点 | 影响结论 | 依据 | 解决方案 |
|--------|---------|------|----------|
| JWT 鉴权 | ✓ 不受影响 | Ocelot 默认原样转发 Authorization header；下游服务 `UseAuthentication` 正常解析 | 无需处理 |
| 多租户（MultiTenant） | ✓ 不受影响 | `ClaimTenantResolver` 从下游 `context.User` 的 `tenant_id` claim 解析，JWT 正确则租户正确 | 无需处理 |
| 审计日志-用户信息 | ✓ 不受影响 | `CurrentUser` 依赖 `context.User` claims，下游 JWT 解析正常则用户信息正确 | 无需处理 |
| 审计日志-客户端 IP | ⚠️ 有变化 | 直连时 `RemoteIpAddress`=浏览器 IP；走网关后需依赖 `X-Forwarded-For` 链路（Vite 代理->Ocelot->下游） | **G-5（一期）**：网关添加 `UseForwardedHeaders` + Ocelot `DownstreamHeaderTransform` |
| 子系统权限（SubsystemAccess） | ⚠️ 行为变化但不拦截 | 网关无 `UseAuthentication`，`context.User` 为空，三个租户解析策略都失败，`tenant==null` 放行（碰巧不拦截，非正确工作） | **G-6（二期）**：网关注册 JWT 鉴权 + `UseAuthentication`，填充 `context.User` 后 `ClaimTenantResolver` 拿到租户，中间件真正工作 |

### 链路详情

**当前直连模式**：
```
浏览器 [Authorization: Bearer <JWT>]
  -> 下游服务 UseAuthentication (解析 JWT, 填充 context.User)
  -> UseMultiTenant (ClaimTenantResolver 从 tenant_id claim 拿到租户)
  -> UseAuditLog (CurrentUser 从 claims 拿用户信息, RemoteIpAddress=浏览器IP)
```

**走网关后**：
```
浏览器 [Authorization: Bearer <JWT>]
  -> Vite 代理 [设置 X-Forwarded-For: <浏览器IP>]
  -> 网关 [context.User 为空(无 UseAuthentication), SubsystemAccess 拿不到租户放行]
  -> Ocelot [原样转发 Authorization + X-Forwarded-For]
  -> 下游服务 UseAuthentication (解析 JWT, 填充 context.User) ✓
  -> UseMultiTenant (ClaimTenantResolver 从 tenant_id claim 拿到租户) ✓
  -> UseAuditLog (CurrentUser 从 claims 拿用户信息 ✓, IP 优先读 X-Forwarded-For)
```

### 阻断性风险

**G-4（UseHttpsRedirection 硬编码）必须最先修复**：
- 网关 `Program.cs:30` 无条件执行 `app.UseHttpsRedirection()`
- 网关 http profile 只有 5020，**无 https 端口**
- 不修复则所有 http 请求被 307 重定向到不存在的 https 端口，网关完全不可用

### 子系统权限中间件说明

走网关后 `SubsystemAccessMiddleware` 会执行，但**碰巧放行**：
1. `ClaimTenantResolver`：网关无 `UseAuthentication`，`context.User` 为空 -> 拿不到 `tenant_id`
2. `HeaderTenantResolver`：前端只带 `Authorization` + `Content-Type`，不带 `X-Tenant-Code` -> 拿不到
3. `HostTenantResolver`：`localhost` 无子域名 -> 返回 null
4. 三个策略都失败 -> `tenant == null` -> `SubsystemAccessMiddleware.cs:31-36` 放行

**这意味着子系统级权限校验形同虚设**。

**解决方案**：二期 **G-6（网关鉴权下沉）**。在网关 `Program.cs` 注册 JWT 鉴权 + 添加 `UseAuthentication`（在 `UseSubsystemAccess` 之前），使 `context.User` 被填充。此后 `ClaimTenantResolver` 能从 `tenant_id` claim 拿到租户，`SubsystemAccessMiddleware` 真正执行子系统权限校验。

**一期处置**：接受"碰巧放行"作为已知限制，不破坏现有功能，但也不提供子系统级权限保护。子系统级权限保护推迟到二期 G-6。

### 审计日志 IP 记录说明

`AuditLogMiddleware.cs:242-261` 获取 IP 顺序：`X-Forwarded-For` -> `X-Real-IP` -> `RemoteIpAddress`

- **开发环境**：直连和走网关都是 127.0.0.1，影响可忽略
- **生产环境**：若 `X-Forwarded-For` 链路断裂，所有请求 IP 变成网关 IP，丢失溯源能力
- **Vite 代理**：基于 http-proxy，默认设置 `X-Forwarded-For`
- **Ocelot**：默认保留上游 headers 转发，但不保证主动设置 `X-Forwarded-For`

**解决方案**：一期 **G-5（网关确保 X-Forwarded-For 传递）**。
1. 网关 `Program.cs` 添加 `UseForwardedHeaders`，让 ASP.NET Core 从 Vite 代理的 `X-Forwarded-For` 解析真实 IP 到 `RemoteIpAddress`
2. `ocelot.json` 的 `GlobalConfiguration` 添加 `DownstreamHeaderTransform`，将 `{RemoteIpAddress}`（网关解析后的真实 IP）写入下游请求的 `X-Forwarded-For`
3. 下游 `AuditLogMiddleware.cs:245-250` 优先读 `X-Forwarded-For`，获取真实客户端 IP

**验证**：V-1.11 审计日志记录的 `RequestIp` 为真实浏览器 IP 而非 127.0.0.1。

## 七、风险与回滚

### 风险
1. **网关单点**：开发环境网关挂了所有接口不可用。缓解：`dotnet watch` 自动重启
2. **配置错误源增加**：网关路由/限流配错是新的问题源。缓解：V-1 验证清单逐项过
3. **限流误伤**：若 G-3 漏做，开发联调会被限流。缓解：G-3 必须与 F-1 同批上线
4. **子系统权限中间件**：`UseSubsystemAccess` 走网关后会执行，但网关无 JWT 解析，三个租户解析策略都失败，`tenant==null` 碰巧放行。**不会拦截现有请求**，但子系统级权限保护形同虚设，需二期 G-5 后才能真正生效。缓解：V-1.9/V-1.12 验证不返回 403

5. **审计日志 IP 溯源**：走网关后若 `X-Forwarded-For` 链路断裂，审计日志记录网关 IP 而非真实客户端 IP。开发环境影响小（均 127.0.0.1），生产环境需 V-1.11 验证。缓解：确认 Vite 代理和 Ocelot 都传递 `X-Forwarded-For`

6. **G-4 阻断性**：`UseHttpsRedirection` 硬编码且网关无 https 端口，不先修复则网关完全不可用。缓解：G-4 必须最先完成
