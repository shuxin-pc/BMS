# 服务时间入库与技师统计归集设计文档

> 状态：**设计已确认**（范围边界已与业务讨论确定）
> 日期：2026-08-20
> 范围：Store 服务（快速开单服务订单 + 项目卡核销）

---

## 1. 背景与目标

### 1.1 问题现状

快速开单（POS）购买服务商品时，存在两个功能缺口：

**缺口一：服务开始/结束时间未入库**

"服务内容"弹窗录入的服务日期 / 开始时间 / 结束时间（涉及"先服务后补单"业务），目前：
- 仅用于前端占用标红检查，**不传后端、不落库**；
- 后端资源冲突检测实际使用 `Order.OrderTime + ServiceProduct.Duration` 推算占用时段（`OrderAppService.cs:306-322`），而非用户选择的真实服务时间，导致占用判定失真；
- `ResourceConflictCheckService.cs:113-114` 对订单占用同样用 `OrderTime + Duration`。

**缺口二：技师统计从未自动归集**

- `TechnicianStatistics`（技师统计）表存在，但**无任何自动写入**——依赖人工维护（`TechnicianStatisticAppService` 仅提供 CRUD + 实时报表）；
- 服务订单创建时后端强制 `Status=1`（进行中），注释声称"待服务完成后由 Complete 接口改为已完成"，但 **Complete 接口并不存在**，服务订单永远停留在"进行中"：无法退款（退款仅限 `Status=2`）、资源永不释放、技师统计无归集触发点；
- 前端已传 `status:2`（"POS 收银即完成"）却被后端强制覆盖为 `1`——存在未完成的改造闭环。

### 1.2 目标

1. **服务开始/结束时间入库**：`OrderItem` 落 `ServiceStartTime / ServiceEndTime`，资源占用检测改用真实服务时间；
2. **技师统计自动归集**：服务订单创建即完成（`Status=2`），创建时自动归集技师统计；退款 / 取消 / 核销冲正时自动回退；
3. **核销项目完整资源录入**：项目卡核销项目本质是服务商品，每个核销项目按服务商品录入技师 / 房间 / 设备 / 服务时间。

### 1.3 已与业务确认的决策

**业务模式：纯补录。** 门店先完成服务，再通过快速开单/核销录入系统。

| 决策点 | 结论 |
|---|---|
| 业务模式 | 纯补录：先完成服务，再录入系统（门店统一先服务后补单） |
| 服务订单状态机制 | **创建即完成**（`Status=2`）；**无"进行中 + 完成按钮"、无 CompleteAsync 接口**（纯补录模式下无需完成闭环） |
| 技师统计归集时机 | **创建时归集**（快速开单服务订单 + 项目卡核销） |
| 回退时机 | 全额退款（`Status=3`）/ 取消（`Status=4`）/ 核销冲正整单回退；**部分退款按全额计入**（仍 `Status=2` 不回退） |
| 项目卡核销 | **纳入归集**，采用**项目级**技师/资源：每个核销项目按服务商品提供技师 / 房间 / 设备 / 服务开始/结束时间 |
| 统计归属日期 StatDate | 用**服务时间日期**（`ServiceStartTime.Date`），为空则回退订单时间 |
| 占用检测范围 | **预约 + 所有有效订单**（未退款未取消，`Status∈{1,2}`）——同一时段冲突检测 |
| 占用检测维度 | **B：技师 + 房间 + 设备 同时检测** |
| 实时报表口径 | **统一为仅 `Status==2`**（修正现状 `Status=2 或 3` 双计，与归集表对齐） |
| 归集算法 | 按"技师 + 日期"全量重算并 upsert，天然幂等，重算即回退 |

## 2. 需求一：服务开始/结束时间入库

### 2.1 数据模型

`OrderItem` 实体新增两列（表 `OrderItems`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ServiceStartTime` | `DateTime?` | 服务开始时间（服务内容弹窗 / 核销项目录入 / 预约转单继承） |
| `ServiceEndTime` | `DateTime?` | 服务结束时间（开始时间 + 服务时长自动计算） |

### 2.2 落库链路

**快速开单服务订单：**
```
服务内容弹窗（serviceDate+startTime / serviceDate+endTime）
  → CartItem.serviceStartTime/serviceEndTime（确认弹窗时拼接完整时间戳）
  → OrderItemCreate.serviceStartTime/serviceEndTime
  → OrderItem.ServiceStartTime/ServiceEndTime（Mapster 自动映射实体子集合）
```

**预约转单**（`addAppointmentToCart`）：继承预约的 `appointmentDate + appointmentTime / appointmentDate + endTime` 到购物车，提交时落库。

**项目卡核销项目**（见 3.4）：每个核销项目录入服务时间，经核销 DTO → 核销明细 → 核销订单 OrderItem 落库。

### 2.3 资源占用检测改造

**范围**：预约 + 所有有效订单（未退款未取消，`Status∈{1,2}`）。纯补录模式下订单创建即完成（`Status=2`），不再是"进行中占用、完成后释放"语义，而是**同一时段冲突检测**——预约 / 核销项目 / 服务订单在录入时，检测该时段是否已被预约或有效订单占用。

**维度**：技师 + 房间 + 设备 同时检测（半开区间 `[start, end)` 重叠算法）。

**时段**：
- `OrderAppService.CreateAsync`（289-348 行）：订单资源冲突检测的结束时间改为优先用 `item.ServiceStartTime / ServiceEndTime`（有值则用），为空回退 `orderStart + duration`；
- `ResourceConflictCheckService`（84-138 行）：`OrderItem` 占用时段 `oStart/oEnd` 改为优先用 `oi.ServiceStartTime / oi.ServiceEndTime`（有值），为空回退 `oi.Order.OrderTime + duration`。

> 注：服务订单创建即 `Status=2`，创建时资源冲突检测仍执行（与预约、其他有效订单对比），保证同一时段同一技师/房间/设备不冲突。

## 3. 需求二：技师统计自动归集

### 3.1 归集算法（核心）

在 `TechnicianStatisticAppService` 新增：

```
Task RecalculateTechnicianStatisticAsync(long tenantId, long storeId, long technicianId, DateTime statDate)
```

**按"技师 + 日期"全量重算并 upsert**。天然幂等，回退无需区分增/减（重算即回退）。

```
1. 查 statDate 当天该技师的有效服务明细：
   OrderItem JOIN Order
   WHERE oi.TenantId=tenantId AND oi.StoreId=storeId
     AND oi.TechnicianId=technicianId AND oi.TechnicianSource=1   -- 仅商家技师
     AND o.Status = 2                                             -- 仅已完成
     AND (oi.ServiceStartTime?.Date ?? o.OrderTime.Date) == statDate
   -- o.Status==2 天然排除：全额退款(3)/取消(4)/核销冲正(4)；部分退款(仍2)按全额计入 ✓
2. 关联 ServiceProduct.Duration（ProductId → Product.MasterId → ServiceProduct.Duration）
3. 计算指标：
   - ServiceCount        = 明细条数
   - ServiceMinutes      = Σ(Quantity × Duration)
   - TotalTechnicianFee  = Σ(TechnicianFee ?? 0)
   - ReturnCustomerCount = 按 CustomerId 分组、出现次数 >1 的组数
4. upsert TechnicianStatistics（定位键 TenantId+StoreId+TechnicianId+StatDate）
   -- 无有效明细则删除该记录
```

> 口径对齐：`GetReportAsync`（实时报表）已实现完全相同的筛选与聚合逻辑（`TechnicianStatisticAppService.cs:222-274`），本算法直接复用其口径。

### 3.2 触发点

| 场景 | 触发动作 | 操作 |
|---|---|---|
| 快速开单服务订单创建 | `OrderAppService.CreateAsync` | 创建即 `Status=2`，对涉及的每个 (技师, 日期) 重算归集 |
| 全额退款（`Status→3`） | `OrderAppService.RefundAsync` | 重算回退 |
| 取消（`Status→4`） | `OrderAppService.CancelAsync` / `ReverseOrderAsync` | 重算回退 |
| 项目卡核销创建 | `TreatmentCardVerifyAppService.CreateAsync` | 对核销各项目的 (技师, 日期) 重算归集 |
| 核销冲正（订单 `Status→4`） | `TreatmentCardVerifyAppService.ReverseAsync` | 重算回退 |

> 服务订单创建即 `Status=2`（纯补录，无"完成服务"接口），归集在创建时触发。

### 3.3 实时报表口径统一

- `GetReportAsync`（`TechnicianStatisticAppService.cs:230`）原过滤为 `o.Status == 2 || o.Status == 3`（已退款订单仍计入），**改为仅 `o.Status == 2`**，与归集表口径对齐（两者数字一致）。

### 3.4 项目卡核销改造（项目级，核心新增）

**业务原则**：核销项目本质是服务项目商品，每个核销项目需按服务商品完整录入 **技师 / 房间 / 设备 / 服务开始/结束时间**，并参与资源占用检测。

**前端核销弹窗**（`quick/index.vue` 597-663 行）：
- 每个核销项目行在"服务项目 / 次数 / 金额"基础上新增：
  - 技师选择（复用快速开单"商家技师 / 平台技师"互斥下拉）
  - 房间 / 床位选择、设备选择（按项目技能过滤，复用快速开单服务弹窗交互）
  - 服务日期 + 开始时间（结束时间按服务时长自动计算，可改）
  - 资源占用标红（复用 `getResourceAvailability` 占用检查）
- 核销行加入购物车（`confirmVerifyCard` 2498 行）时携带上述资源/时间字段到 CartItem verify 行的 `verifyItems`；
- 结算聚合（1759-1779 行）透传各项目的技师/房间/设备/服务时间。

**后端**：
- `TreatmentCardVerifyItemInput`（DTO）：新增 `TechnicianId / TechnicianSource / RoomId / EquipmentId / ServiceStartTime / ServiceEndTime`
- `TreatmentCardVerifyItem` 实体（表 `TreatmentCardVerifyItems`）：新增同名字段（核销明细是原始记录，资源/时间随明细落库）
- `TreatmentCardVerifyAppService.CreateAsync`：
  - 构建核销订单 `OrderItem`（264-276 行）时，从核销项目复制技师/房间/设备/服务时间到 OrderItem；
  - 核销创建前对每个项目做**资源冲突检测**（技师/房间/设备 + 服务时间区间，复用 `IResourceConflictCheckService.CheckAsync`），冲突则拒绝核销；
  - 核销创建后对涉及的 (技师, 日期) 归集（statDate = 该项目 ServiceStartTime.Date）。
- `TreatmentCardVerifyAppService.ReverseAsync`（冲正，519-529 行订单 `Status→4` 后）：重算回退。

## 5. 范围边界（已确认，最终结论）

### 5.1 技师统计两个数据源的口径

- **已确认**：`GetReportAsync` 实时报表统一为仅 `Status==2`（与归集表口径一致，两者数字对齐）。

### 5.2 核销订单的资源占用语义

- **已确认（选项 B）**：占用判定为"同一时段冲突检测"，范围 = 预约 + 所有有效订单（未退款未取消，`Status∈{1,2}`），核销未来服务时段同样被占用保护，核销之间也互检。维度 = 技师 + 房间 + 设备。

### 5.3 "完成服务"入口位置

- **已确认**：纯补录模式，服务订单创建即 `Status=2`（已完成），**无"进行中 + 完成按钮"**，无 CompleteAsync 接口。

### 5.4 其余默认约定（无异议按此执行）

- 服务订单创建即 `Status=2`；核销订单创建即 `Status=2`；
- 核销项目行的技师/房间/设备为**可选项**（未选则不占用、不参与技师归集），服务日期/开始时间为**必填**（与快速开单服务弹窗一致）；
- 核销项目服务结束时间 = 开始时间 + 服务时长自动计算（与快速开单一致）；
- 订单详情页暂不展示服务时间（`OrderItemDto` 字段已加，页面展示留待后续）；
- 部分退款按全额计入（已确认，不作折算）；
- 仅商家技师（`TechnicianSource==1`）参与技师统计归集（平台技师不计入）。

## 6. 验证方案

1. **后端编译**：`dotnet build src/Services/Store`；生成迁移并应用（OrderItems +2 列、TreatmentCardVerifyItems +6 列）；
2. **前端类型/lint**：`vue-tsc --noEmit` + `eslint`（快速开单 / 核销弹窗）；
3. **端到端手工验证**：
   - 快速开单选服务项目 → 弹窗录日期/时间/技师/房间/设备 → 下单 → 订单 `Status=2`，DB 确认 OrderItem 含 `ServiceStartTime/ServiceEndTime`，`TechnicianStatistics` 生成该技师当天记录（ServiceCount / ServiceMinutes / TotalTechnicianFee / ReturnCustomerCount）；
   - 全额退款 → 统计回退/清除；部分退款 → 不回退；
   - 取消订单 → 统计回退；
   - 核销弹窗多项目，每项目录技师/房间/设备/时间 → 核销订单 OrderItem 落资源/时间，技师统计归集（StatDate=服务时间日）；冲正 → 统计回退；
   - 核销项目资源冲突（技师/房间/设备在服务时段被预约/有效订单占用）→ 拒绝核销；
   - 预约转单 → 订单继承预约服务时间，占用检测正确；
   - 资源占用：同一时段同一技师/房间/设备三维冲突检测正确。
