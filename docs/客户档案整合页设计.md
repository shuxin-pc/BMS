# 客户档案整合页设计

## 一、背景与目标

当前客户管理下有 4 个独立菜单页面，各自是一个"全店记录列表 + 客户名/手机号搜索"的形态：

| 菜单 | 路径 | 行数 |
|---|---|---|
| 美容档案 | `/store/customer/beauty-profile` | 539 |
| 体型数据 | `/store/customer/body-data` | 517 |
| 反应记录 | `/store/customer/reaction` | 566 |
| 照片管理 | `/store/customer/photo` | 776 |

问题：这 4 类数据在业务上都从属于同一个客户，但界面上被拆成 4 个入口。门店人员为某位客户建档时，需要在 4 个菜单间反复跳转，并在每个页面重复输入同一个客户名。

目标：整合为单一菜单 `服务档案`，页面内以选项卡切换，**4 个选项卡共享同一个"当前客户"上下文**，形成真正的客户档案视角。

### 1.1 菜单命名：为何不叫"客户档案"

`StoreMenuSeedData.cs:90` 中 `store:customer:profile` 已占用"客户档案"这个名称，且与新菜单同属"客户管理"父目录。若新菜单也叫"客户档案"，侧边栏同一分组下会出现两个同名项，用户无法区分，验收标准也无法判定。

因此新菜单定名 **服务档案**（承载客户接受服务过程中产生的档案数据），Code 与路径仍为 `store:customer:archive` / `/store/customer/archive`。既有的"客户档案"（客户基本信息管理）不改动。

## 二、关键前置调查结论

### 2.1 后端零改动

4 个查询 DTO 均已支持 `CustomerId` 精确过滤，且 AppService 已实现过滤逻辑：

| 服务 | 过滤实现位置 |
|---|---|
| `CustomerBeautyProfileAppService` | `:50-51` |
| `BodyDataRecordAppService` | `:43-44` |
| `ServiceReactionAppService` | `:51-52` |
| `ServiceComparisonPhotoAppService` | `:43-44` |

本次改造不需要修改任何后端查询逻辑。

### 2.2 美容档案是"一客户一份"，形态与其余三个不同

`CustomerBeautyProfileAppService.cs:119-123` 存在唯一性校验：*同租户同门店下每个客户仅允许一份未删除的美容档案*。

因此选中客户后，美容档案应呈现为**一份详情**，而体型数据、反应记录、照片管理是**多条时间序列记录**，仍为列表 + 分页。若给单份档案配表格和分页器，界面会失真。

### 2.3 现有权限体系可以间接控制选项卡，无需新增权限层级

`Menu.Type` 只有三级（`Menu.cs:44-46`）：`0-目录`、`1-菜单`、`2-按钮`，确实没有"选项卡"层级。但按钮权限（`Type=2`）本身就是通用的"页面内区块权限"，链路完整：

1. 后端只收集 `Type == 2` 的菜单 Code 作为权限码 —— `UserRepository.cs:280-285`
2. 经 `AuthAppService.cs:89-90` 下发到前端 `userInfo.permissions`
3. 前端 `userStore.hasPermission(code)` 判断 —— `stores/user.ts:154-161`
4. `stores/user.ts:529-531` 注释确认了该设计意图：*按钮类型(type=2)不显示在侧边栏，按钮权限通过 permissions 列表控制页面内操作*

**既有同类先例**：供应商页面用 `store:product:supplier:create:public`、`edit:public` 两个按钮权限控制页面内元素显隐（`supplier/index.vue:323-325`）。选项卡只是另一种"页面内元素"。

### 2.4 菜单可见性靠祖先推导

`stores/user.ts:473-493`：已授权菜单会向上推导出所有祖先并加入可见集合。因此只要授权了任意一个子按钮，父菜单就会出现在侧边栏。

**由此产生一个必须处理的边界**：若某角色被授予了菜单但 4 个选项卡权限一个都没有，页面会打开成一个空壳。

### 2.5 `:view` 按钮不需要手写进种子数据

`SystemSeedData.EnsurePageViewButtons`（`:213-330`）会为每个 `Type=1` 菜单自动创建 `菜单Code:view` 按钮（Name="页面查看"）并授权 super_admin。种子数据中只需定义 4 个选项卡业务按钮。

### 2.6 无其它页面引用旧路径

已确认代码库中除种子数据外，无任何页面跳转引用这 4 个路由路径。

### 2.7 四类数据的可写能力并不一致

`api/customer-profile/index.ts` 实际导出的函数决定了各面板能提供哪些操作：

| 数据 | 查询 | 新增 | 编辑 | 删除 |
|---|---|---|---|---|
| 美容档案 | ✅ | ✅ | ✅ `updateBeautyProfile` | ✅ `deleteBeautyProfile` |
| 体型数据 | ✅ | ✅ | ❌ 无接口 | ❌ 无接口 |
| 反应记录 | ✅ | ✅ | ❌ 无接口 | ❌ 无接口 |
| 照片管理 | ✅ | ✅ | ❌ 无接口 | ❌ 无接口 |

后三者的原页面同样只有"新增"和"详情"两个入口，不存在编辑与删除。**本次改造不新增任何后端接口**，因此这三个面板保持只增不改的形态，"操作"列仅保留详情。

### 2.8 前端无 lint 可用

`package.json` 声明了 `lint` 脚本，但 eslint 既不在 `devDependencies` 中，也未安装到 `node_modules`，且仓库无 eslint 配置文件——执行 `npm run lint` 会直接报"eslint 不是内部或外部命令"。因此验证手段只有 `npm run build`（内含 `vue-tsc` 类型检查）与手工验收。

为一次 UI 整合改造引入 eslint 属于超出需求的改动，本次不引入。

## 三、目录结构

```
views/store/customer/archive/
  index.vue                  容器：客户选择器 + 选项卡 + 权限过滤 + 空态
  components/
    BeautyProfilePanel.vue   美容档案（单份详情 + 编辑弹窗）
    BodyDataPanel.vue        体型数据（列表 + 分页 + 弹窗）
    ReactionPanel.vue        反应记录（列表 + 分页 + 弹窗）
    PhotoPanel.vue           照片管理（配对展示）
    PhotoUploadDialog.vue    照片上传弹窗（含 base64 转换）
```

旧的 4 个页面目录删除。业务逻辑迁移而非重写。

照片上传弹窗单独成文件：原 `photo/index.vue` 776 行，去掉客户搜索与客户下拉后仍有约 740 行，超出可一次性通读的范围。按职责拆分后，`PhotoPanel` 只负责列表配对展示，上传表单及其 base64 转换独立可测。

## 四、容器与子组件的契约

**容器职责**（仅三件事）：选择客户、按权限过滤选项卡、选项卡懒加载。

**子组件契约**：

- 入参：`props: { customerId: number; customerName: string }`
- 职责：自行负责数据加载、分页、增删改弹窗
- 容器不感知子组件内部状态；子组件不感知容器如何选出客户
- `customerId` 变化时子组件 `watch` 重新加载数据

`customerName` 一并传入，是因为各面板的弹窗需要只读展示"当前客户是谁"。若不传，4 个面板就得各自再调一次 `getCustomerOptions()`（全量拉取 9999 条）反查名字，重复 4 次。容器已持有该信息，直接传递即可。

该边界保证每个面板可独立理解与测试。容器预计不超过 150 行，四个面板均比原页面更短（去掉了客户名/手机号搜索项、客户列、客户选择字段）。

## 五、各面板改动要点

| 面板 | 去掉 | 改为 |
|---|---|---|
| 全部 | 搜索区的客户名称、手机号字段 | 由顶部统一客户上下文提供 |
| 全部 | 表格中的客户名称、手机号列 | 列宽让给业务字段 |
| 全部 | 弹窗中的"选择客户"下拉 | 只读展示 `props.customerName`，提交时用 `props.customerId` |
| 全部 | 详情弹窗中的客户名称、手机号项 | 同上，客户已恒定，无需重复 |
| 美容档案 | 表格 + 分页 | 详情卡片；有档案显示"编辑"+"删除"，无档案显示空态 + "新建档案" |
| 体型数据 | — | 保留记录日期区间筛选；操作列仅"详情"（无编辑/删除接口，见 2.7） |
| 反应记录 | — | 保留日期区间 + 严重程度筛选；操作列仅"详情" |
| 照片管理 | — | 保留服务项目筛选、前后对比配对逻辑；上传弹窗拆为独立组件 |

照片面板另需注意：配对卡头部原本展示 `pair.customerName`，客户恒定后应去掉；"关联订单"下拉原由客户选择变更触发加载，改为面板挂载及 `customerId` 变化时加载，其 `:disabled="!photoForm.customerId"` 一并去掉。

## 六、客户选择器

复用已有的 `getCustomerOptions()`（`api/customer-profile/index.ts:49-52`），配 `el-select filterable` 本地过滤，与 `photo/index.vue:543` 现有做法一致。

**已知权衡**：该函数以 `pageSize: 9999` 拉取全量客户，客户量大时存在性能隐患。这是既有实现的问题，非本次改造引入。经确认沿用现状以保持一致，暂不引入远程搜索模式。若后续出现性能问题，可改为 `getCustomers({ name, pageSize: 20 })` 远程搜索（`pos/quick/index.vue:686` 有先例）。

## 八、权限设计

`StoreMenuSeedData.cs` 中删除旧 4 条菜单定义（`:151-154`），新增：

| Code | Type | 名称 | Path | Sort |
|---|---|---|---|---|
| `store:customer:archive` | 1 | 服务档案 | `/store/customer/archive` | 6 |
| `store:customer:archive:beauty` | 2 | 美容档案 | — | 1 |
| `store:customer:archive:body-data` | 2 | 体型数据 | — | 2 |
| `store:customer:archive:reaction` | 2 | 反应记录 | — | 3 |
| `store:customer:archive:photo` | 2 | 照片管理 | — | 4 |

Type=2 按钮的 `ParentCode` 均为 `store:customer:archive`，`IsVisible=false`、`IsCache=false`，与 `store:product:master:edit`（`:146`）的既有写法一致。

前端以 `v-if="userStore.hasPermission('store:customer:archive:beauty')"` 控制 `el-tab-pane` 渲染。

**两个必须处理的边界**：

1. 无任何选项卡权限却能进入页面 → 整页空态提示"暂无可查看的档案内容，请联系管理员分配权限"
2. 默认激活的选项卡必须是**第一个有权限的**选项卡，不可硬编码为美容档案，否则无该权限的用户会看到空白

## 九、种子数据

### 9.1 正式种子数据

`SystemSeedData.cs` 新增 `EnsureCustomerArchiveMenuAuths(context)`，严格仿照 `EnsureProductMasterMenuAuths`（`:341-403`）的既有模式：

- 仅授权 `super_admin` 角色，与现有惯例一致
- 目标 Code 为新菜单及 4 个选项卡按钮，`:view` 由 `EnsurePageViewButtons` 处理，此处不重复
- 幂等，可安全重复调用，用于已有数据库的增量补全

说明：正式种子数据中不存在"门店管理员"角色（`Code=MDGLY`、`IsSystem=false`，属于测试租户 `MDZH` 的自建业务角色），且 `tenant_admin` 在正式种子中从未被授权任何菜单。因此正式种子仅授权 `super_admin`。

### 9.2 测试种子数据

`TestSeedData/` 下三个文件需同步：

**`Menus.json`**：删除旧 8 条（4 个菜单 `...000021`~`...000024` + 4 个 `:view` 按钮 `...000121`~`...000124`），新增 6 条（1 菜单 + 1 个 `:view` + 4 个选项卡按钮）。

**`RoleMenuAuths.json`**：删除上述 8 个菜单的旧授权，为新菜单及其 5 个按钮分别授权给三个角色：

| 角色 | Code | RoleId |
|---|---|---|
| 超级管理员 | `super_admin` | `206963827227496448` |
| 管理员 | `tenant_admin` | `206963827227496449` |
| 门店管理员 | `MDGLY` | `206965965286543360` |

（这三个角色正是旧 4 个菜单原有的授权对象，保持一致。）

**`SubsystemMenus.json`**：新菜单挂到门店管理子系统 `206963886274908160`。

### 9.3 测试种子数据的生效方式

`Bms.System.Api/appsettings.json:28` 已设 `SeedTestData:Enabled = true`。启动时 `Program.cs:244-249` 走 `TestSeedData.InitializeAsync`，该分支会清空并重载 Menus / SubsystemMenus / RoleMenuAuths 三张表。

因此改完 JSON 后，**重启 `Bms.System.Api` 即生效**，无需手工建库。但前端权限与动态路由在登录时写入 store，必须**重新登录**才能看到变化。

### 9.4 正式种子数据在当前环境无法验证

由于 `SeedTestData:Enabled = true`，`Program.cs:250-271` 的 `else` 分支不会执行——`StoreMenuSeedData` 的新定义与 `EnsureCustomerArchiveMenuAuths` 都不会被调用。这两处改动在当前环境下**只能靠编译通过来保证正确性**，浏览器里看到的效果全部来自测试种子数据。

另外 `EnsureCustomerArchiveMenuAuths` 与既有的 `EnsureProductMasterMenuAuths` 一样，在菜单尚未被 Store 服务注册时会提前返回（`menus.Count == 0`），这是既有行为，不作改动。

### 9.5 已部署环境的注意事项

`StoreMenuRegistrationService.cs:59-63` 仅在子系统不存在时才创建菜单，**不做差异同步、不会自动删除多余菜单**。因此已部署环境中的旧菜单需要重建种子数据或手工清理，不在本次代码改动范围内。

可观察到的症状：旧菜单仍显示在侧边栏，但点击无法打开——组件目录已删除，`router/modules.ts:22-25` 的 `resolveComponent` 只 `console.warn` 后跳过该路由注册。

依据编码规范"加了软删除的表在没有明确指令要求的情况下不能物理删数据"，本次改造不提供任何删除线上菜单数据的脚本。

## 十、验证标准

1. `npm run build` 类型检查通过
2. 超级管理员登录 → 侧边栏"客户管理"下显示"服务档案"菜单，旧 4 个菜单消失，既有的"客户档案"菜单仍在且不受影响
3. 选中客户 → 4 个选项卡均只显示该客户数据，切换选项卡无需重新输入客户
4. 切换客户 → 当前选项卡数据随之刷新
5. 切换选项卡时只发出当前面板的请求，不并发 4 个（懒加载生效）
6. 美容档案选项卡：有档案显示详情与编辑、删除入口，无档案显示空态与新建入口；编辑、删除、新建均生效
7. 体型数据、反应记录、照片管理三个选项卡：新增与详情功能与改造前行为一致（这三者本无编辑/删除，见 2.7）
8. 角色授权界面取消某个选项卡权限 → 该用户重新登录后对应选项卡消失，其余正常
9. 取消全部 4 个选项卡权限 → 页面显示空态提示而非空白
10. 管理员、门店管理员账号登录后均可正常访问服务档案菜单
