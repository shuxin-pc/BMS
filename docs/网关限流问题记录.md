# 网关限流问题记录

## 一、概述

在"启用网关改造"一期实施过程中，前端通过网关访问 `/api/system/SystemConfigs/system` 接口时返回 503。经系统排查，确认是 Ocelot 24.1.0 限流中间件的客户端识别机制问题。本文档记录问题现象、调查过程、根因分析和当前处理方式，供后续解决限流配置参考。

## 三、错误现象

### 触发条件

前端（http://localhost:3000）通过 Vite 代理访问网关（http://localhost:5020），请求系统配置接口：

```
GET http://localhost:3000/api/system/SystemConfigs/system
```

请求链路：浏览器(3000) -> Vite 代理 -> 网关(5020) -> System.Api(5000)

### 现象

- 网关返回 **HTTP 503 Service Unavailable**
- System.Api（5000）直接访问返回 **HTTP 200**（服务正常）
- 所有端口（5000/5010/5020/5030）均正常监听

### HTTP 响应

```
HTTP/1.1 503 Service Unavailable
Content-Length: 162
Date: Mon, 13 Jul 2026 07:24:18 GMT
Server: Kestrel
Retry-After: -1

Rate limiting client could not be identified for the route '/api/system/{everything}' due to a missing or unknown client ID header required by rule '600/1m/w0ms'!
```


### 日志关键点

1. **限流中间件命名空间**：`Ocelot.RateLimiting.RateLimitingMiddleware`（注意 `RateLimiting` 带 -ing 后缀，旧版为 `Ocelot.RateLimit`）
2. **错误类型**：`QuotaExceededError`（但实际并非配额超限，而是客户端识别失败）
3. **限流规则**：`600/1m/w0ms`（对应 Limit=600, Period=1m，来自 ocelot.Development.json）
4. **错误原因**：`missing or unknown client ID header`（缺失或未知的客户端 ID header）

## 五、调查过程

### 5.1 初始假设与验证

**假设1**：System.Api（5000）未启动，网关转发失败返回 503。

**验证**：
```
netstat -ano | grep ":5000"   -> LISTENING（端口正常）
curl http://localhost:5000/api/system/SystemConfigs/system   -> HTTP 200（服务正常）
curl http://localhost:5020/api/system/SystemConfigs/system   -> HTTP 503（网关返回 503）
```

**结论**：假设推翻。下游服务正常，503 来自网关自身。

### 5.2 限流错误确认

查看 503 响应体，发现是限流错误：
```
Rate limiting client could not be identified for the route '/api/system/{everything}' due to a missing or unknown client ID header required by rule '600/1m/w0ms'!
```

`600/1m` 对应 ocelot.Development.json 中配置的 `Limit=600, Period=1m`，确认是 Ocelot 限流中间件返回的 503。

### 5.3 客户端 ID 识别尝试

尝试通过不同 header 提供客户端 ID，均无效：

| 尝试 | 请求 header | 结果 |
|------|------------|------|
| 不带 header | 无 | 503 |
| 带 ClientId | `ClientId: test-client` | 503 |
| 带 X-Forwarded-For | `X-Forwarded-For: 127.0.0.1` | 503 |

### 5.4 显式配置 ClientIdHeader

在 ocelot.Development.json 的 system 路由 RateLimitOptions 中显式配置：
```json
"ClientIdHeader": "X-Forwarded-For"
```

重启网关后测试，仍返回 503。配置项未生效。

### 5.5 对比有限流与无限流路由

| 路由 | 有限流 | 请求路径 | 结果 |
|------|--------|---------|------|
| /api/system/SystemConfigs/system | 是 | 真实接口 | 503（限流拦截） |
| /api/system/nonexistent | 是 | 不存在路径 | 400（MultiTenant 拦截，未到限流） |
| /api/identity/nonexistent | 否 | 不存在路径 | 400（下游返回） |
| /api/store/nonexistent | 是 | 不存在路径 | 400（下游返回） |
| /api/customer/nonexistent | 否 | 不存在路径 | 400（下游返回） |

**关键发现**：store/product 路由也有 `EnableRateLimiting: true`，但能正常转发（返回 400）。只有 system/SystemConfigs/system 被 MultiTenant 放行后到达限流中间件，触发 503。

**原因**：网关中间件顺序为 `UseMultiTenant -> UseOcelot`。MultiTenant 对 `/api/system/SystemConfigs/system` 在白名单中（放行），请求到达 Ocelot 限流中间件触发 503。而 `/api/system/nonexistent` 不在白名单，MultiTenant 先返回 400（"无效的租户信息"），未到达限流。

### 5.6 禁用限流验证

将 ocelot.Development.json 的 `EnableRateLimiting` 改为 `false`，重启网关：
```
curl http://localhost:5020/api/system/SystemConfigs/system   -> HTTP 200（正常返回系统配置）
```

**结论**：根因确认是 Ocelot 24.1.0 限流启用时的客户端识别问题。

## 六、根因分析

### 6.1 Ocelot 24.1.0 限流重构

Ocelot 24.x 对限流模块进行了重构：
- **命名空间变化**：从 `Ocelot.RateLimit` 改为 `Ocelot.RateLimiting`（日志中可见 `Ocelot.RateLimiting.RateLimitingMiddleware`）
- **客户端识别机制变化**：限流启用时强制要求 client ID header，无法识别则返回 503（而非旧版的 429 配额超限）

### 6.2 ClientIdHeader 配置无效

Ocelot 文档记载的 `RateLimitOptions.ClientIdHeader` 配置项（默认值 `"ClientId"`）在 24.1.0 中未生效：
- 显式配置 `"ClientIdHeader": "X-Forwarded-For"` 后，带该 header 的请求仍返回 503
- 可能 24.1.0 的客户端识别逻辑不再读取此配置项，或需要额外的服务注册（如分布式缓存、客户端 ID 提供者等）

### 6.3 历史原因

原 `ocelot.json` 的 system/store/product 路由均有 `EnableRateLimiting: true, Limit: 60`，但前端直连各服务端口（绕过网关），限流配置从未被实际触发。启用网关改造后前端统一走网关，限流配置生效，暴露了此既有问题。

## 七、当前处理

### 7.1 临时处理：禁用限流

为不阻塞一期"走网关可达"目标，当前禁用所有限流：

| 文件 | 改动 |
|------|------|
| `ocelot.json` | 3 处 `EnableRateLimiting: true` -> `false`（system/store/product 路由） |
| `ocelot.Development.json` | 3 处 `EnableRateLimiting: false`（开发环境，Limit=600 保留但不生效） |

### 7.2 影响评估

- **开发环境**：无限流，满足联调需求
- **生产环境**：无限流保护。但原限流配置从未实际工作过（前端直连绕过网关），故未降低现有保护水平
- **功能可用性**：网关转发正常，仅缺失限流能力

## 八、后续待解决

### 8.1 研究 Ocelot 24.1.0 限流正确配置

需要确认以下问题：
1. Ocelot 24.1.0 的 `RateLimitOptions` 有效配置项有哪些（`ClientIdHeader` 是否仍有效）
2. 限流客户端识别的新机制（是否需要额外的服务注册、客户端 ID 提供者等）
3. 是否需要 `IDistributedCache`（分布式缓存）支持限流计数存储
4. 查阅 Ocelot 24.x 发行说明（changelog）确认限流 breaking changes

### 8.2 验证项

限流配置修复后需验证：
1. 带 `X-Forwarded-For` header 的请求能被正确识别客户端
2. 超过 Limit 的请求返回 429（而非 503）
3. ClientWhitelist 中的客户端不限流
4. 生产环境（经反向代理）限流正常工作
