## 1. 项目概述

### 1.1 项目背景
本项目是面向企业的SaaS化BMS（后台管理系统）平台，采用微服务分布式架构，支持集团级用户规模，提供系统管理、权限控制、组织架构、运营配置等企业级后台管理能力。

### 1.2 核心需求
- **用户规模**：集团级，支持10000+用户，并发<10000
- **集成需求**：定制化集成，支持ERP、CRM、OA及各行业专用系统
- **部署方式**：SaaS化部署，支持多租户模式
- **行业定位**：通用企业后台管理，支持多行业多场景
- **开发优先级**：平台化优先，先建设基础平台，再快速构建业务功能

### 2.2 架构设计原则
1. **严格分层**：各层职责清晰，单向依赖，不允许跨层调用
2. **服务自治**：每个微服务独立开发、独立部署、独立运维
3. **云原生友好**：全栈支持容器化部署，Kubernetes编排
4. **平台化支撑**：公共服务层抽象通用能力，避免重复建设
5. **高可用设计**：无单点故障，支持水平扩展
6. **安全可靠**：多层安全防护，数据加密存储和传输

## 4. 多租户架构设计

### 4.1 混合隔离方案
采用**Schema级隔离 + 共享基础服务**的混合方案，同时支持三种隔离级别并存：
```
┌─────────────────────────────────────────────────────────────────┐
│                          租户访问入口                            │
│ 租户1: tenant1.bms.com  租户2: tenant2.bms.com  ...             │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│                          API网关层                                │
│  1. 域名解析识别租户ID  2. 租户状态校验  3. 路由到对应服务         │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│                          业务服务层                                │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐              │
│  │ 租户1 Schema│  │ 租户2 Schema│  │ 租户3 Schema│  ...          │
│  │ (业务数据)  │  │ (业务数据)  │  │ (业务数据)  │              │
│  └─────────────┘  └─────────────┘  └─────────────┘              │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│                          共享基础服务层                            │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐              │
│  │ 全局租户表  │  │ 公共配置表  │  │ 系统字典表  │  全局共享数据   │
│  └─────────────┘  └─────────────┘  └─────────────┘              │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐              │
│  │ 文件存储    │  │ 消息队列    │  │ 缓存集群    │  共享基础设施   │
│  └─────────────┘  └─────────────┘  └─────────────┘              │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 三种隔离级别对比
| 隔离级别 | 隔离方式 | 优点 | 缺点 | 适用客户 |
|---------|---------|------|------|---------|
| 独立数据库 | 每个租户独立数据库 | 隔离级别最高，数据安全，性能好 | 成本高，维护复杂 | 大型企业VIP客户 |
| Schema级隔离 | 共享数据库，每个租户独立Schema | 隔离级别较高，成本适中，性能较好 | 跨租户统计复杂，Schema管理成本高 | 标准企业客户 |
| 行级隔离 | 共享数据库，共享Schema，通过租户ID隔离 | 成本最低，维护简单 | 隔离级别最低，性能有损耗 | 免费试用、小型客户 |

### 4.3 租户生命周期管理
1. **租户注册**：自动创建租户Schema、初始化基础数据、分配资源配额
2. **租户启用/禁用**：动态控制租户访问权限，禁用后所有接口拒绝访问
3. **租户扩容**：动态调整租户资源配额（用户数、存储容量、API调用量等）
4. **租户数据导出**：支持一键导出租户所有业务数据，满足合规要求
5. **租户注销**：软删除租户数据，保留30天后彻底删除，可恢复

### 4.4 复杂度控制
通过多租户框架封装，对业务开发完全透明，开发复杂度增加不超过15%：
- 统一拦截器：请求入口统一解析租户信息，存入ThreadLocal上下文
- 动态数据源：根据租户级别自动切换数据源/Schema
- ORM拦截器：自动为所有查询追加租户ID过滤条件
- 统一迁移工具：数据库迁移时自动遍历所有租户Schema

### 4.5 多级角色权限架构

#### 4.5.1 设计目标
- 明确区分平台级管理员（超级管理员）与租户级管理员（租户管理员）的职责边界
- 超级管理员可管理所有租户，租户管理员只能管理本租户数据
- 基于角色实现权限控制，业务逻辑判断依据角色进行

#### 4.5.2 角色定义

| 角色代码 | 角色名称 | 所属租户 | 职责范围 |
|---------|---------|---------|---------|
| `super_admin` | 超级管理员 | 平台租户(platform) | 管理所有租户、创建租户管理员、系统全局配置 |
| `tenant_admin` | 租户管理员 | 具体租户 | 管理本租户内的用户、角色、菜单、业务数据 |

> 详细的业务逻辑说明请参阅《BMS系统基础数据权限说明》文档。

#### 4.5.3 平台租户设计

引入特殊的"平台租户"概念，用于承载超级管理员：

- **平台租户代码**：`platform`
- **平台租户不参与业务数据隔离**
- **超级管理员属于平台租户**，可管理所有业务租户
- **租户管理员属于具体租户**，只能管理本租户数据

#### 4.5.4 数据隔离策略

| 角色 | 查询范围 | 隔离方式 |
|-----|---------|---------|
| super_admin | 所有租户数据 | 不过滤租户ID |
| tenant_admin | 当前租户数据 | 强制追加 TenantId = 当前用户.TenantId |

#### 4.5.5 数据权限类型

数据范围用于控制角色对应的用户登录后能访问哪些组织的数据：

| 类型值 | 名称 | 说明 |
|--------|------|------|
| 1 | 全部数据 | 查看角色所属租户内的所有数据 |
| 2 | 部门及以下 | 查看本部门及下属子部门的数据 |
| 3 | 仅本人 | 只能查看自己创建的数据 |
| 4 | 自定义 | 可指定具体的组织ID列表 |

> 详细的业务逻辑、数据权限控制、菜单权限分配、子系统管理等请参阅《BMS系统基础数据权限说明》文档。

### 5.2 双消息队列方案
| 消息队列 | 定位 | 适用场景 | 核心优势 |
|---------|------|---------|---------|
| **RabbitMQ** | 业务消息总线 | 服务间异步调用、延时任务、事务性消息、高可靠消息投递 | 可靠性高、支持丰富路由模式、支持高级特性 |
| **Kafka** | 流式数据处理平台 | 生产设备数据采集、日志传输、实时数据同步、大数据分析 | 吞吐量极高、消息堆积能力强、适合流式处理 |

### 5.3 三种集成模式
| 集成模式 | 适用场景 | 技术实现 | 性能指标 |
|---------|---------|---------|---------|
| **实时同步集成** | 主数据同步、指令下发等需要实时响应的场景 | RESTful API + gRPC | 响应时间<200ms，可用性99.9% |
| **异步消息集成** | 生产数据采集、日志上报等高吞吐量场景 | RabbitMQ + Kafka | 吞吐量>10000TPS，消息不丢失 |
| **文件批量集成** | 批量数据导入导出、定期同步等场景 | SFTP + 文件解析 | 支持GB级文件处理，断点续传 |

### 6.4 统一开发规范
1. **代码规范**：严格遵循Microsoft C#编码规范和Vue官方风格指南
2. **命名规范**：统一采用帕斯卡命名、驼峰命名，禁止拼音和缩写（通用缩写除外）
3. **接口规范**：RESTful API设计规范，统一返回格式、错误码、分页参数
4. **数据规范**：统一数据库设计规范，必填字段、索引规范、软删除规范
5. **安全规范**：统一接口鉴权、参数校验、SQL注入防护、XSS防护
6. **文档规范**：所有接口必须有完整的Swagger注释，复杂业务必须有设计文档

### 7.1 Kubernetes部署架构
```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            全局负载均衡层                                    │
│                        SLB / Nginx / CDN                                    │
└───────────────────────────┬─────────────────────────────────────────┘
                                    ↓
┌─────────────────────────────────────────────────────────────────────────────┐
│                            Kubernetes集群层                                  │
├──────────────────┬──────────────────┬──────────────────┬───────────────────┤
│  控制节点        │  计算节点        │  存储节点        │  边缘节点           │
│  (3台高可用)     │  (弹性扩缩容)    │  (分布式存储)    │  (工厂就近接入)     │
└──────────────────┴──────────────────┴──────────────────┴───────────────────┘
                                    ↓
┌─────────────────────────────────────────────────────────────────────────────┐
│                            服务部署层                                       │
├──────────────────┬──────────────────┬──────────────────┬───────────────────┤
│  无状态服务      │  有状态服务      │  中间件服务      │  定时任务           │
│  (业务微服务)    │  (数据库)        │  (Redis/RabbitMQ)│  (Job/CronJob)      │
│  弹性扩缩容      │  持久化存储      │  高可用集群      │  分布式调度          │
└──────────────────┴──────────────────┴──────────────────┴───────────────────┘
```

### 7.2 多环境部署策略
1. **开发环境**：开发人员本地/测试服务器，快速迭代
2. **测试环境**：QA测试用，功能测试、集成测试
3. **预发布环境**：与生产环境一致，上线前最后验证
4. **生产环境**：正式对外提供服务，高可用部署

### 7.3 高可用设计
- **应用层**：所有微服务至少3副本部署，自动扩缩容
- **数据库层**：PostgreSQL一主两从，读写分离，自动故障切换
- **中间件层**：Redis集群、RabbitMQ集群、Kafka集群，无单点故障
- **基础设施层**：Kubernetes多可用区部署，避免单点故障

## 9. 非功能性需求

### 9.1 性能要求
- 接口响应时间：P95 < 200ms
- 支持并发用户数：>= 10000
- 系统可用性：>= 99.9%
- 消息队列吞吐量：RabbitMQ >= 2万TPS，Kafka >= 10万TPS

### 9.2 安全要求
- 密码采用BCrypt加密存储
- 接口传输采用HTTPS
- 支持SQL注入、XSS攻击防护
- 操作日志不可篡改，保存周期 >= 1年
- 租户数据严格隔离，禁止跨租户数据访问
- 符合等保三级要求

### 9.3 扩展性要求
- 支持水平扩展，可通过增加节点提升性能
- 模块化设计，功能可插拔
- 支持自定义扩展字段
- 支持租户级自定义配置

### 9.4 兼容性要求
- 支持Windows/Linux跨平台部署
- 前端支持Chrome、Firefox、Edge等主流浏览器
- 数据库兼容PostgreSQL 14+版本
- 支持主流工业标准协议和第三方系统集成
