# 采购退货增强需求

## 文档目的

本文档记录采购退货功能需要增强的具体点，配套「方案 1：采购订单创建即入库，不支持编辑/删除，录错走采购退货」的修复策略。

当采购订单按方案 1 完成修复后（前端补创建入口、后端禁用 Update/Delete），所有录入错误的修正都将依赖采购退货流程。当前采购退货在「修正录入错误」场景下存在体验摩擦和数据安全隐患，需对照本文档逐项优化。

## 背景与前提

### 方案 1 的核心决策

- 采购订单采用「创建即入库」模式，单据不可变（不支持编辑/删除）
- 录入错误的修正统一走采购退货冲减
- 路径 B（入库管理-采购入库）的「采购入库」来源选项移除，采购入库只走采购订单

### 采购退货当前能力

采购退货（`PurchaseReturnAppService`）已支持：

- 一次退回多种商品（`Items` 列表）
- 部分退货（`Quantity` 自由填写）
- 关联原采购订单（`PurchaseOrderId`，关联后冲减 `RefundedAmount`）
- 指定批次退货（`BatchNo`，不指定时 FIFO 扣减）
- 库存联动扣减（事务内调用 `DeductByBatchAsync`）

能力上可以支撑「修正录入错误」，但存在以下摩擦点与隐患。

## 当前问题清单

### 问题 1：批次号需用户手动查询填写

- **位置**：`PurchaseReturnItemCreateDto.BatchNo`（`Dtos/PurchaseReturns/PurchaseReturnItemCreateDto.cs:17`）
- **现象**：退货界面要求用户填写批次号，但用户不知道路径 A 自动生成的批次号是 `PO-{单号}-{行号}` 格式
- **风险**：不填 `BatchNo` 时走 FIFO 扣减（`PurchaseReturnAppService.cs:155-158`），可能扣到其他批次的库存，导致批次库存与实际不符
- **影响场景**：修正录入错误时，刚入库的批次库存最新，FIFO 大概率扣对，但不保证

### 问题 2：退款金额需用户手算

- **位置**：`PurchaseReturnItemCreateDto.RefundAmount`（`Dtos/PurchaseReturns/PurchaseReturnItemCreateDto.cs:15`）
- **现象**：退款金额必填，用户需自己计算 `退回数量 * 原采购单价`
- **风险**：算错会导致 `PurchaseOrder.RefundedAmount` 不准，报表对账失真（实际采购成本 = TotalAmount - RefundedAmount）
- **影响场景**：纯数量修正（非真实退货）时，用户可能不清楚该填多少退款金额

### 问题 3：退货单删除不回滚库存（严重隐患）

- **位置**：`PurchaseReturnAppService.DeleteAsync`（`Services/PurchaseReturnAppService.cs:273-286`）
- **现象**：直接物理删除退货单，不回滚已扣减的库存，不回退 `RefundedAmount`
- **代码注释已明确警示**（270-272 行）：
  > 业务约束：库存扣减与成本冲减不可逆，本方法不回滚已扣减库存与 RefundedAmount。
  > 生产环境建议改为"作废"状态保留审计轨迹，避免直接物理删除导致库存数据不一致。
- **风险**：用户录错退货单后删除，会导致库存被扣但不回滚，数据彻底错乱
- **影响场景**：这是定时炸弹，方案 1 后修正错误全靠退货，退货单本身录错的概率会上升

### 问题 4：退货单自身不可编辑

- **位置**：`PurchaseReturnAppService.UpdateAsync`（`Services/PurchaseReturnAppService.cs:203-266`）
- **现象**：`UpdateAsync` 只替换明细，不调整库存与 `RefundedAmount`（注释 200-201 行已说明）
- **风险**：退货单录错后无法直接改，只能作废重建
- **影响场景**：与问题 3 叠加，作废流程不通畅

### 问题 5：整单退回后采购单状态不变

- **位置**：`PurchaseReturnAppService.CreateAsync`（`Services/PurchaseReturnAppService.cs:170-180`）只更新 `RefundedAmount`，不改 `Status`
- **现象**：即使整单退回，采购单仍是 `3已入库`，不会变成 `4已取消` 或「已退货」
- **风险**：报表与列表展示可能造成困惑，用户难以判断哪些采购单已实际退清

## 增强需求

### 需求 1：退货界面从原采购单带出明细（前端）

**目标**：用户选择关联采购单后，自动带出该采购单的明细，降低手动填写负担与出错概率。

**具体要求**：

- 退货新增弹窗中，选择「关联采购订单」后，调用采购订单详情接口（`GET /api/store/PurchaseOrders/{id}`）
- 自动填充退货明细列表，每行包含：
  - 商品（`ProductId`、商品名称、商品编码）- 只读展示
  - 原采购数量 - 只读展示
  - 原批次号（`BatchNo`）- 自动带入，作为默认值
  - 原采购单价（`UnitPrice`）- 只读展示，用于计算退款金额
  - 本次退回数量 - 可编辑，默认 0，上限为原采购数量
  - 退款金额 - 自动计算 = `本次退回数量 * 原采购单价`，只读
- 支持用户手动调整批次号（如需退回其他批次）
- 支持删除不需要退货的明细行
- 保留「不关联采购单」的独立退货入口（历史数据或独立退货场景）

**关联文件**：

- 前端：`src/Admin/mes-admin/src/views/store/product/purchase-return/index.vue`
- 前端 API：`src/Admin/mes-admin/src/api/purchase/index.ts`（已有 `getPurchaseOrder`，需确认是否走真实接口而非 Mock）

### 需求 2：退款金额自动计算（前端）

**目标**：消除用户手算 `RefundAmount` 的负担。

**具体要求**：

- 退货明细的 `RefundAmount` 由前端自动计算：`退回数量 * 原采购单价`
- 当「退回数量」变化时，实时更新 `RefundAmount`
- 当「批次号」或「单价」被手动调整时，同步重算
- 未关联采购单的独立退货，仍允许用户手动填写 `RefundAmount`

**关联文件**：

- 前端：`src/Admin/mes-admin/src/views/store/product/purchase-return/index.vue`

### 需求 3：退货单删除改为作废（后端，严重）

**目标**：消除「删除不回滚库存」的定时炸弹。

**具体要求**：

- 禁用 `PurchaseReturnAppService.DeleteAsync` 与 `BatchDeleteAsync` 的物理删除逻辑
- 改为「作废」状态：
  - `PurchaseReturn` 实体新增 `IsVoid` / `Status` 字段（任选其一，建议 `Status`：1有效/2已作废）
  - 作废时需回滚库存：调用入库接口将扣减的库存加回（按原明细的 `BatchNo` 与 `Quantity`）
  - 作废时需回滚 `PurchaseOrder.RefundedAmount`：减去原退货单的 `TotalRefundAmount`
  - 作废操作需记录操作人与时间
- 作废后的退货单在列表中标记展示，不再参与库存与成本计算
- 前端退货列表新增「作废」按钮，移除「删除」按钮

**关联文件**：

- 后端实体：`src/Services/Store/Bms.Store.Domain/Entities/PurchaseReturn.cs`
- 后端服务：`src/Services/Store/Bms.Store.Application/Services/PurchaseReturnAppService.cs`
- 后端 DTO：`src/Services/Store/Bms.Store.Application/Dtos/PurchaseReturns/`
- 前端：`src/Admin/mes-admin/src/views/store/product/purchase-return/index.vue`
- 数据库迁移：需新增字段

### 需求 4：退货单 UpdateAsync 禁用或限制（后端）

**目标**：避免误用 `UpdateAsync` 导致库存与单据脱钩。

**具体要求**：

- 方案 A（推荐）：直接禁用 `UpdateAsync`，退货单创建后不可编辑，录错只能作废重建
- 方案 B：限制 `UpdateAsync` 只能改非库存相关字段（如 `Remark`、`VoucherImageUrl`），明细数量与商品不可改

**关联文件**：

- 后端服务：`src/Services/Store/Bms.Store.Application/Services/PurchaseReturnAppService.cs`
- 后端控制器：`src/Services/Store/Bms.Store.Api/Controllers/PurchaseReturnsController.cs`

### 需求 5：采购单退清状态展示（可选，优先级低）

**目标**：让用户直观看到采购单是否已退清。

**具体要求**：

- 采购订单列表与详情中，增加「退清状态」展示：
  - 当 `RefundedAmount >= TotalAmount` 时，标记为「已退清」
  - 当 `RefundedAmount > 0 且 < TotalAmount` 时，标记为「部分退货」
  - 当 `RefundedAmount == 0` 时，无标记
- 不建议改 `PurchaseOrder.Status` 字段值（避免影响现有状态机），建议在前端展示层计算
- 或在 DTO 中新增 `RefundStatus` 计算字段

**关联文件**：

- 后端 DTO：`src/Services/Store/Bms.Store.Application/Dtos/PurchaseOrders/PurchaseOrderDto.cs`
- 前端：`src/Admin/mes-admin/src/views/store/product/purchase-order/index.vue`

## 验收标准

### 前端验收

- [ ] 退货新增弹窗选择关联采购单后，自动带出明细（商品、原数量、批次号、单价）
- [ ] 退回数量变化时，退款金额自动重算
- [ ] 未关联采购单时，仍可手动填写明细
- [ ] 退货列表「作废」按钮可用，作废后单据标记展示
- [ ] 采购订单列表能展示退清状态（若实施需求 5）

### 后端验收

- [ ] 退货单物理删除接口已禁用或改为作废
- [ ] 作废操作回滚库存（`Inventory.Quantity` 增加、`InventoryBatch` 数量恢复）
- [ ] 作废操作回滚 `PurchaseOrder.RefundedAmount`
- [ ] 作废操作记录操作人与时间
- [ ] `UpdateAsync` 已禁用或限制为非库存字段
- [ ] 作废后的退货单不参与库存与成本计算

### 数据一致性验收

- [ ] 创建退货 -> 作废退货，库存与 `RefundedAmount` 回到创建前状态
- [ ] 创建退货 -> 作废 -> 重新创建退货，数据正确
- [ ] 整单退回后，采购单退清状态正确展示

## 实施顺序建议

1. **先做需求 3（作废机制）**：这是数据安全隐患，优先级最高
2. **再做需求 4（禁用 Update）**：与需求 3 配套，避免误用
3. **然后做需求 1、2（前端增强）**：在作废机制就绪后，前端可放心调用
4. **最后做需求 5（退清状态）**：可选优化，不影响数据安全
