# 用户管理权限提升修复方案

## 一、背景与问题

### 1.1 问题描述

用户管理页面中，员工可以修改自己的组织架构及角色，间接造成员工提升自己权限。经 review 发现这是后端的系统性权限校验缺失，而非单点漏洞。

### 1.2 漏洞根因

| 位置 | 问题 |
|---|---|
| `UsersController.cs` Update / AssignRoles / Create / Delete / BatchDelete / ResetPassword | 仅 `[Authorize]`，未加 `[Permission]` 特性，任何登录用户均可调 |
| `UserAppService.UpdateAsync` | 直接用 `dto.OrganizationId` / `dto.RoleIds` 落库，零业务规则 |
| `UsersController.Update` / `UserAppService.UpdateAsync` | 完全未调用 `IDataPermissionFilter`，组织变更无范围校验 |
| `DataPermissionFilter.cs` 第 99-104、159-163 行 | DataPermission 记录缺失时默认 `All`，违反"默认拒绝" |
| `DataPermissionFilter.cs` 第 50-53 行 | `HasDataPermissionAsync` 中 `targetUserId == userId` 直接放行，与"禁改自己"冲突 |
| `UsersController.ChangePassword` 第 201 行 | `userId = 1L` 硬编码，未从 Claims 获取 |

### 1.3 已验证的漏洞路径

- 普通员工 A 调用 `PUT /api/users/{A的id}`，body 中 `organizationId` 填上级组织 ID -> 直接落库成功
- 普通员工 A 调用 `PUT /api/users/{A的id}`，body 中 `roleIds` 填 tenant_admin 角色 ID -> 直接落库成功
- 任意登录用户调 `POST /api/users/{id}/assign-roles` 给任何人分配任何角色 -> 成功

## 二、架构理解

### 2.1 租户与角色分布

```
平台租户 (TenantId=1)
├── 角色：super_admin (Level=0)、tenant_admin (Level=1)
├── 用户：super_admin 用户、tenant_admin 用户
└── 平台租户的角色/用户不做界面变更（SeedData 初始化）

普通租户 (TenantId=2,3,...)
├── 角色：由 tenant_admin 创建，Level > 1，Code 不能是 super_admin/tenant_admin
├── 组织：由 tenant_admin 创建
└── 用户：由 tenant_admin 创建，只能分配本租户角色
```

### 2.2 关键约定

- **tenant_admin 角色属于平台租户**，不会出现在普通租户角色列表中。
- **平台租户的角色不做界面变更**，super_admin 和 tenant_admin 角色由 SeedData 初始化。
- **tenant_admin 用户的 `TenantId` = 他管理的普通租户 ID**（不是平台租户 ID）。tenant_admin 登录后，租户上下文即为他管理的普通租户。
- **后端判定用户身份**靠角色 Code，不靠角色 TenantId：
  ```csharp
  var isSuperAdmin = roles.Any(r => r.Code == "super_admin");
  var isTenantAdmin = roles.Any(r => r.Code == "tenant_admin");
  ```

## 三、设计方案

### 3.1 三级权限模型

| 级别 | 判定依据 | 能做什么 | 限制 |
|---|---|---|---|
| super_admin | 角色 Code = `super_admin` | 系统内任何事 | 无 |
| tenant_admin | 角色 Code = `tenant_admin` | 管理自己 `TenantId` 对应的普通租户内的任何角色/组织/用户 | 不能动平台租户、不能动其他普通租户、不能创建/编辑/分配 super_admin 或 tenant_admin 角色 |
| 普通用户 | 其他角色 | 受 Level + 数据权限双重约束 | 不能改同级或上级、不能改组织树外、不能管理角色 |

**关键**：tenant_admin 的判定靠角色 Code，不靠 Level。Level 只在"普通用户之间"起作用，不约束 tenant_admin。

### 3.2 数据模型变更

#### 3.2.1 Role 表加 `Level` 字段

```csharp
public class Role
{
    // ... 现有字段
    /// <summary>
    /// 角色等级，数字越小权限越大
    /// super_admin=0, tenant_admin=1, 普通角色>1
    /// </summary>
    public int Level { get; set; }
}
```

初始值约定：

| 角色 | Level | TenantId |
|---|---|---|
| super_admin | 0 | 1（平台租户） |
| tenant_admin | 1 | 1（平台租户） |
| 租户内角色 | > 1（tenant_admin 创建时设置） | 创建者所在租户 ID |

#### 3.2.2 DataPermission 配置

| 角色 | DataScopeType | 说明 |
|---|---|---|
| super_admin | `All` | 系统全部 |
| tenant_admin | `All` | 本租户全部（靠租户隔离实现） |
| 普通角色 | `DepartmentAndBelow` / `Custom` / `Self` | 按业务配置 |

#### 3.2.3 DataPermissionFilter 修正

1. **`All` 类型填充组织列表**（解决写入校验失效）：
   ```csharp
   case DataScopeType.All:
       hasAll = true;
       if (user.TenantId > 0)
       {
           var tenantOrgs = await _organizationRepository.GetByTenantIdAsync(user.TenantId);
           allOrgIds.AddRange(tenantOrgs.Select(o => o.Id));
       }
       break;
   ```
   super_admin 也填充（本租户=平台租户的组织），跨租户操作靠 super_admin 的特殊放行逻辑。

2. **修复"记录缺失默认 All"**（第 99-104 行）：
   ```csharp
   if (dataPermission == null)
   {
       // 角色没有 DataPermission 记录，视为 Self（默认拒绝）
       hasSelf = true;
       continue;
   }
   ```

3. **修复"全部缺失默认 All"**（第 159-163 行）：
   ```csharp
   else
   {
       // 默认视为 Self
       result.ScopeType = DataScopeType.Self;
   }
   ```

4. **修复 Self 覆盖 All 语义**（第 88-92 行注释逻辑）：
   改为"取最宽权限"：`All > DepartmentAndBelow/Custom > Self`。多角色场景下取最高权限。

5. **新增 `allowSelf` 参数**给 `HasDataPermissionAsync`，Update 校验时传 `false`，避免"自己永远有权限"绕过禁改自己：
   ```csharp
   Task<bool> HasDataPermissionAsync(long userId, long? targetUserId = null, long? targetOrganizationId = null, bool allowSelf = true);
   ```

### 3.3 统一校验逻辑：IUserPermissionChecker

新增服务封装权限校验，避免 6 个接口重复实现。

```csharp
public interface IUserPermissionChecker
{
    /// <summary>获取当前用户权限上下文</summary>
    Task<CurrentUserPermissionContext> GetContextAsync(long currentUserId);

    /// <summary>校验能否分配指定角色（规则 3 + 5 + 受保护角色）</summary>
    Task CheckCanAssignRolesAsync(CurrentUserPermissionContext ctx, List<long> targetRoleIds);

    /// <summary>校验能否操作目标用户（规则 2 + 4 + 组织范围）</summary>
    Task CheckCanOperateUserAsync(CurrentUserPermissionContext ctx, long targetUserId, bool allowSelf = false);

    /// <summary>校验能否把用户移动到指定组织（规则 7）</summary>
    Task CheckCanMoveToOrganizationAsync(CurrentUserPermissionContext ctx, long? targetOrganizationId);

    /// <summary>校验能否修改目标用户租户归属（规则 6）</summary>
    Task CheckCanChangeTenantAsync(CurrentUserPermissionContext ctx);
}

public class CurrentUserPermissionContext
{
    public long UserId { get; set; }
    public bool IsSuperAdmin { get; set; }
    public bool IsTenantAdmin { get; set; }
    public long TenantId { get; set; }
    public int MaxRoleLevel { get; set; }           // 当前用户最高角色等级（数字最小）
    public DataPermissionScope DataScope { get; set; } = null!;
}
```

### 3.4 校验规则总览

```
所有写接口统一校验流程：

1. 角色分配校验（Create/Update/AssignRoles 涉及 RoleIds 时）：
   if ctx.IsSuperAdmin: 放行
   if ctx.IsTenantAdmin:
     - 待分配角色 Code == "super_admin" 或 "tenant_admin": 拒绝
     - 待分配角色 TenantId != ctx.TenantId: 拒绝
     - 其他: 放行
   else (普通用户):
     - 待分配角色 TenantId != ctx.TenantId: 拒绝
     - 待分配角色 Code in ("super_admin", "tenant_admin"): 拒绝
     - 待分配角色 Level <= ctx.MaxRoleLevel: 拒绝（只能分配严格低于自己的）

2. 目标用户校验（Update/Delete/ResetPassword/AssignRoles）：
   if ctx.IsSuperAdmin: 放行
   if ctx.IsTenantAdmin:
     - 目标用户 TenantId != ctx.TenantId: 拒绝
     - 目标用户拥有 super_admin 角色: 拒绝
     - 其他: 放行
   else (普通用户):
     - 目标用户 TenantId != ctx.TenantId: 拒绝
     - 目标用户拥有 super_admin/tenant_admin 角色: 拒绝
     - 目标用户 MaxRoleLevel <= ctx.MaxRoleLevel: 拒绝
     - 目标用户当前组织不在 ctx.DataScope.OrganizationIds 内: 拒绝
   if targetUserId == ctx.UserId && !allowSelf: 拒绝

3. 组织变更校验（Create/Update 涉及 OrganizationId 时）：
   if ctx.IsSuperAdmin: 放行
   if ctx.IsTenantAdmin:
     - 目标组织 TenantId != ctx.TenantId: 拒绝
     - 其他: 放行
   else (普通用户):
     - 目标组织不在 ctx.DataScope.OrganizationIds 内: 拒绝

4. 租户字段变更校验（Update 涉及 TenantId/CreatorTenantId 时）：
   if !ctx.IsSuperAdmin: 拒绝
```

### 3.5 各接口校验矩阵

| 接口 | 权限码 | 角色分配校验 | 目标用户校验 | 组织校验 | 禁自己 | 租户字段校验 |
|---|---|---|---|---|---|---|
| Create | `system:user:add` | ✓ | - | ✓ | - | 强制当前租户 |
| Update | `system:user:edit` | ✓ | ✓ | ✓ | ✓ | 只 super_admin 改 |
| AssignRoles | `system:user:edit` | ✓ | ✓ | - | ✓ | - |
| Delete | `system:user:delete` | - | ✓ | - | ✓ | - |
| BatchDelete | `system:user:delete` | - | ✓（遍历） | - | ✓ | - |
| ResetPassword | `system:user:resetPwd` | - | ✓ | - | ✓ | - |

### 4.5 关联接口 review 结果

实施前已 review 3 个关联控制器，发现 `OrganizationsController` 和 `RolesController` 存在与 `UsersController` 同类的权限校验缺失，`TenantsController` 已正确校验。

#### 4.5.1 OrganizationsController（高危，需修复）

**文件**：`src/Services/System/Bms.System.Api/Controllers/OrganizationsController.cs`

**当前状态**：
- 类级别仅 `[Authorize]`，无 `[Permission]` 特性
- `GetTree` / `GetList` 做了租户隔离（第 30-44、57-71 行）
- `Create` / `Update` / `Delete`（第 100-147 行）完全无权限校验，未调用 `IDataPermissionFilter`

**漏洞场景**：
- 普通员工调 `POST /api/organizations` 创建 `TenantId=其他租户` 的组织 -> 成功
- 普通员工调 `PUT /api/organizations/{id}` 把某组织 `ParentId` 改到自己组织下 -> 偷组织
- 普通员工调 `DELETE /api/organizations/{id}` 删除任意组织 -> 破坏
- 普通员工调 `PUT /api/organizations/{id}` 修改上级组织的 `TenantId` -> 跨租户移动

**修复方向**：
- 写接口加 `[Permission("system:org:edit")]` / `[Permission("system:org:delete")]` 等特性
- Service 层校验：
  - `super_admin`：放行
  - `tenant_admin`：只能操作 `dto.TenantId == ctx.TenantId` 的组织；`ParentId` 必须在同租户内
  - 普通用户：拒绝（组织管理只给 admin）
- `Create`：非 super_admin 时强制 `dto.TenantId = ctx.TenantId`
- `Update`：校验目标组织和新 `ParentId` 都在同租户内
- `Delete`：校验目标组织在同租户内
- tenant_admin 创建租户内第一个组织时：`dto.TenantId` 自动设为当前用户 TenantId，放行（鸡生蛋问题解决）

#### 4.5.2 RolesController（严重，需优先修复）

**文件**：`src/Services/System/Bms.System.Api/Controllers/RolesController.cs`

**当前状态**：
- 类级别仅 `[Authorize]`，无 `[Permission]` 特性
- `GetList` / `GetAll` 做了租户隔离（第 32-54 行）
- `GetAllWithoutFilter`（第 59-63 行）完全不过滤租户，任何登录用户可调
- `Create` / `Update` / `Delete` / `BatchDelete` / `AssignPermissions` / `UpdateMenuAuths` / `RemoveMenuAuth`（第 77-222 行）全部无权限校验
- `Create` 时直接用 `currentTenantId`（第 85 行），但**未校验 `dto.Code` 是否为 `super_admin` / `tenant_admin`**

**漏洞场景（严重，可完全提权）**：
- 普通员工调 `POST /api/roles` 创建 `Code=super_admin` 的角色 -> 成功
- 普通员工再调 `POST /api/users/{自己的id}/assign-roles` 把这个角色分配给自己 -> 完全提权
- 普通员工调 `PUT /api/roles/{id}` 把任意角色 `Code` 改成 `super_admin` -> 成功
- 普通员工调 `POST /api/roles/{id}/permissions` 给任意角色分配任意权限 -> 成功
- 普通员工调 `PUT /api/roles/{id}/menus/auth` 给任意角色分配任意菜单 -> 成功
- 普通员工调 `DELETE /api/roles/{id}` 删除 `super_admin` 角色 -> 破坏系统

**修复方向**：
- 所有写接口加 `[Permission("system:role:edit")]` / `[Permission("system:role:delete")]` 等特性
- `Create` / `Update`：
  - `dto.Code` 不能是 `super_admin` 或 `tenant_admin`（除非 super_admin）
  - `super_admin`：放行
  - `tenant_admin`：`dto.Level > 1`，只能操作 `dto.TenantId == ctx.TenantId` 的角色
  - 普通用户：拒绝
- `Delete` / `BatchDelete`：
  - 目标角色 `Code` 是 `super_admin` / `tenant_admin` -> 拒绝（除非 super_admin）
  - `tenant_admin` 只能删自己租户的角色
- `AssignPermissions` / `UpdateMenuAuths` / `RemoveMenuAuth`：同 `Delete` 校验
- `GetAllWithoutFilter`：评估必要性，建议改为仅 super_admin 可调，或加 `[Permission("system:role:view")]`

#### 4.5.3 TenantsController（安全，无需修复）

**文件**：`src/Services/System/Bms.System.Api/Controllers/TenantsController.cs`

**当前状态**：
- 类级别 `[Authorize]`
- 每个接口都用 `IsSuperAdmin()` 做了校验（第 37、50、63、76、96、117、137、157、177、197、210、230、250、270、290 行）
- 非 super_admin 调用返回 403

**结论**：安全，无需修复。

**可优化点**（非安全问题）：
- `IsSuperAdmin()` 在每个方法重复调用，可提取为 Action Filter 或用 `[Authorize(Roles="super_admin")]` 替代
- 可作为 `OrganizationsController` / `RolesController` 修复的参考模板

#### 4.5.4 Review 总结

| 控制器 | 严重程度 | 主要问题 | 是否需修复 | 优先级 |
|---|---|---|---|---|
| RolesController | 严重 | 写接口零校验，可创建 super_admin 角色直接完全提权 | 是 | P0（与 UserController 同步修复） |
| OrganizationsController | 高 | 写接口零校验，普通员工可任意创建/编辑/删除组织 | 是 | P1 |
| TenantsController | 无 | 已用 IsSuperAdmin() 校验 | 否 | - |

**关键结论**：`RolesController` 的漏洞比 `UsersController` 更严重--`UsersController` 只是能让员工提权自己，`RolesController` 能让普通员工创建 `super_admin` 角色并分配给自己，直接获得系统最高权限。两者必须同步修复，否则修复 `UsersController` 后仍可通过 `RolesController` 绕过。

## 六、测试要点

### 6.1 单元测试（`IUserPermissionChecker`）

- `CheckCanAssignRolesAsync`：覆盖三级用户 × 各类目标角色组合
- `CheckCanOperateUserAsync`：覆盖三级用户 × 各类目标用户 × allowSelf 组合

### 6.2 集成测试（接口层）
