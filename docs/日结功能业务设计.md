## 一、日结业务目标与原则约束

### 1.1 核心业务目标

日结是门店每日经营闭环的最后一环。店主下班前通过确认日结，锁定当日营业数据，实现以下目标：

| 目标 | 说明 |
|------|------|
| 经营快照 | 为店主提供当日营收/退款/储值/订单数的汇总视图，不用手动算账 |
| 防漏校验 | 日结时校验是否有遗漏订单，防止漏记（原则8推论："日结时校验，防止漏单"） |
| 数据基线 | 确认后的日结数据作为当日经营基线，支撑月度汇总和趋势分析 |
| 经营节奏 | 帮助店主建立"每日确认"的经营节奏，形成闭环习惯 |

### 1.2 原则8（补漏容忍）对日结的约束

原则8原文："允许店主漏记后补录，但不允许遗漏"。对日结功能的具体约束：

| 约束编号 | 约束内容 | 来源 |
|---------|---------|------|
| C-01 | 允许补录历史日期订单 | 原则8推论 + G3.1 |
| C-02 | 通过站内信推送"今日待补录"提醒（不强制，站内信功能待补充；后端查询接口已就绪） | 原则8推论 + G3.1 |
| C-03 | 日结时校验，防止漏单 | 原则8推论 |
| C-04 | 不允许遗漏：日结确认时必须有前序日结记录或为首日 | 本设计推导 |

### 1.3 其他相关原则

| 原则 | 对日结的影响 |
|------|------------|
| 原则1（记账不交易） | 日结仅汇总已发生业务数据，不产生任何交易动作 |
| 原则2（极简优先） | 日结操作一键确认，数据自动汇总，店主无需手动录入 |
| 原则3（经营者视角） | 日结报表直观，不做会计级 |
| 原则4（门店数据隔离） | 日结按门店隔离，每日结记录归属具体门店 |

## 二、日结完整生命周期

### 2.1 状态定义

日结记录只有2个状态：

| 状态值 | 状态名称 | 含义 | 数据可变性 |
|--------|---------|------|-----------|
| 0 | 待确认 | 系统已自动汇总当日营业数据（含0数据），等待店主确认 | 可变（订单变动时重算） |
| 1 | 已确认 | 店主已确认日结数据，数据锁定 | 不可变（需反日结才能修改） |

### 2.2 状态流转图

```
                     每日凌晨定时任务（含无订单日，生成0数据记录）
    [无记录] ─────────────────────────────────────────> [待确认]
                                                          │    ^
                                                    店主确认│    │反日结/订单变动重算
                                                          v    │
                                                     [已确认]
```

### 2.3 各状态详细说明

#### 状态0：待确认

| 项目 | 说明 |
|------|------|
| 含义 | 系统已根据当日订单/储值等数据自动生成汇总（当日无订单则生成全0记录），等待店主审视确认 |
| 触发条件 | 每日凌晨定时任务自动触发；或店主手动触发汇总 |
| 可执行操作 | 店主确认日结（转为状态1）；店主查看汇总数据；订单变动时自动重算 |
| 数据状态 | 可变。若当日有新订单/退款/补录等变动，日结汇总数据自动重算 |
| 特殊说明 | 日结列表中缺失某日期的记录 = 汇总遗漏（异常）；有记录但数据为0 = 当日无订单（正常） |

#### 状态1：已确认

| 项目 | 说明 |
|------|------|
| 含义 | 店主已确认日结数据，数据锁定，作为当日经营基线 |
| 触发条件 | 店主在日结页面点击"确认日结"按钮 |
| 可执行操作 | 查看日结数据（只读）；反日结（状态改回0，系统重新汇总） |
| 数据状态 | 不可变。锁定后任何订单变动不直接影响日结数据，需反日结后重算 |
| 特殊说明 | 反日结针对具体日期，不要求连续。如只有3天前数据有误，只需反日结3天前那天，不影响中间日期 |

## 三、触发机制设计

### 3.1 设计决策总览

| 机制 | 触发方 | 时机 | 动作 |
|------|--------|------|------|
| 自动汇总 | 系统（定时任务） | 每日凌晨 | **兜底机制**，对前一天未汇总的日期自动生成日结记录 |
| 手动汇总 | 店主 | 任意时间 | **主要入口**，可对任意日期（含当天）手动触发汇总 |
| 手动确认 | 店主 | 下班前 | 确认日结数据，锁定为"已确认"状态 |
| 自动重算 | 系统 | 订单变动时 | "待确认"状态下，订单变动触发自动重算 |

### 3.2 自动汇总：凌晨兜底机制

**定位**：兜底机制，确保即使店主忘记手动汇总，系统也会自动生成日结记录。

**触发时间**：每日凌晨 02:00（建议值，可配置）

**汇总范围**：前一天（T-1）的营业数据

**理由**：
- 凌晨2点避开门店营业时间和跨日订单的时间窗口
- 选择T-1而非当天，因为当天数据尚未完整
- 需求文档（G4.2）明确要求"每日自动汇总"，第184行提到"每日凌晨/日结时生成当日统计数据"
- 作为兜底，仅处理前一天尚无日结记录的日期；若店主已手动汇总，不重复生成

**生成内容**：
- 营收总额（TotalRevenue）
- 退款总额（TotalRefund）
- 储值充值总额（TotalStoredValueRecharge）
- 储值消费总额（TotalStoredValueConsume）
- 订单数（OrderCount）
- 毛利（GrossProfit，建议新增字段，修复 MED-012）
- 成本（Cost，建议新增字段，修复 MED-012）

**无订单日处理**：当日无订单时仍生成全0日结记录（OrderCount=0、TotalRevenue=0 等）。这样日结列表中缺失记录 = 汇总遗漏（异常），有记录但数据为0 = 当日无订单（正常），店主可从日期连续性一眼看出是否汇总遗漏。

**生成状态**：待确认，Status=0

### 3.3 手动确认：店主下班前确认

**交互方式**：
- 日结列表页面展示所有日结记录
- "待确认"状态的日结高亮提示
- 店主点击"确认日结"按钮，系统弹出汇总数据确认弹窗
- 店主核对数据后点击"确认锁定"

**确认前校验**（见第七节防漏单校验）：
- 校验是否有前序日结遗漏
- 校验当日是否有异常数据（如0订单但有储值消费等）
- 校验结果为阻止级别时，禁止确认

**确认后**：
- 状态变为"已确认"，Status=1
- 记录确认人（ConfirmedBy）和确认时间（ConfirmedTime）
- 日结数据锁定

### 3.4 超时处理：保持待确认状态

**设计决策**：日结超时（如超过24小时未确认）**不自动确认**，保持"待确认"状态。

**理由**：
1. G4.2原文："店主下班前确认即可" -- "确认"是店主的经营行为，系统不应代替
2. 原则2（极简优先）要求减少店主负担，但日结确认本身是极简操作（一键），不应跳过
3. 日结确认的核心价值在于"店主审视数据"这一行为，自动确认使该价值丧失
4. 若自动确认，后续发现错误时需要频繁反日结，反而增加操作

**超时提醒**：
- 首页看板增加"日结待确认"提醒：显示待确认日结的日期列表
- 超过3天未确认的日结标记为"逾期"，提醒颜色升级
- 逾期提醒是轻提醒，不阻止其他操作

### 3.5 手动汇总：主要入口

**定位**：主要入口，店主可随时查看任意日期（含当天）的日结数据，无需等到第二天凌晨。

**场景**：
- 当天营业中想实时查看当日汇总（如下午想看当天营收情况）
- 补汇总遗漏的历史日期（日结列表中缺失的日期）
- 凌晨兜底未执行时手动补汇总

**操作**：日结页面点击"立即汇总"按钮，选择目标日期手动触发汇总

**限制**：
- 仅对无日结记录的日期可触发首次汇总
- 已有"待确认"记录的日期通过"重算"更新数据
- 已"确认"的日期需先反日结才能重新汇总

**与自动汇总的关系**：手动汇总生成记录后，凌晨兜底自动汇总对该日期不再重复处理

## 四、数据汇总规则

### 4.1 数据源

日结数据从以下数据源汇总：

| 数据源 | 实体 | 汇总维度 | 提供字段 |
|--------|------|---------|---------|
| 订单 | Order | OrderTime 的日期部分 = 日结日期 | 营收、退款、订单数 |
| 储值流水 | StoredValueLog | 流水时间的日期部分 = 日结日期 | 储值充值、储值消费 |
| 消费记录 | ConsumeLog | ConsumeTime 的日期部分 = 日结日期 | 消费客户数（去重） |
| 客户档案 | Customer | CreatedTime 的日期部分 = 日结日期 | 新客数 |

### 4.2 字段计算口径

#### TotalRevenue（总营收）

**口径**：按权责发生制计算当日营收，退款按"原下单日归属"冲减（方案 A）

```
TotalRevenue = CashRevenue + StoredValueRevenue + TreatmentCardVerifyAmount - CashRefundAmount
```

**数据来源**：Order 表中 OrderTime 日期 = 日结日期，且 Status IN (2, 3) 的订单（含已退款订单的 PaidAmount，与退款金额同日抵消）

| 订单类型 | OrderType | 计入营收 | 金额来源 |
|---------|-----------|---------|---------|
| 零售 | 1 | 是 | PaidAmount |
| 服务 | 2 | 是 | PaidAmount |
| 项目卡核销 | 3 | 是 | PaidAmount（核销折算金额，PaidAmount=0，实际取项目卡核销记录的 VerifyAmount） |

**按支付方式拆分（组合支付改造后新增）：**

| 营收字段 | 计算口径 |
|---------|---------|
| CashRevenue | PayMethod=1-4 的 PaidAmount + PayMethod=7 的 CashAmount |
| StoredValueRevenue | PayMethod=5 的 PaidAmount + PayMethod=7 的 StoredValueAmount |
| PointsDeductAmount（仅记录，不纳入营收） | PayMethod=6 的 PaidAmount + PayMethod=7 的 PointsAmount |
| TreatmentCardVerifyAmount | 当日项目卡核销记录的 VerifyAmount 之和 |
| CashRefundAmount（冲减营收） | 见下方 TotalRefund 口径，仅现金类退款部分 |

**退款归属规则（方案 A，2026-07-19 修订）：**
- 营收与退款均按 **OrderTime（下单日）** 归属，确保同日抵消
- 当日下单当日退款的订单：PaidAmount 计入 CashRevenue，RefundAmount 计入 CashRefundAmount，Revenue 净额为 0
- 跨日退款的订单：退款金额不计入"退款发生日"，而是按 OrderTime 归属到原下单日；原下单日已确认的日结需通过反日结重算（见 5.6 节）

**说明**：
- 项目卡核销订单（OrderType=3）的 PaidAmount=0，营收金额取核销记录的折算金额
- 储值充值**不计入营收**（计入负债，在 TotalStoredValueRecharge 单独统计）
- 项目卡购买**不计入营收**（计入负债）
- 积分抵扣金额**不计入营收**（仅记录在 PointsDeductAmount，避免与现金/储值重复计算）

#### TotalRefund（总退款）

**口径**：按"原下单日归属"统计退款总额（方案 A，2026-07-19 修订）

```
TotalRefund = CashRefundAmount + StoredValueRefundAmount + PointsRefundAmount
其中各分项 = SUM(Order.RefundAmount 按 PayMethod 拆分)
       WHERE OrderTime 日期 = 日结日期 AND RefundAmount > 0
```

**数据来源**：Order 表中 OrderTime 日期 = 日结日期，且 RefundAmount > 0 的订单（含部分退款 Status=2 与全额退款 Status=3）

**按 PayMethod 拆分（用于决定是否冲减营收）：**

| 退款分项 | 计算口径 | 是否冲减营收 |
|---------|---------|-------------|
| CashRefundAmount | PayMethod=1-4 全额 + PayMethod=7 按 CashAmount 比例分摊 | 是（计入 TotalRevenue 减项） |
| StoredValueRefundAmount | PayMethod=5 全额 + PayMethod=7 按 StoredValueAmount 比例分摊 | 否（储值消费本身计入营收，退款冲减会重复） |
| PointsRefundAmount | PayMethod=6 全额 + PayMethod=7 按 PointsAmount 比例分摊 | 否（积分抵扣不计入营收） |

**说明**：
- 退款按 **OrderTime（下单日）** 归属，而非 RefundTime（退款发生日）。理由：退款是订单的逆向操作，应与订单同日抵消，避免"当日下单当日退款"时出现 Revenue 为负的异常
- 部分退款（Status=2 但 RefundAmount > 0）也计入退款统计，确保 Revenue 正确反映净收入
- 全额退款（Status=3）的订单 PaidAmount 仍计入 CashRevenue，与 RefundAmount 同日抵消

#### TotalStoredValueRecharge（储值充值总额）

**口径**：当日储值充值总额（含实收+赠送）

```
TotalStoredValueRecharge = SUM(StoredValueLog.Amount) WHERE Type = 1（充值） AND 流水时间日期 = 日结日期
```

**数据来源**：StoredValueLog 表中 Type=1，流水时间日期 = 日结日期

**说明**：储值充值是负债增加，不计入营收，在此字段单独统计。

#### TotalStoredValueConsume（储值消费总额）

**口径**：当日储值消费总额（含实收+赠送）

```
TotalStoredValueConsume = SUM(StoredValueLog.Amount的绝对值) WHERE Type = 2（消费） AND 流水时间日期 = 日结日期
```

**数据来源**：StoredValueLog 表中 Type=2，流水时间日期 = 日结日期

**说明**：储值消费金额已包含在 TotalRevenue 中（单一支付通过订单 PaidAmount 体现，组合支付通过 StoredValueAmount 体现，汇总到 StoredValueRevenue 字段），此字段用于独立展示储值消费情况。

#### OrderCount（订单数）

**口径**：当日已完成的有效订单数

```
OrderCount = COUNT(Order) WHERE OrderTime 日期 = 日结日期 AND Status IN (2, 3)
```

**说明**：包含已完成（2）和已退款（3）的订单，不含进行中（1）和已取消（4）。已退款的订单仍计入订单数（退款是独立业务事件），但退款金额在 TotalRefund 中体现。

#### GrossProfit（毛利）-- 建议新增

```
GrossProfit = TotalRevenue - Cost
```

#### Cost（成本）-- 建议新增

**口径**：当日销售商品/服务的成本

```
Cost = 零售商品成本(FIFO) + 服务项目耗材成本(BOM归集)
```

**说明**：成本计算口径与 G4.1 首页看板一致。项目卡核销不额外计算成本（购买时已入库的商品成本在核销时归集）。

### 4.3 补录订单的日结归属规则

**核心原则**：补录订单按**订单日期（OrderTime）**计入日结，而非补录日期。

**场景说明**：
- 7月13日的订单在7月15日补录（BackfillStatus=1，OrderTime=7月13日）
- 该订单计入7月13日的日结，不计入7月15日的日结

**理由**：
1. 日结是按日汇总经营数据，订单归属于其业务发生日
2. 补录订单的 OrderTime 记录的是实际业务发生日期
3. 若按补录日计入，会导致补录日的日结数据虚高，原始日数据失真

**对已确认日结的影响**：
- 若7月13日的日结已确认（锁定），7月15日补录7月13日的订单
- 系统检测到已确认日结受影响，发出提醒
- 店主需对7月13日执行反日结 -> 重新汇总 -> 重新确认
- 详见第五节数据修正规则

### 4.4 跨日订单的时间归属

**规则**：以 OrderTime（下单时间）的日期部分为日结归属日。退款同样按 OrderTime 归属到原下单日（方案 A，2026-07-19 修订）。

**边界场景**：

| 场景 | 处理方式 |
|------|---------|
| 23:59 下单，00:01 完成 | 计入下单日（OrderTime 日期） |
| 跨日服务（如过夜SPA） | 计入下单日 |
| 退款发生在次日 | 退款金额计入**原下单日**（OrderTime 日期），与订单 PaidAmount 同日抵消；若原下单日已确认，需触发自动反日结重算（见 5.6 节） |
| 当日下单当日退款 | PaidAmount 与 RefundAmount 同日抵消，Revenue 净额为 0 |

**退款归属设计理由（方案 A）**：
- 退款是订单的逆向操作，应与订单同日抵消
- 若按 RefundTime 归属，"当日下单当日退款"会出现 Revenue 为负的异常（退款无源之扣）
- 跨日退款通过自动反日结机制（5.6 节）确保原下单日营收数据准确

## 五、数据修正规则

### 5.1 核心原则：改订单而非改日结数据

**原则**：日结数据是订单等业务数据的汇总结果。发现日结数据有误时，应修正源头数据（订单、储值流水等），然后重新汇总日结，而非直接修改日结汇总数据。

**理由**：
1. 日结是派生数据，直接修改日结会导致与订单数据不一致
2. 修正源头数据可以保持数据链路完整可追溯
3. 与原则1（记账不交易）一致：系统记录已发生的业务，日结是对业务数据的汇总

### 5.2 已汇总（待确认）状态下的修正

**场景**：日结已汇总但尚未确认，发现数据有误（如漏了订单、订单金额错误等）

**处理流程**：
1. 店主直接修改/新增订单（源头数据）
2. 系统检测到日结日期范围内有订单变动
3. 系统自动重新汇总该日日结数据
4. 日结状态保持"已汇总(待确认)"
5. 店主核对后确认

**自动重算触发条件**：
- 新增订单（含补录订单）
- 订单状态变更（如退款）
- 订单金额修改
- 储值流水变动

**说明**：待确认状态下不需要反日结，直接重算即可。这是"待确认"状态存在的核心价值 -- 给店主一个审视窗口。

### 5.3 已确认（已锁定）状态下的修正

**场景**：日结已确认锁定，之后发现错误（如补录了遗漏的历史订单）

**处理流程（反日结机制）**：

```
1. 店主在日结列表找到需修正的日期
2. 点击"反日结"按钮
3. 系统校验反日结前置条件（见5.4）
4. 校验通过 -> 日结状态变为"已撤销"
5. 系统自动重新汇总该日数据
6. 日结状态变为"已汇总(待确认)"
7. 店主核对数据 -> 确认日结 -> 状态变为"已确认(已锁定)"
```

**反日结的影响**：
- 仅影响被反日结的那一天的数据
- 不影响其他日期的日结
- 不影响 DailyStat（日统计） -- DailyStat 在日结确认时同步，反日结时也同步更新

**自动反日结触发场景（2026-07-19 新增）：**

除店主手动反日结外，以下场景系统自动触发反日结，无需店主主动操作：

| 触发入口 | 方法 | 触发条件 | reason 文案 |
|---------|------|---------|------------|
| 订单退款 | `OrderAppService.RefundAsync` | `order.OrderTime.Date < DateTime.Today` 且订单非项目卡核销类型 | `跨日退款自动反日结：订单 X 退款 Y 元` |
| 取消订单 | `OrderAppService.CancelAsync` | `order.OrderTime.Date < DateTime.Today` | `跨日取消订单自动反日结：订单 X（实付 Y 元）` |
| 补录订单 | `OrderAppService.CreateAsync` | `BackfillStatus == 1 && OrderTime.Date < DateTime.Today` | `补录订单自动反日结：订单 X（实付 Y 元）` |

**DailySettlement 三种处理路径**：

| 原下单日 DailySettlement 状态 | 处理动作 |
|------------------------------|---------|
| 不存在（兜底任务遗漏，视为 bug） | 创建待确认记录（Status=0, Source=1），填充汇总数据，Remark=reason |
| Status=0 待确认 | 仅重新汇总字段（数据已是最新） |
| Status=1 已确认 | 反日结 -> Status=0，记录 ReversedReason，重新汇总字段 |

**设计要点**：
- 自动反日结在退款/取消订单事务内执行，失败整体回滚，保证数据一致性
- 原下单日无 DailySettlement 记录时主动补建待确认记录，因兜底任务（凌晨 02:00 自动汇总过去 30 天）本应覆盖，未覆盖视为 bug
- DailyStat 不立即同步，等店主重新确认时由 `ConfirmAsync -> EnsureDailyStatAsync` 自然同步
- 幂等性：同日多次退款仅首次从 Status=1 -> 0 时记录 ReversedReason，后续只更新字段
- 不受 5.4 节反日结前置条件 P-02（后续日结连续性）约束，因订单回滚是业务事实，原下单日数据已不准确，必须立即修正
- 提示机制：`RefundResultDto.ReversedSettlementDates` 携带反日结日期列表，前端据此展示"请前往日结管理重新确认"提示；取消订单通过返回消息文本提示

### 5.4 反日结前置条件

| 条件编号 | 条件 | 阻止/提醒 | 理由 |
|---------|------|----------|------|
| P-01 | 该日日结状态必须为"已确认(已锁定)" | 阻止 | 只有已确认的日结才能反日结 |
| P-02 | 该日之后的所有日结必须也是"已确认"状态或无记录 | 阻止 | 防止时间线混乱（不允许跳过中间日期反日结） |
| P-03 | 系统记录反日结操作日志（操作人、时间、原因） | 必须 | 审计追溯 |
| P-04 | 反日结需填写原因备注 | 提醒 | 审计需要，建议但不强制 |

**关于条件P-02的说明**：
- 如果7月15日要反日结7月13日，但7月14日尚未日结，系统应阻止并提示"请先完成7月14日的日结"
- 这确保日结的时间连续性
- 但如果7月14日已有"已确认"的日结，可以先反日结7月14日再反日结7月13日，或按顺序逐日反日结

**建议简化**：MVP阶段对条件P-02放宽为提醒而非阻止。即允许反日结任意已确认的日期，系统提醒"后续日期的日结可能需要同步检查"。理由是美业门店日单量小（<100单），跨日影响概率低，严格阻止反而增加操作负担。

### 5.5 补录历史订单对已确认日结的影响处理

**场景**：7月15日补录7月13日的订单（BackfillStatus=1，OrderTime=7月13日），但7月13日日结已确认

**处理流程（方案 B，2026-07-19 修订为自动反日结）**：
1. 店主补录7月13日的订单（OrderTime=7月13日，BackfillStatus=1）
2. 系统在 `CreateAsync` 事务内检测到 `BackfillStatus=1 && OrderTime < Today`
3. 系统自动对7月13日的 DailySettlement 执行反日结或补建（见 5.3 节三种处理路径）
4. 系统重新汇总7月13日数据（含补录订单）
5. 返回消息提示"订单下单日 2026-07-13 日结已自动反日结/补建，请前往日结管理重新确认"
6. 店主在日结管理页面看到7月13日为"待确认"状态，核对后重新确认

**补录订单录入错误的修正路径**：
- 由于订单修改功能已移除，店主发现补录错误时只能"取消订单 + 重新补录"
- 取消订单（`CancelAsync`）同样触发自动反日结（见 5.3 节），原下单日数据被重算为"不含已取消订单"的状态
- 重新补录正确订单时再次触发自动反日结，原下单日数据更新为"含正确补录订单"的状态
- 整个修正路径中，原下单日 DailySettlement 始终保持数据最新

**采用自动反日结的理由（方案 B）**：
- 订单修改功能已移除，"先核对再反日结"的窗口价值已弱化
- 与退款/取消订单的处理方式统一（跨日变动即反日结），降低店主认知负担
- 同日多次补录的幂等性已有保障（仅首次从 Status=1 -> 0 时记录 ReversedReason，后续只更新字段）
- 减少店主操作步骤：无需手动反日结 + 手动重算

**批量补录场景的说明**：
- 店主批量补录同一天的多笔订单时，每笔补录都会触发一次 `ReverseSettlementForOrderReversalAsync`
- 由于幂等性保障，仅首笔触发反日结状态变更（Status=1 -> 0），后续仅更新汇总字段
- 性能影响可接受：每次反日结包含一次 `SummarizeCoreAsync` 聚合查询，美业门店日单量小（<100单）

## 六、补日结交互设计

### 6.1 设计决策：逐日确认 + 一键补所有，两者都支持

**建议**：两种方式都支持，默认推荐逐日确认。

| 方式 | 适用场景 | 操作步骤 | 优势 |
|------|---------|---------|------|
| 逐日确认 | 遗漏1-3天 | 逐日查看汇总数据 -> 逐日确认 | 店主能审视每日数据 |
| 一键补所有 | 遗漏多天或长时间未日结 | 选择起止日期 -> 系统批量汇总 -> 一键全部确认 | 操作效率高 |

### 6.2 逐日确认交互

**界面元素**：
- 日结列表按日期倒序排列
- "待确认"状态的日结以醒目标签标记
- 每条待确认日结右侧显示"查看详情"和"确认日结"按钮
- 点击"查看详情"展示该日汇总数据明细（订单列表、储值流水等）
- 点击"确认日结"弹出确认弹窗，展示汇总数据，店主核对后确认

**防漏单校验**：确认前执行校验（见第七节），校验不通过则阻止确认

### 6.3 一键补所有交互

**界面元素**：
- 日结列表页面顶部显示"待确认日结"汇总条："您有 N 天日结待确认"
- 点击"一键补确认"按钮
- 系统展示待确认日期列表及其汇总数据概览（每日一行：日期、营收、订单数）
- 店主可勾选要确认的日期（默认全选）
- 点击"批量确认"按钮

**限制**：
- 一键补确认仍需执行防漏单校验
- 若某日校验不通过，该日高亮标记并排除出批量确认范围，店主需单独处理

### 6.4 推荐策略

**默认推荐逐日确认**，理由：
1. 逐日确认让店主有机会审视每日数据，发现异常
2. 一键补所有适用于长时间未日结后的追赶场景
3. 首页提醒优先引导逐日确认
4. 一键补所有作为辅助功能，在日结列表页面提供入口

## 七、防漏单校验逻辑（HIGH-031 核心）

### 7.1 校验时机

| 时机 | 校验类型 | 阻止/提醒 | 说明 |
|------|---------|----------|------|
| 日结确认时 | 完整校验 | 阻止 | 确认前必须通过所有校验，否则禁止确认 |
| 自动汇总时 | 基础校验 | 提醒 | 汇总时做基础检查，结果记入日结备注，不阻止汇总 |
| 手动汇总时 | 基础校验 | 提醒 | 同自动汇总 |

### 7.2 校验规则

#### 规则1：重复日结校验（阻止级别）

**规则**：同一门店同一日期不允许存在多条日结记录。

**逻辑**：
- 汇总时检查该日期是否已有日结记录
- 若已有记录，更新现有记录而非新建
- 若状态为"已确认"，需先反日结才能重新汇总

#### 规则2：前序汇总连续性校验（提醒级别）

**规则**：确认某日日结前，检查该日之前是否存在"无日结记录"的日期（系统汇总遗漏）。

**逻辑**：
- 由于无订单日也会生成全0日结记录，"无日结记录"必然意味着系统汇总遗漏（定时任务未执行等）
- 若存在遗漏日期，提醒店主："7月12日-7月14日无日结记录，可能汇总遗漏，建议先补汇总"
- **不阻止确认**（符合原则8补漏容忍），店主可先确认当前日结，后续补汇总
- 首日（系统使用第一天）不需要前序日结

#### 规则3：异常数据校验（提醒级别）

**规则**：检测可能导致日结数据异常的情况，辅助店主发现漏单。

| 异常类型 | 检测条件 | 处理 |
|---------|---------|------|
| 有储值消费但无订单 | TotalStoredValueConsume > 0 AND OrderCount = 0 | 提醒 |
| 退款大于营收 | TotalRefund > TotalRevenue | 提醒 |
| 营收异常高 | TotalRevenue > 历史日均的 3 倍 | 提醒 |
| 仅有退款无正常订单 | OrderCount > 0 AND 所有订单 Status=3 | 提醒 |

### 7.3 校验结果处理

| 校验结果 | 处理方式 | UI 表现 |
|---------|---------|---------|
| 全部通过 | 允许确认 | 确认按钮可点击 |
| 有阻止级校验未通过 | 禁止确认 | 确认按钮置灰，显示阻止原因 |
| 有提醒级校验未通过 | 允许确认但需额外确认 | 确认弹窗显示提醒信息，店主需勾选"已知晓"后才能确认 |

### 7.4 与补日结的关系

1. 补日结时每个日期独立校验，**不要求按顺序补**（反日结也允许跳过中间日期）
2. 一键补确认时，系统逐日校验，校验通过的日期才纳入批量确认范围
3. 前序汇总遗漏不阻止当前日结确认，仅在提醒中引导店主补汇总

## 八、与其他模块的关联

### 8.1 与订单（G3）的关系

| 关联点 | 说明 |
|--------|------|
| 数据来源 | 日结营收/退款/订单数从 Order 表汇总 |
| 补录订单影响 | 补录历史日期订单（BackfillStatus=1）影响对应日期的日结数据 |
| 订单状态影响 | Order.Status 变更（如退款）触发日结重算（待确认状态）或提醒反日结（已确认状态） |
| 时间归属 | 订单按 OrderTime 日期归属日结；退款按 RefundTime 日期归属日结 |

**关键交互**：
- 订单创建/修改/退款时，系统检查受影响日期的日结状态
- 若日结为"待确认"：自动重算
- 若日结为"已确认"：在日结页面显示"待更新"标记，提醒店主反日结
- 若日结为"待汇总"（无记录）：无需处理，下次汇总时会包含

### 8.2 与统计（G4.1）的关系

| 关联点 | 说明 |
|--------|------|
| DailyStat 同步 | 日结确认时，同步生成/更新 DailyStat 记录（同日期同门店） |
| 首页看板数据 | 首页看板优先读取 DailyStat；当日（尚未日结）实时从订单表聚合 |
| 月度统计 | MonthlyStat = SUM(DailyStat)，依赖日结确认后的 DailyStat 数据 |

**DailyStat 与 DailySettlement 的关系**：

| 维度 | DailyStat | DailySettlement |
|------|-----------|-----------------|
| 定位 | 统计快照（经营数据） | 日结记录（经营闭环动作） |
| 生成时机 | 日结确认时同步生成 | 凌晨自动汇总/手动汇总 |
| 状态 | 无状态，是数据快照 | 有状态流转（待确认/已确认/已撤销） |
| 可变性 | 随日结状态变化而更新 | 按状态规则管理可变性 |
| 用途 | 支撑首页看板和月度统计 | 店主日结确认流程 |

**说明**：DailyStat 和 DailySettlement 是两个独立但关联的实体。DailySettlement 管理日结流程（状态流转、确认、反日结），DailyStat 存储统计快照数据。日结确认时，DailySettlement 的汇总数据同步写入 DailyStat。日结反日结时，DailyStat 也同步更新。

### 8.3 与储值（G7）的关系

| 关联点 | 说明 |
|--------|------|
| 储值充值 | 计入日结 TotalStoredValueRecharge，不计入营收 |
| 储值消费 | 计入日结 TotalStoredValueConsume，同时通过订单计入营收 |
| 储值退款 | 不影响营收（充值时未计入），在储值流水中体现 |
| 数据来源 | StoredValueLog 表，按 Type 和日期汇总 |

**关键说明**：
- 储值消费金额在日结中会被"双重展示"：既在 TotalRevenue 中（单一支付通过订单 PaidAmount，组合支付通过 StoredValueAmount，统一汇总到 StoredValueRevenue），又在 TotalStoredValueConsume 中（通过储值流水）。这是设计意图，不是重复计算 -- 两个字段从不同维度展示同一笔业务。
- 储值充值独立于订单系统（G7.1），不创建订单，因此 TotalStoredValueRecharge 仅从 StoredValueLog 汇总。

### 8.4 与项目卡（B2）的关系

| 关联点 | 说明 |
|--------|------|
| 项目卡购买 | 不计入日结营收（计入负债） |
| 项目卡核销 | 按折算金额计入日结营收（通过 OrderType=3 订单） |
| 项目卡退款 | 不影响营收（购买时未计入） |

## 九、用户核心疑问解答

### 疑问1：日结是系统自动触发还是门店操作员手动触发？超时是否自动日结？

**回答**：
- **自动汇总**：系统每日凌晨2点自动汇总前一天的营业数据，生成"已汇总(待确认)"状态的日结记录。店主无需手动触发汇总。
- **手动确认**：店主需手动确认日结（一键操作），将日结从"待确认"锁定为"已确认"。
- **超时不自动确认**：日结保持"待确认"状态直到店主手动确认。系统通过首页提醒引导店主确认，但不强制、不自动确认。
- **理由**：G4.2明确"每日自动汇总"+"店主下班前确认即可"。确认是经营行为，系统不应代替。自动确认会使店主失去审视数据的机会。

### 疑问2：补日结的交互是逐日确认还是一键补所有遗漏？

**回答**：
- **两者都支持**，默认推荐逐日确认。
- **逐日确认**：适用于遗漏1-3天的场景。店主逐日查看汇总数据，核对无误后逐日确认。
- **一键补所有**：适用于长时间未日结的场景。选择起止日期，系统批量汇总并展示概览，店主可勾选要确认的日期，一键批量确认。
- **理由**：逐日确认让店主有机会审视数据（符合日结的核心价值），一键补所有提供效率（符合极简优先原则）。两者并存，店主按需选择。

### 疑问3：系统自动汇总的日结数据如果发现有误能否修改？是改订单还是改日结数据？

**回答**：
- **改订单而非改日结数据**。日结数据是订单等业务数据的汇总结果，发现错误时修正源头数据（订单、储值流水等），然后重新汇总日结。
- **待确认状态下**：修改/新增订单后，系统自动重算日结汇总数据，无需额外操作。
- **已确认状态下**：需先反日结，系统重新汇总后，店主重新核对确认。
- **理由**：日结是派生数据，直接修改会导致与订单数据不一致。修正源头数据保持数据链路完整可追溯，与原则1（记账不交易）一致。

### 疑问4：日结确认（锁定）后能否修改？如何处理补录历史订单？

**回答**：
- **确认后不能直接修改**。日结数据锁定为当日经营基线。
- **通过反日结机制修改**：店主执行反日结操作，日结回到"待确认"状态，系统重新汇总数据，店主核对后重新确认。
- **补录历史订单处理**：
  1. 店主补录历史日期订单（如7月13日的订单在7月15日补录）
  2. 系统检测到7月13日日结已确认，在日结页面显示"待更新"标记
  3. 店主对7月13日执行反日结 -> 系统重新汇总（含补录订单）-> 店主重新确认
- **不做自动反日结**：反日结是重要操作，应由店主主动决定。店主可能需要先确认补录订单的正确性。

## 十二、风险与待确认事项

### 12.1 需用户确认的设计决策

| 编号 | 决策点 | 本文档建议 | 需确认原因 |
|------|--------|-----------|-----------|
| Q-01 | 凌晨兜底汇总的具体时间 | 02:00（已确认） | 可能在某些门店的营业时间内 |
| Q-02 | 反日结是否允许跳过中间日期 | 允许（已确认） | 反日结针对具体日期，中间日期订单未改不受影响 |
| Q-03 | 反日结是否必须填写原因 | 建议填写但不强制（已确认） | 审计需要 vs 极简优先 |
| Q-04 | 暂停营业日是否需要日结 | 生成0数据记录（已确认） | 无订单日统一生成0数据记录，不需要特殊处理 |
| Q-05 | 一键补确认是否允许跨月 | 允许，但提醒跨月影响月度统计（已确认） | 跨月可能影响月度统计 |

### 12.2 潜在风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 长时间不日结导致数据积压 | 补日结工作量大 | 首页持续提醒，逾期标红 |
| 频繁反日结导致数据不稳定 | DailyStat 频繁变动 | 日结确认后才同步 DailyStat，待确认状态不影响 |
| 补录订单影响多个已确认日结 | 需逐日反日结 | 提供批量反日结功能（后续迭代） |
| 并发汇总导致数据不一致 | 日结数据错误 | 同一日期同一门店的汇总加锁 |

| 术语 | 定义 |
|------|------|
| 日结 | 每日营业数据的汇总确认流程 |
