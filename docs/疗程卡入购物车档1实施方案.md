# 项目卡入购物车档1实施方案

> 创建日期: 2026-08-19
>
> 背景: POS 快速收银（`src/Admin/mes-admin/src/views/store/pos/quick/index.vue`）当前项目卡有两条独立链路（项目卡 Tab 开卡弹窗、底部"项目卡核销"按钮），均不经过购物车。现要求"项目卡选择到购物车"，即开卡与核销都支持与商品/服务混合结算。经需求澄清与多轮影响分析，确认采用"档1"方案：开卡入购物车仅做展示关联（收款仍走现有独立销售流程），核销入购物车（结算时调独立核销接口），并引入批次号做交易聚合。

---

## 一、方案总览

| 维度 | 档1 决策 |
|------|----------|
| 核销入购物车 | ✅ 购物车新增核销行，结算时调 `verifyTreatmentCard` 独立接口，核销项不参与收款（`PaidAmount=0`） |
| 开卡入购物车 | ✅ 购物车新增开卡行，结算时调 `createTreatmentCardSale`（现有独立销售流程），**不新增 OrderType、不新增支付载体、不进入订单统计/日结** |
| 交易关联 | 三张单据（订单/核销/开卡）挂 `CheckoutSessionNo` 批次号，落库可追溯，前端聚合展示 |
| 混合单修复 | 后端按行分流修复"零售+服务"合单库存/统计缺口（独立工作包，为合单兜底） |

### 核心业务场景

| 场景 | 购物车组成 | 结算产出 |
|------|------------|----------|
| 纯商品/服务 | 商品/服务行 | 1 张订单 |
| 商品 + 核销 | 商品/服务行 + 核销行 | 1 张订单 + N 条核销记录（各含 1 张 Type=3 订单） |
| 商品 + 开卡 | 商品/服务行 + 开卡行 | 1 张订单 + N 条项目卡销售记录（开卡不建单） |
| 三者混合 | 商品/服务行 + 核销行 + 开卡行 | 1 张订单 + N 条核销记录 + N 条开卡记录 |

## 二、现状分析（关键代码点）

### 2.1 订单模型约束

- `Order.OrderType` 为单值字段，注释明确仅允许 1(零售)/2(服务)/3(项目卡核销)（`src/Services/Store/Bms.Store.Domain/Entities/Order.cs`）。
- `OrderAppService.CreateAsync` 显式拒绝 `OrderType==3`，强制核销走独立核销接口（`OrderAppService.cs:231`）——**该约束在档1中保留，核销项不通过订单接口创建**。
- `OrderAppService.CreateAsync` 库存扣减 `switch` 仅处理 case 1（零售扣实物）/ case 2（服务扣 BOM）（`OrderAppService.cs:402-414`）。

### 2.2 现有"零售+服务混合"的缺口

- 前端 `orderType = hasService ? 2 : 1`（`quick/index.vue:1298-1299`）：购物车含任一服务项目即整体记为 Type=2。
- `DeductServiceBomAsync` 逐行查 BOM，**无 BOM 的零售商品行被 `continue` 跳过，实物库存不扣**（`OrderAppService.cs:785-794`）。
- `RecordProductSalesStatAsync` 按 `order.OrderType` 单值映射 `ProductType`（1→1零售、2→2服务），混合订单中零售商品被统计成"服务"（`OrderAppService.cs:1141-1147`）。
- 退款按 `OrderItemBatch` 精确退（`RefundRetailInventoryAsync`），零售行未扣过库存则无批次可退。

### 2.3 项目卡现有链路

- 核销：`TreatmentCardVerifyAppService.CreateAsync` 创建核销主单 + Type=3 订单（`OrderNo=TCV-...`、`PaidAmount=0`、`Status=2`），扣卡次数、按 `Product.Type` 联动扣库存/BOM、写消费记录（不发积分）、写 `ProductSalesStat(ProductType=5)`、跨店审计（`TreatmentCardVerifyAppService.cs:242-428`）。
- 开卡：`TreatmentCardSaleAppService.CreateAsync` **不创建订单**（`OrderId=null`，`TreatmentCardSaleAppService.cs:248`），一次性发积分；金额**不进入订单统计/日结营收**（日结统计 Orders + TreatmentCardVerifies + StoredValueLogs，开卡金额不在其中）。
- 核销接口入参：`TreatmentCardVerifyRequest{ cardSaleId, items[{productId, verifyTimes}], operatorId?, remark? }`（`src/Admin/mes-admin/src/api/treatment-card/types.ts:432-445`），金额/关联订单/时间由后端计算。
- 开卡接口入参：`createTreatmentCardSale({ cardId, customerId, purchaseDate, amount, items[{productId, quantity, originalPrice}] })`（`quick/index.vue:1530-1537`）。

### 2.4 日结口径

- 现金/储值营收按 `Order.PayMethod` 汇总；核销折算金额单独从 `TreatmentCardVerifies.VerifyAmount` 聚合（权责发生制转营收）；成本按 `InventoryLog.SourceType` 区分（`DailySettlementAppService.cs:85-210`）。
- 开卡金额不参与日结营收（现状口径，档1保持不变）。

## 三、已确认决策

| 编号 | 决策 | 说明 |
|------|------|------|
| D1 | `CheckoutSessionNo` 落库 | `Order` / `TreatmentCardVerify` / `TreatmentCardSale` 三表新增字段，可历史追溯（需 Migration） |
| D2 | 结算顺序：先核销后建单 | 核销扣次成功后再收款建单，避免收款失败白扣卡次 |
| D3 | 开卡金额不纳入统计/日结 | 保持现状口径，开卡仅作展示关联，收款走现有独立销售流程 |

## 四、工作包设计

### WP1 后端混合单按行分流修复（独立 bug fix）

**目标**：修复"零售+服务"合单时零售商品丢库存、统计错乱。

**改动**（`src/Services/Store/Bms.Store.Application/Services/OrderAppService.cs`）：

1. `CreateAsync` case 2（`OrderAppService.cs:409-412`）按行分流扣减：
   - 服务行（有 BOM）→ `DeductServiceBomAsync` 扣 BOM 耗材；
   - 实物行（`productTypeMap` 中非赠品、非服务，即 `Product.Master.Type=1` 实物）→ 补调 `DeductItemBatchesAsync` 扣实物库存（复用零售扣减逻辑，`OrderAppService.cs:519`）；
   - 赠品行（Type=5）→ 仍走 `DeductSampleGiftOutAsync`。
   - 前置数据：`productTypeMap` 已在 `CreateAsync:238-240` 加载，可直接复用。
2. `RecordProductSalesStatAsync`（`OrderAppService.cs:1141`）改为按行映射：用 `productTypeMap` 逐行判定 `ProductType`（1→零售、2→服务），不再用 `order.OrderType` 单值。
3. 退款逻辑无需改动：`RefundRetailInventoryAsync` 按 `OrderItemBatch` 精确退，扣减修复后零售行自动有批次可退。

**验证**：构造零售+服务混合订单，核对 `InventoryBatch`/`InventoryLog` 扣减正确、`ProductSalesStat.ProductType` 与商品实际类型一致、全额退款后库存与批次 `RefundedQuantity` 完整回补。

### WP2 核销入购物车（前端）

**改动**（`src/Admin/mes-admin/src/views/store/pos/quick/index.vue`）：

1. **购物车行类型扩展**：

```ts
type CartLineType = 'product' | 'verify' | 'sale'

interface CartItem {
  // ...现有字段
  lineType: CartLineType
  // 核销行专属
  cardSaleId?: number          // 项目卡销售记录ID
  cardName?: string            // 卡名（展示）
  remainingTimes?: number      // 剩余次数（展示）
  verifyItems?: { productId?: number; verifyTimes: number }[]  // 核销项目列表
}
```

2. **「项目卡核销」按钮改造**（现 `handleVerifyCard`，`quick/index.vue:1611`）：选会员 → 查有效卡（复用 `loadCustomerCards`，`:1619`）→ 选卡选项目 → **加入购物车**（生成核销行）而非直接提交核销。支持多张卡多行。
3. **购物车核销行展示**：卡名、核销项目、次数、剩余次数；金额仅展示不参与收款（`rowSubAmount` 逻辑可复用，`:1579`）。
4. **核销行编辑**：只读展示 + 删除；需调整项目/次数时删除后重新添加（最小实现）。
5. **结算拆分**：核销行从收款中排除——`payableAmount`、组合支付三栏（现金/储值/积分）、储值余额校验、积分校验基数均**不含核销行**。

### WP3 开卡入购物车（档1：仅展示关联，前端）

**改动**（`quick/index.vue`）：

1. **项目卡 Tab 点击行为**：由"立即打开销售弹窗提交"改为"选择会员 + 输入售价 → 加入购物车"（生成开卡行）。复用现项目卡配置数据 `treatmentCards`（`:698`）。
2. **购物车开卡行**：展示卡名、售价、会员；可删除。
3. **结算拆分**：开卡行参与 `payableAmount` 展示，但**收款走独立销售流程**——结算时调 `createTreatmentCardSale`（现有接口），金额为线下/独立收款，**不进入系统支付（PayMethod/储值/积分）**，与现状开卡一致。

### WP4 CheckoutSessionNo 批次关联（落库 + 聚合展示）

**后端**：

1. 三表新增可空字段 `CheckoutSessionNo`（`nvarchar(64)`，建议索引）：
   - `src/Services/Store/Bms.Store.Domain/Entities/Order.cs`
   - `src/Services/Store/Bms.Store.Domain/Entities/TreatmentCardVerify.cs`
   - `src/Services/Store/Bms.Store.Domain/Entities/TreatmentCardSale.cs`
2. 三个 Create DTO 新增可选字段 `CheckoutSessionNo`（向后兼容，历史单据为空）：
   - `src/Services/Store/Bms.Store.Application/Dtos/Orders/OrderCreateDto.cs`
   - `src/Services/Store/Bms.Store.Application/Dtos/TreatmentCards/TreatmentCardVerifyCreateDto.cs`
   - `src/Services/Store/Bms.Store.Application/Dtos/TreatmentCards/TreatmentCardSaleCreateDto.cs`
3. 三个 AppService 的 CreateAsync 将 DTO 字段透传落库：
   - `OrderAppService.CreateAsync`
   - `TreatmentCardVerifyAppService.CreateAsync`
   - `TreatmentCardSaleAppService.CreateAsync`
4. 新增 Migration（见第八章）。

**前端**：

1. 结算时生成批次号（`checkoutSessionNo`，如 `CS{yyyyMMddHHmmss}{3位随机}`），透传给三个接口。
2. 结算成功弹窗聚合展示"本次交易完成"：
   - 商品订单：单号、金额、支付方式；
   - 核销记录：核销单号、卡名、次数；
   - 开卡记录：卡名、金额。
3. 类型定义扩展：`OrderCreate`/`TreatmentCardVerifyRequest`/`TreatmentCardSaleRequest` 增加 `checkoutSessionNo?`。

## 五、结算时序（handleConfirmPay 改造）

```
用户点击「结算收银」
  ├─ 1. 校验
  │     - 核销行必须已选卡+项目（canConfirmVerify 逻辑复用）
  │     - 会员必填（核销/开卡均依赖 CustomerId）
  ├─ 2. 生成 checkoutSessionNo
  ├─ 3. 拆分购物车三批（先核销、后建单、再开卡）
  │     A. 核销行（每行）→ verifyTreatmentCard({ cardSaleId, items, remark, checkoutSessionNo })
  │     B. 商品/服务行 → createOrder({ ...现有 payload, checkoutSessionNo })   ← 系统收款（PayMethod/储值/积分/组合）
  │     C. 开卡行（每行）→ createTreatmentCardSale({ cardId, customerId, purchaseDate, amount, items, checkoutSessionNo })  ← 线下独立收款
  ├─ 4. 部分成功容错：记录每批成功/失败，失败项弹窗提示重试（只补未成功项，不重复已成功项）
  └─ 5. 全部成功 → 弹窗聚合展示本次交易（订单号/核销单号/开卡记录），清空购物车
```

**收款金额口径**：

| 行类型 | 计入应付金额 | 参与系统支付（PayMethod/储值/积分） |
|--------|-------------|-----------------------------------|
| 商品/服务行 | ✅ | ✅ |
| 开卡行 | ✅（展示） | ❌（线下独立收款） |
| 核销行 | ❌（仅展示） | ❌（不收款，扣卡次） |

## 六、边界与失败处理

1. **非原子性（档1固有代价）**：三批独立接口，任一失败不回滚其他。前端维护"已成功清单"，失败重试只补未成功部分，避免重复建单/重复核销/重复开卡。
2. **核销失败重试防重复扣次**：核销扣次为消耗性操作，重试前弹窗确认"该卡核销是否已成功"，防止重复扣次。
3. **收款口径**：开卡金额在结算弹窗单独标注"线下收取"，不进入 PayMethod/储值/积分三栏（与现状开卡一致）。
4. **服务资源冲突**：购物车内"零售+服务"仍合单（WP1 修复兜底），不拆单，不触碰 `ResourceConflictCheckService` 逻辑。
5. **会员一致性**：核销/开卡均强依赖会员，结算前必须已选会员；核销卡属主与当前会员需一致（后端 `TreatmentCardVerifyAppService` 已有客户归属校验）。

## 九、风险与后续扩展

1. **非原子性是档1固有代价**：部分成功需人工介入。若后续要求原子性 → 升级档2（开卡/核销并入订单支付体系，引入支付载体）。
2. **开卡线下收款**：系统不跟踪开卡收到的钱（现状如此），对账靠门店线下，属已知取舍（决策 D3）。
3. **核销单与商品单分离**：一次到店核销+购买产生多张单号，靠 `CheckoutSessionNo` 聚合追溯；订单列表暂不折叠展示（后续可按批次号增强）。
4. **WP1 是独立 bug fix**：不依赖项目卡功能，可先行上线修复存量混合单问题。
