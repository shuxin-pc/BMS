# 门店管理系统 - 大方向与应用场景纲领

> 版本: v1.0 | 日期: 2026-07-12 | 状态: 已确认
>
> 本文档作为《通用需求规格.md》《门店管理系统菜单架构.md》《门店管理系统架构设计.md》的前置指导纲领，用于规范功能设计方向，避免实现偏差。所有后续功能设计、技术实现都应以本纲领为准绳。

## 一、整体需求描述

### 1.1 系统目的

**一句话定位**：面向小微实体美容门店的**事后记账型经营辅助工具**，不是交易引擎。

- 系统记录已发生的业务（进货/交易/库存变动等），不驱动交易
- 店主在线下完成真实交易后，通过系统**补录**数据
- 系统的价值在"记完账后给店主看懂生意"，不在"通过系统做生意"
- 门店系统是整个平台内的一个独立子系统，门店管理人员作为平台一个租户存在

### 1.2 面向对象

| 维度 | 画像 |
|------|------|
| 行业 | 美容院/美甲店/美发店/皮肤管理/SPA等生活美容，以及医疗美容机构的经营管理（不覆盖医疗业务本身） |
| 规模 | 1-5 人（含店主），单店为主，可能 1 租户多店 |
| 日单量 | <100 单 |
| 操作者 | 店主亲自操作为主，部分功能指定员工使用 |
| IT 能力 | 低，要求交互极简，减少店员学习成本 |
| 设备 | MVP 桌面端为主，手机端后期单独设计制作 |
| 平台关系 | 门店管理人员作为平台租户存在，平台对门店系统的主要约束在用户及权限方面 |

### 1.3 核心价值主张

相比纸笔等线下记录或部分门店使用的成熟收银软件，本系统的 3 个核心爽点：

| 层次 | 爽点 | 含义 |
|------|------|------|
| 入口体验层 | 使用方便 | 学习成本低，操作步骤少，店主愿意天天用 |
| 核心价值层 | 流水一目了然 | 首页打开即看经营状况，不用算账 |
| 终极目标层 | 辅助盈利 | 数据洞察 + 营销增量 + 库存损耗 + 储值现金流，4 方向并重 |

**辅助盈利的 4 个方向：**

| 方向 | 实现手段 |
|------|---------|
| 数据洞察驱动决策 | 首页看板、毛利分析、客户消费统计 |
| 营销工具带增量收入 | 宣传图片生成、积分体系、疗程卡、储值 |
| 库存/效期减少损耗 | 库存预警、效期管理、样品赠品管理 |
| 会员储值优化现金流 | 储值赠送规则、沉淀资金统计 |

### 1.4 典型使用场景

**场景 1：交易补录（高频）**
- 客户线下付款后，店主在电脑上 3 步内完成开单记账
- 忙时允许跳过，下班前根据"待补录提醒"补上
- 漏记的允许补录历史日期订单

**场景 2：经营查看（高频）**
- 每日开店，店主查看昨日营收/今日预约
- 当天可随时手动汇总查看日结数据，每日下班前确认日结（凌晨自动汇总为兜底机制）
- 每月查看月度趋势

**场景 3：库存管理（中频）**
- 进货时在电脑上做入库，关联供应商
- 库存预警时及时补货
- 效期临近时系统提醒，避免损耗

**场景 4：客户运营（中频）**
- 客户到店，店主查客户档案（肤质/过敏史/疗程卡余额）
- 客户消费后，系统自动累积积分（店主不需要手动操作）
- 储值客户到店，直接扣减余额

**场景 5：营销活动（低频）**
- 店主选模板生成宣传图片，打印或发朋友圈
- 配置储值赠送规则，吸引客户充值
- 配置积分兑换，促进复购

### 1.5 多门店业务模式

- 1 租户可拥有多个实体门店，但以单店视角为主
- MVP 支持多店独立运营：店主可创建多店、切换门店查看各自数据
- 业务数据（订单、库存、消费记录等）按门店隔离，不做跨店汇总报表、库存调拨
- 跨店权益（疗程卡、储值卡）在租户内共享，客户在租户内任意门店均可使用

## 二、设计原则

以下 8 条原则从大方向推导，后续每个功能设计都应对照检查。功能设计出现偏差时，回到这 8 条原则校准。

### 原则 1：记账不交易

- 系统记录已发生的业务，不驱动交易
- 收银是"补录"不是"收款"
- **推论**：不对接支付平台，支付方式只是标记
- **推论**：储值卡消费是系统内资金流变动，不是"支付"
- **推论**：系统不涉及实际资金流转，只记录资金流向
- **推论**：疗程卡核销、储值消费为实时权益变动，不适用补录
- **推论**：储值卡验证职责归收款执行人，系统仅做数据变更记录

### 原则 2：极简优先

- 每多一个操作步骤，店主就少一分使用意愿
- **推论**：开单 3 步内完成，常用功能一键触达
- **推论**：减少必填项，提供智能默认值
- **推论**：不为了"系统完整性"增加店主负担

### 原则 3：经营者视角

- 所有功能从经营者使用角度设计，不是从"系统完整性"角度
- **推论**：经营者角色包括店主、店长、前台等，系统需明确各角色的权限边界
- **推论**：不做客户自助端（MVP）
- **推论**：报表要直观，不要会计级
- **推论**：不做营销自动化触达，提醒仅限店主端

### 原则 4：门店业务数据隔离，跨店权益共享

- 门店业务数据严格隔离，跨店权益（疗程卡、储值卡）在租户内共享
- **推论**：所有业务实体带 StoreId，核销/消费记录归属具体门店
- **推论**：疗程卡、储值卡在租户内跨店通用，不归属单一门店
- **推论**：UI 需要门店切换器
- **推论**：MVP 不做跨店业务数据汇总/调拨/共享

### 原则 5：美容专注

- MVP 聚焦美容行业，不强行通用
- **推论**：数据模型为美容设计，但不主动阻碍扩展（用主表+子表）
- **推论**：不做行业切换/模块可见性配置
- **推论**：未来扩展其他行业时再重构，不为假想需求预留
- **推论**：适用于生活美容与医疗美容机构的经营管理，但不覆盖医疗业务本身（如处方、病历、医疗操作等）

### 原则 6：平台分工

- 用户/权限归平台，业务归门店系统
- **推论**：不重复建设账号体系
- **推论**：通过 JWT 复用平台认证
- **推论**：门店系统不存用户密码
- **推论**：门店系统通过 HTTP 调用 System 服务获取用户/菜单/权限

### 原则 7：桌面优先

- MVP 只做桌面端，手机端后期单独设计制作
- **推论**：MVP 不做响应式适配
- **推论**：手机端是后期独立项目，单独设计页面，不在同一页面中混合
- **推论**：不为手机端做 UI 预留，但后端 API 要保持通用性

### 原则 8：补漏容忍

- 允许店主漏记后补录，但不允许遗漏
- **推论**：支持补录历史日期订单
- **推论**：通过站内信推送"今日待补录"提醒（不强制，站内信功能待补充）
- **推论**：日结时校验防漏单（提醒级，不阻止确认；详见 `docs/通用需求规格.md` G4.2 日结业务规则）

## 三、范围边界

### 3.1 MVP 范围

- v1.5 通用需求规格中的模块（按本纲领第四章修正后）
- 多店独立运营（业务数据不跨店，跨店权益共享）
- 桌面端完整功能
- 适用于生活美容与医疗美容机构的经营管理（不覆盖医疗业务本身）

### 3.2 明确不做

| 不做项 | 理由 |
|--------|------|
| 线上交易/电商 | 与线下交易模式冲突 |
| 客户自助端（小程序/H5） | MVP 不做，后期根据市场反馈再决定 |
| 员工考勤 | 超出经营辅助范畴，不增加系统负担 |
| 员工排班 | 预约防冲突基于已记录的预约本身实现，技师在店/请假等线下情况由门店人员知情处理 |
| 会计级财务报表 | 系统只做经营流水，不做财务会计 |
| 营销自动化触达 | 提醒仅限店主端，不自动触达客户 |
| 客户关怀（G5.5） | MVP 不需要，后期再说 |
| 跨店汇总/调拨/共享 | MVP 多店业务数据独立运营，跨店权益共享 |
| 手机端页面（MVP） | 后期单独设计制作，不在 MVP 范围 |
| 其他行业适配 | MVP 聚焦美容（含医疗美容经营管理），不考虑其他行业扩展 |

## 四、对 v1.5 需求规格的修正建议

大方向明确后，v1.5 通用需求规格需要以下修正：

| 编号 | 现状 | 修正建议 | 依据原则 |
|------|------|---------|---------|
| G3.1 快速开单 | 未提补漏 | 增加"待补录提醒"和"历史日期补录"机制 | 原则 8：补漏容忍 |
| G3.2 多种支付方式 | 列出 4 种支付 | 明确"支付方式仅为标记，不对接支付平台"；储值卡消费是"系统内资金流" | 原则 1：记账不交易 |
| G5.5 客户关怀 | 含生日提醒、消费感谢 | **MVP 不做**，从需求中移除 | 范围边界：明确不做 |
| 首页看板 G4.1 | 桌面端视角 | MVP 桌面端实现，手机端后期单独设计 | 原则 7：桌面优先 |
| 全局 | 未提门店切换 | 补充"门店切换器"作为全局组件 | 原则 4：门店隔离 |
