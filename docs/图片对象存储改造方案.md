# 图片对象存储改造方案（MinIO）

## 一、背景与目标

### 现状问题

项目所有图片字段命名均为 `XxxUrl`，设计意图是**存引用**：

| 实体 | 字段 |
|---|---|
| `ProductMaster` | `ImageUrl` |
| `Technician` | `AvatarUrl` |
| `PurchaseReturn` | `VoucherImageUrl` |
| `ServiceComparisonPhotoItem` | `PhotoUrl` |

但项目当前**没有任何文件上传能力**（全局无 `IFormFile`、无 `UseStaticFiles`、无 `wwwroot`、无对象存储 SDK）。前端 `PhotoUploadDialog.vue` 的 `handleBeforeUpload` 用 `FileReader` 把本地图片转成 base64 DataURL 直接写入该字段，导致图片实体落进了数据库 `text` 列。

按服务对比照片的上限（服务前 12 张 + 服务后 12 张）估算：手机实景照 2–4MB/张，base64 膨胀约 33% → 3–5MB/张，**单组记录可达 70–120MB**。

由此产生的问题，按紧急程度排序：

1. **列表接口会打爆内存（即刻可触发）**：`ServiceComparisonPhotoAppService.FillItemsAsync` 会 `Select` 当页所有明细的 `PhotoUrl`，默认 20 条/页 → 单次响应可能达数百 MB。
2. 图片无法被浏览器缓存，每次翻页/刷新全量重传。
3. 数据库体积被图片主导，`pg_dump` 耗时、备份存储、主从复制流量全部受累。
4. 超 2KB 的 `text` 走 PostgreSQL TOAST 外存并尝试压缩，而 JPEG 再 base64 几乎不可压缩，纯属无效开销。
5. 无法生成缩略图，列表页必须加载原图。

### 目标

- 图片存入 MinIO，数据库仅保存**对象键（object key）**
- 列表接口响应体回归 KB 级
- 保持现有的租户/门店数据隔离强度，照片不可被越权访问
- 抽象出**跨服务可复用**的文件存储能力（共享类库），供 `ImageUrl` / `AvatarUrl` / `VoucherImageUrl` 及其他子系统服务后续接入
- 不锁死 MinIO，将来可平滑切换到阿里云 OSS 等 S3 兼容服务

### 非目标（本次不做）

- 前端直传（预签名 PUT）——见「关键设计决策」决策 3
- 缩略图生成
- 历史 base64 数据迁移——已确认不保留

---

## 二、方案总览

```
浏览器
  │  ① POST /api/store/files  (multipart, 单张图片)
  │     ← { objectKey, fileName, size }
  │
  │  ② POST /api/store/servicecomparisonphotos
  │     { ..., items: [{ objectKey }] }        ← 只传 key，不再传图片内容
  │
  │  ③ GET  /api/store/servicecomparisonphotos
  │     ← { items: [{ id, photoUrl, sortOrder }] }
  │        photoUrl 为后端现场生成的预签名 URL（有时效）
  │
  │  ④ GET  http://minio:9000/bms-store/...?Signature=...
  ▼     浏览器凭预签名 URL 直接向 MinIO 取图（不经过 Store API）
```

分两个层级落地：

- **MinIO 是基础设施组件**，与 PostgreSQL 同层级，以 Windows 服务方式常驻本机（不用 Docker，见 4.1）。**不新增微服务项目，不注册 Consul，不改 `ocelot.json`。**
- **存储能力抽成共享类库** `Bms.BuildingBlocks.Storage`，与 `Core` / `Web` / `MultiTenant` 同级，供所有子系统服务复用（`Bms.sln` 需新增该项目）。

## 三、关键设计决策

### 决策 1：存储能力放 BuildingBlocks 共享类库，而非 System 服务

文件存储是**通用能力**，不应锁在 Store 服务内。但通用能力的落点有两种选择：

| 选项 | 优点 | 缺点 |
|---|---|---|
| **共享类库 `BuildingBlocks.Storage`（选用）** | 无跨服务往返；预签名本地计算；各服务复用同一份实现与校验逻辑；与项目现有惯例一致 | MinIO 凭据需在各服务 appsettings 中配置 |
| 下沉到 System 服务，其他服务 HTTP 调用 | 凭据集中一处 | System 不认识 `storeId`；读取路径引入跨服务往返与可用性单点 |

**选共享类库。** 三条依据：

1. **System 服务不认识 `storeId`。** System 的中间件管道中没有 `StoreContextMiddleware` / `StoreAccessMiddleware` / `StoreRequiredActionFilter`（这些仅存在于 Store 服务）。而 objectKey 前缀需要 `{tenantId}/{storeId}/...`，上传端点若放 System，`storeId` 只能由前端传入，直接违反本方案「租户/门店标识取自 `ICurrentUser`，不接受前端传入」的安全底线。

2. **读取路径会引入运行时强依赖。** 预签名 URL 必须在持有 objectKey 的服务内现场生成。若 Store 不持凭据，每个照片列表接口都要多一次跨服务往返，且 System 故障会导致 Store 照片全部无法显示；若 Store 持凭据，则「凭据集中」的收益归零，System 只剩一个上传端点，没有意义。

3. **项目既有惯例是通用能力进 BuildingBlocks，不进 System。** 雪花 ID 生成（`Core/IdGenerator`）、Consul 服务发现（`Core/ServiceDiscovery`）、审计日志上下文（`Core/Context`）、JWT 认证与 `CurrentUser`（`Web`）、`ICurrentUser` 与 `PermissionAttribute`（`Abstractions`）、多租户解析与中间件（`MultiTenant`）—— 一个都没放在 System 服务。System 承载的是**业务能力**（用户/角色/菜单/租户/消息），每项都有自己的数据表；文件存储没有业务语义、没有需要 System 独占的表，性质上属于基础设施。

此外，项目的跨服务调用范式本就是 **Npgsql 直连对方数据库**（见 `Store.Api/Services/UserQueryService.cs` 类注释）。既然各服务直连共享 PostgreSQL 是既有做法，各服务直连共享 MinIO 属同一性质。

**能力共享，端点各归其位**：存储实现与校验逻辑在类库中共享；上传端点由各服务自行开设，从而运行在自己的业务上下文里——Store 的 `POST /api/store/files` 走门店上下文（前缀含 `storeId`），System 将来做用户头像时开 `POST /api/system/files`（无门店维度，前缀退化为 `{tenantId}/system-avatar/...`）。

> **为什么 Controller 不放类库**：类库中的 Controller 需要 `AddControllers().AddApplicationPart(...)` 才能被发现，而现有三个服务的 `Program.cs` 均未调用（`BuildingBlocks.Core/HealthChecks/HealthCheckController.cs` 因此实际未生效）。与其引入 ApplicationPart 机制，不如让各服务自行开设 Controller。

**边界规则（防止下一个服务接入时产生冗余代码）**：服务侧代码只允许两件事——**数据搬运**（从 `IFormFile` 取流、从 `ICurrentUser` 取租户/门店）与**响应包装**（套成本服务自己的 `ApiResponseDto<T>`）。任何判断、校验、拼装、异常处理都必须在类库内，服务侧不得出现 `if`。

这条规则由类型签名强制，而非靠自觉：类库暴露的 `IFileUploadService.UploadAsync` 返回带成败标记的结果对象（见 4.3），服务侧无从复制校验逻辑；预签名与删除接口强制要求传入 `PresignScope`，前缀越权校验因此不可能被漏写。

> 响应包装之所以无法共享：`ApiResponseDto<T>` 在各服务的 Application 层各有一份独立定义（`Store.Application/Dtos/`、`System.Application/Dtos/`），类型不同，无法抽公共 Controller 基类。这是既有结构的约束，不在本次改造范围内。

### 决策 2：读取走预签名 URL，而非 API 代理

| 选项 | 优点 | 缺点 |
|---|---|---|
| **预签名 URL（选用）** | 图片流量不经 Store API；浏览器可缓存；实现简单 | URL 在有效期内可被转发传播 |
| API 代理读取 | 每次读取都经完整鉴权链 | 图片流量全压在 Store API；无法利用浏览器缓存 |

**选预签名 URL，有效期 30 分钟。** 对比照片属敏感隐私但非高危凭证，短时效签名的风险可接受，换取的性能收益显著。

**安全前提**：预签名由后端生成，后端只会为**属于当前租户/门店前缀**的 key 签名（见「六、安全设计」），因此越权访问在签名环节即被阻断。

### 决策 3：上传经 API 转发，而非前端直传

| 选项 | 优点 | 缺点 |
|---|---|---|
| **经 API 转发（选用）** | 服务端可校验真实文件类型、大小；无需配置 MinIO CORS；单阶段协议，前端简单；可审计 | 图片上行流量经过 Store API |
| 前端直传预签名 PUT | 不占用 API 带宽 | 服务端无法校验文件内容；需配 MinIO CORS；两阶段协议；孤儿对象更难治理 |

**选经 API 转发。** 单张图 ≤10MB、单次最多 12 张，不是视频级流量，API 转发完全可承受；而服务端校验（尤其魔术字节校验，防止伪装成图片的可执行文件）是不能放弃的安全边界。前端直传属于性能优化，等真的出现带宽瓶颈再做。

### 决策 4：实体存引用，DTO 出可展示 URL

这是本方案的关键命名设计，两侧语义都准确且**前端展示逻辑零改动**：

| 层 | 字段 | 内容 | 说明 |
|---|---|---|---|
| 实体 | `PhotoSource` | `1001/2001/customer-photo/202608/7234...jpg`<br>或 `https://img.example.com/abc.jpg` | 照片来源：MinIO 对象键（相对 key，不含 endpoint）**或**外部图片直链 |
| 输入 DTO | `ObjectKey` | 同上 | 前端上传后回传的 key，或用户粘贴的外链 |
| 输出 DTO | `PhotoUrl` | `http://.../...?X-Amz-Signature=...`<br>或原样外链 | 可直接放进 `<img src>` 的地址 |

**字段为什么不叫 `PhotoObjectKey`**：它同时容纳 objectKey 与外部直链两种值（见决策 5），叫 `PhotoObjectKey` 会误导后续开发者。也**不能沿用 `PhotoUrl`** —— 那正是本次要修掉的错误语义，留着这个名字，下一个人还会往里写完整 URL。`PhotoSource`（照片来源）对两种值都成立。

**绝不能把 MinIO 的完整 URL 或预签名 URL 入库**。MinIO 能给出的两种地址都不可存：

| 地址形态 | 为什么不能入库 |
|---|---|
| 预签名 URL（带 `X-Amz-Signature` / `X-Amz-Expires`） | 30 分钟后失效，字段随即变成死链 |
| 静态拼接 `{endpoint}/{bucket}/{key}` | 桶是 private，直接访问 403；要能访问就得把桶设为公开读，越权隔离随之作废。且写死 endpoint，换域名或迁云时历史数据全废 |

因此 MinIO 图片的 URL 只能**每次读取时现场签发**，库里只存 key。

### 决策 5：外部图片直链与 objectKey 单字段并存

「输入图片URL」入口保留。实现方式是**单字段前缀判别**，而非增设 `ExternalUrl` 列：

```
PhotoSource.StartsWith("http://") || StartsWith("https://")  →  外链，原样返回
否则                                                          →  objectKey，现场签名
```

不用双字段，是因为双字段会引入「二者必有且只有一个非空」这条隐式不变量，需要额外校验去保证，而单字段前缀判别没有非法中间态。

**并存带来的两处必要处理**：

1. **协议白名单（安全必需）**：外链是前端传入的任意字符串，会原样渲染进 `<img src>`。若不限制协议，`javascript:` 伪协议、`data:text/html` 即是现成的 XSS 入口。写入时必须校验**只接受 `http://` / `https://`**，其余一律拒绝。
2. **删除路径无需额外改造**：`DeleteManyAsync` 的 `PresignScope` 前缀校验会发现 `https://...` 不匹配 `{tenantId}/{storeId}/` 前缀而自动跳过，不会误删非本店对象。这是决策 1 中「授权范围做成必填参数」设计的顺带收益。

**业务上的取舍**：外链图片不受本系统控制——图床失效、开启防盗链、或图片被替换成别的内容，均无从保障，也无法纳入备份与孤儿清理。这是保留该入口的既知代价（见第八章）。

### 决策 6：SDK 选 `AWSSDK.S3`

MinIO 完整兼容 S3 API。用 `AWSSDK.S3` 而非 MinIO 专用 SDK，可在将来切换到阿里云 OSS / 腾讯云 COS 时**只改配置不改代码**。

### 决策 7：单桶 + 前缀隔离

单个 private 桶 `bms-store`，通过 key 前缀做租户/门店隔离。不采用「每租户一桶」——桶数量随租户线性增长，运维成本高，且 MinIO 桶级策略管理复杂。

### 决策 8：删除采用「先删库、后删对象、失败兜底」

数据库事务与 MinIO 不在同一事务内，必须定序：

1. 先删数据库记录（事务提交）
2. 再尽力删除 MinIO 对象；失败**仅记日志，不回滚、不抛异常**
3. 残留对象由孤儿清理任务兜底（第四阶段）

**不可反序**：若先删对象而数据库事务回滚，会造成记录存在但图片永久丢失。宁可留孤儿文件，不可丢数据。

## 四、变更清单

### 4.1 基础设施 —— MinIO 以 Windows 服务方式部署（不用 Docker）

**已部署完成**，操作手册见 [MinIO部署说明](部署文档/MinIO部署说明.md)。此处仅记录形态与决策，不重复步骤。

**部署形态**：MinIO 以 nssm 包装成 **Windows 服务**常驻，开机自启、崩溃自动重启——与本机 PostgreSQL 同一个模型。**开发环境与生产环境使用同一套部署流程**（同一个 `deploy\注册MinIO服务.bat`），差异只在数据目录、密码强度、`PublicEndpoint` 等取值上。

> **为什么开发环境也注册服务**：若开发环境用手工/脚本启动、生产环境才注册服务，那么注册凭据这一步在开发环境从来没被执行过，第一次执行是在服务器上——这正是最容易出事的做法。统一流程后，开发环境每天都在验证生产环境的部署方式。

| 事项 | 取值 / 做法 |
|---|---|
| 可执行文件 | `D:\软件\MinIO\` 下的 `minio.exe` / `mc.exe` / `nssm.exe`，**仓库目录之外**（140MB+ 二进制不进 Git 历史） |
| 数据目录 | 由服务的 `AppParameters` 指定，开发环境为 `D:\minio-data`；生产环境必须放独立数据盘 |
| 凭据 | 由 nssm 的 `AppEnvironmentExtra` 注入进程环境（`MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`），开发环境为 `mes` / `mes@2026` |
| 端口 | 9000（S3 API，Store 服务与**浏览器**都要访问）、9001（Web 控制台，仅人工使用）。与现有端口（5000–5031、5432）均不冲突 |
| 运维脚本 | `deploy\注册MinIO服务.bat`、`deploy\卸载MinIO服务.bat`（一次性，需管理员权限） |

> **凭据用 nssm 注入而不是 `setx`**：服务默认以 `SYSTEM` 账户运行，而 `setx` 写的是当前用户的环境变量，`SYSTEM` 读不到——此时 MinIO 会**静默退回默认凭据 `minioadmin`，不报任何错**，服务状态照样 RUNNING、业务功能照样正常。部署说明步骤 3.2 用一条反向校验（默认凭据必须登录失败）专门拦这个问题。

**不改动的部分**：本机未使用 Docker，`deploy/` 下的 compose 与 `start-infrastructure.cmd` 本次不改动。MinIO 是开机自启服务，`runLocal.bat` **不含** MinIO 步骤，也因此没有「MinIO 必须先于微服务启动」的顺序要求。

**桶的创建**：不依赖手工操作。`AddObjectStorage()` 在服务启动时会检查并自动创建 `bms-store` 桶（见 4.3），桶默认即为 private，符合安全设计要求。

> **验证手段以 `mc`（MinIO Client）为准，不依赖 Web 控制台。** MinIO 社区版的内置控制台在近期版本中功能有所精简，能否浏览对象与版本相关。`mc` 是官方命令行工具，行为稳定：
> ```cmd
> mc alias set local http://localhost:9000 mes mes@2026
> mc ls local/bms-store --recursive
> ```
> 本方案第七章的各阶段验证均可用 `mc ls` 完成，无需控制台。

**数据安全**：单机单目录部署无任何冗余，数据目录所在磁盘损坏即丢全部图片。必须把该目录纳入备份策略——这是本次部署方式下最需要落实的一条（见第八章）。生产环境的数据目录不要放系统盘。

### 4.2 配置

**`src/Services/Store/Bms.Store.Api/appsettings.json`** —— 新增顶层节。凡接入 `BuildingBlocks.Storage` 的服务都需配置本节，本次只改 Store：

```json
"ObjectStorage": {
  "Endpoint": "http://localhost:9000",
  "PublicEndpoint": "http://localhost:9000",
  "AccessKey": "mes",
  "SecretKey": "mes@2026",
  "BucketName": "bms-store",
  "PresignExpireMinutes": 30,
  "MaxFileSizeBytes": 10485760,
  "AllowedExtensions": [ ".jpg", ".jpeg", ".png", ".webp" ],
  "AllowedBizTypes": [ "customer-photo", "product-image", "technician-avatar", "purchase-voucher" ]
}
```

> **`AllowedBizTypes` 放配置而非硬编码在类库里**：`bizType` 是业务概念，类库不该认识它。放进配置后，System 将来接入只需在自己的 appsettings 里写 `[ "system-avatar" ]`，无需改动或扩展类库代码。同理 `AllowedExtensions` 也上移到配置——魔术字节校验规则是技术性的，留在类库内。

> **`PublicEndpoint` 是必需的，不是冗余配置。** `Endpoint` 是 Store API 访问 MinIO 用的地址，`PublicEndpoint` 是写进预签名 URL、交给**浏览器**访问的地址，必须是浏览器可达的。本机部署且开发机自用时两者相同；一旦服务部署到服务器而浏览器在别的机器上，`PublicEndpoint` 就必须换成服务器的实际域名或 IP（如 `http://192.168.1.10:9000`）。两者混用是此类改造最常见的故障点。

> **`AccessKey` / `SecretKey` 必须与 MinIO 服务里 `AppEnvironmentExtra` 配的一致**，改一处就要改两处。开发环境明文写在 appsettings，随项目现有惯例（数据库密码亦如此）。**生产环境改为环境变量注入**（`ObjectStorage__AccessKey`，`setx /M`），具体实现见 [MinIO部署说明](部署文档/MinIO部署说明.md) 第五章。

`.csproj` 与同级类库同构：`net8.0` + `Nullable enable` + `ImplicitUsings enable`，`ProjectReference` 引用 `Bms.BuildingBlocks.Core`（复用 `ISnowflakeIdGenerator` 生成文件名），`PackageReference` 引入 `AWSSDK.S3`。

**校验器与 key 拼装标记为 `internal`**，服务侧拿不到、也就不可能各自组装一套流程。对外只有 `IFileUploadService` 一个入口：

```csharp
public interface IFileUploadService
{
    /// <summary>上传单个文件。校验失败不抛异常，通过返回值的 Succeeded/ErrorMessage 表达</summary>
    Task<FileUploadOutcome> UploadAsync(FileUploadRequest request, CancellationToken ct = default);
}
```

**预签名与删除接口把授权范围做成必填参数**，前缀校验因此无法被漏写：

```csharp
public interface IFileStorageService
{
    /// <summary>单个 key 预签名。key 前缀与 scope 不匹配时返回 null</summary>
    string? GetPresignedUrl(string objectKey, PresignScope scope);

    /// <summary>批量预签名。列表接口用，避免各服务自行写循环与判空</summary>
    IReadOnlyDictionary<string, string> GetPresignedUrls(IEnumerable<string> objectKeys, PresignScope scope);

    /// <summary>删除对象。前缀不匹配则跳过；失败仅记日志不抛异常（见决策 8）</summary>
    Task DeleteAsync(string objectKey, PresignScope scope, CancellationToken ct = default);
    Task DeleteManyAsync(IEnumerable<string> objectKeys, PresignScope scope, CancellationToken ct = default);
}
```

**外链并存的两段逻辑也在类库内，不留给服务各写一遍**（决策 5）。读取侧用 `IFileReferenceResolver`，服务侧因此不出现 `StartsWith("http")` 这种判断；写入侧用 `IExternalUrlValidator`，避免某个服务漏做协议白名单而开出 XSS 口子：

```csharp
public interface IFileReferenceResolver
{
    /// <summary>
    /// 把库中保存的照片来源批量解析为可展示 URL：
    /// http/https 外链原样透传，其余按 objectKey 现场签名（前缀越权者被丢弃）
    /// </summary>
    IReadOnlyDictionary<string, string> Resolve(IEnumerable<string> references, PresignScope scope);
}

public interface IExternalUrlValidator
{
    /// <summary>判断是否为允许入库的外部图片直链（仅 http/https）</summary>
    bool IsAllowedExternalUrl(string value);

    /// <summary>判断该来源值是否为外链（用于写入侧决定是否走协议校验）</summary>
    bool LooksLikeExternalUrl(string value);
}
```

**抽象层不依赖 ASP.NET Core**：`FileUploadRequest` 收 `Stream` + `fileName` + `contentType` + `length`，而非 `IFormFile`。这样类库无需引用 `Microsoft.AspNetCore.Http`，Application 层也不会被动引入 Web 依赖。

> **不新建 `BuildingBlocks.Storage.Web` 项目做 `IFormFile` 适配**：适配代码是 5 行纯字段搬运（见 4.4 代码），为它单开一个项目、多一层依赖不划算。若将来出现第三个服务且搬运代码开始分化（例如需要多文件、需要进度回调），再抽。

| 文件 | 职责 |
|---|---|
| `Bms.Store.Api/Controllers/FilesController.cs` | 上传端点。**只做数据搬运与响应包装，无任何判断逻辑** |

不再单独定义 `FileUploadResultDto`——直接复用类库的 `FileUploadResult`，避免只为转发而存在的一层映射。

**`FilesController`** 遵循现有 Controller 风格（`[ApiController]` + `[Route("api/store/[controller]")]` + `[Authorize]` + 返回 `ApiResponseDto<T>`）。全部内容如下，这也是其他服务接入时唯一需要重写的部分：

```csharp
[HttpPost]
public async Task<ApiResponseDto<FileUploadResult>> Upload([FromForm] IFormFile file, [FromForm] string bizType)
{
    await using var stream = file.OpenReadStream();
    var outcome = await _uploadService.UploadAsync(new FileUploadRequest
    {
        Content = stream,
        FileName = file.FileName,
        ContentType = file.ContentType,
        Length = file.Length,
        BizType = bizType,
        TenantId = _currentUser.TenantId ?? 0,
        StoreId = _currentUser.StoreId
    });

    return outcome.Succeeded
        ? ApiResponseDto<FileUploadResult>.Ok(outcome.Result)
        : ApiResponseDto<FileUploadResult>.Fail(outcome.ErrorMessage!);
}
```

服务端校验全部在类库的 `IFileUploadService` 内完成，顺序如下，任一失败即返回 `Succeeded = false` 与对应 `ErrorMessage`：

1. 文件非空、大小 ≤ `MaxFileSizeBytes`
2. `bizType` 在 `AllowedBizTypes` 配置白名单内
3. 扩展名在 `AllowedExtensions` 配置白名单内
4. `ContentType` 以 `image/` 开头
5. **魔术字节校验**：JPEG `FF D8 FF`、PNG `89 50 4E 47`、WebP `RIFF....WEBP`——防止把可执行文件改扩展名上传

> **错误表达遵循项目既有约定**：HTTP 状态码仍为 200，错误通过响应体 `code = 400` + `message` 传达（`ApiResponseDto.Fail(message, 400)`），前端 `request()` 判的正是响应体的 `code`。校验失败**不抛异常**——项目中既没有统一业务异常类型，也没有全局异常处理中间件，抛异常会退化成 500。这也是 `FileUploadOutcome` 用返回值而非异常表达失败的原因。

objectKey 生成规则（不使用原始文件名，避免路径穿越与中文编码问题）：

```
{tenantId}/{storeId}/{bizType}/{yyyyMM}/{snowflakeId}{ext}
例：1001/2001/customer-photo/202608/723412345678901234.jpg
```

`tenantId` / `storeId` 取自 `ICurrentUser`，**不接受前端传入**。

无门店维度的服务（如 System 将来做用户头像）传入 `StoreId = null`，key 退化为 `{tenantId}/{bizType}/{yyyyMM}/{snowflakeId}{ext}`。

## 六、安全设计

| 风险 | 措施 |
|---|---|
| 越权访问其他门店照片 | objectKey 前缀含 `tenantId/storeId`，取自 `ICurrentUser` 而非前端；预签名与删除接口强制传 `PresignScope`，key 前缀与之不匹配即拒签/跳过——该校验在类库内实现，服务侧无法绕过或漏写 |
| 桶被公网直接遍历 | 桶设为 private，不开放匿名读；所有访问必须持有效签名 |
| 预签名 URL 泄露 | 有效期限制为 30 分钟 |
| 上传恶意文件 | 扩展名白名单 + ContentType 校验 + 魔术字节校验；文件名不采用客户端原名，用雪花 ID 重命名 |
| 路径穿越 | key 完全由服务端拼装，`bizType` 需命中 `AllowedBizTypes` 配置白名单，不拼接任何未经校验的客户端字符串 |
| 超大文件耗尽资源 | 单文件 ≤10MB；需同步调整 Kestrel `MaxRequestBodySize`（默认 30MB）与网关转发限制 |
| 密钥泄露 | 生产环境通过环境变量注入，不提交到仓库 |
| 外链被写成 `javascript:` / `data:` 等伪协议造成 XSS | `PhotoSource` 允许存外部直链（决策 5），故必须校验协议：仅接受 `http://` / `https://` 开头。校验由类库的 `IExternalUrlValidator` 统一实现，各服务不得自行手写判断（漏一处即是一个 XSS 入口）。前端的同类提示仅为体验优化，不构成安全边界 |

请求体上限需确认三处：Store API 的 Kestrel、Gateway 的 Kestrel、Ocelot 转发。当前上传为**单张图片逐个上传**（非 12 张打包），单请求 ≤10MB，在默认 30MB 限制内，预计无需调整——但需实测确认。

#### 孤儿清理实现要点

`Bms.Store.Api/BackgroundServices/OrphanObjectCleanupService.cs`，每日 04:00 执行（避开 01:00–03:00 的既有定时任务）。判定与删除逻辑在类库 `IOrphanObjectCleaner` 内，服务侧只提供「清理范围」与「查库回调」。

删对象不可逆，故设三重防护，任一失效都不会误删：

| 防护 | 作用 | 失效方向 |
|---|---|---|
| **先列举对象、后查库引用** | 列举之后才建立的引用必然出现在随后查出的集合中 | 顺序反了会误删两个动作之间新保存的对象，因此该定序封装在类库内、由回调参数强制，调用方无从写反 |
| **保留期 24 小时** | 保护「已上传、用户仍停留在编辑界面尚未提交」的对象 | — |
| **bizType 白名单** | 桶为多服务共用，只清理引用已被统计的业务类型 | 漏登记 → 不回收（安全）；错登记 → 误删（危险） |

配套的两处设计：

- 列举全桶与「无 scope 删除」做成 `MinioFileStorageService` 的方法，**故意不挂到 `IFileStorageService` 接口上**。清理是跨租户运维操作，没有单一 `PresignScope` 可传；若把这两个能力暴露给业务代码，决策 1 建立的「前缀越权校验不可能被漏写」保证即失效。
- 引用查询使用 `IgnoreQueryFilters()`，确保取到全量引用而不依赖运行时租户上下文——漏掉一条引用就等于误删一张在用图片。

> **后续接入新图片字段时必须同步两处**：`CleanupBizTypes` 常量与 `LoadReferencedKeysAsync` 的查询。两者在同一文件内相邻定义，就是为了让漏改难以发生。只改前者会误删，只改后者不回收。

**验证结果**（造 7 个对象的判定矩阵，用 `mc` 核对）：4 个有引用对象保留、`product-image`（未登记类型）保留、格式不符的 key 保留、唯一真孤儿被删除；保留期改回 24 小时后重造孤儿再跑，删除数为 0，确认保留期生效。

## 八、已知取舍与技术债

| 项 | 说明 | 计划 |
|---|---|---|
| 孤儿对象 | 用户上传后未保存，或删对象失败，会残留 MinIO 对象 | **已由阶段 4 的 `OrphanObjectCleanupService` 兜底**（每日 04:00，保留期 24 小时）。仅覆盖已登记 bizType，外链与未接入字段的对象不在统计范围内 |
| 图片上行流量经 Store API | 换取服务端校验能力 | 出现带宽瓶颈再改前端直传 |
| 预签名 URL 可在有效期内传播 | 30 分钟时效控制风险 | 若合规要求提高，改为 API 代理读取 |
| MinIO 单机部署无冗余 | 单进程 + 单目录，数据盘损坏即丢全部图片。已注册为 Windows 服务，具备开机自启与崩溃自动重启，但**冗余与自愈是两件事**——服务能拉起进程，救不回损坏的数据 | **必须**将数据目录纳入备份策略；对可用性要求提高时改多节点纠删码模式 |
| 无缩略图 | 列表仍加载原图（但已可缓存、可并发） | 阶段 4 |
| MinIO 凭据需在各接入服务的 appsettings 中重复配置 | 共享类库方案的固有代价；换取的是无跨服务往返 | 与数据库密码同等对待，生产统一由环境变量注入 |
| 各服务需各自开一个 `FilesController` | 约 15 行，且只含数据搬运与响应包装（4.4 已给出全部内容）。根因是 `ApiResponseDto<T>` 在各服务 Application 层各有一份独立定义，无法抽公共基类 | 若统一 `ApiResponseDto` 或引入 `AddApplicationPart`，可进一步消除；两者都超出本次改造范围 |
| 未做 `IFormFile` → `FileUploadRequest` 的适配层 | 适配是 5 行纯字段搬运，为它单开 `Storage.Web` 项目不划算 | 若第三个服务接入时搬运代码开始分化（多文件、进度回调），再抽 |
| 外链图片不受本系统控制 | 决策 5 保留「输入图片URL」入口的既知代价：图床可能失效、可能开防盗链、图片内容可能被悄悄替换；这些对象也**无法纳入备份，也不会被阶段 4 的孤儿清理任务统计** | 接受。该入口的定位是应急补录，主路径是本地上传；若日后发现外链占比升高或频繁失效，再改为「后端拉取后转存 MinIO」 |
