# 库存盘点批次化改造设计

> 创建日期: 2026-07-31
>
> 背景: 现有库存盘点功能（`InventoryCheck` / `InventoryCheckAppService` / `views/store/product/check`）只针对商品整体数量做差异调整，未纳入批次管理体系。这导致三方面问题：(1) 盘亏只扣 `Inventory` 汇总表不扣 `InventoryBatch`，汇总表与批次表长期对不上；(2) 盘盈只加汇总表不加批次，新增库存无批次号、无效期、无成本来源；(3) 差异金额按 `Product.CostPrice` 临时计算，未持久化且与真实采购成本脱节。本期将盘点纳入批次体系，并修正差异金额算法。

---

## 一、问题清单

### 1.1 盘点未联动批次表

**现状**（`InventoryCheckAppService.SubmitCheckAsync:229-276`）：

- 差异调整只修改 `Inventory.Quantity` 汇总表
- `InventoryBatch` 表完全不动
- 写 `InventoryLog` 时 `BatchNo` / `UnitPrice` / `ExpirationDate` 全部留空

**后果**：

| 场景 | 后果 |
|------|------|
| 盘亏 | `Inventory.Quantity` 减少，但 `InventoryBatch.Quantity` 不变，`Σ 批次.Quantity` 与汇总表长期偏差 |
| 后续出库 FIFO | 出库按 `InventoryBatch` 扣减（`InventoryAppService.DeductByBatchAsync:267`），可能出现"汇总表有库存但批次已用完"的死锁场景 |
| 盘盈 | `Inventory.Quantity` 增加，但无对应 `InventoryBatch` 记录，新增库存无批次号、无效期、无成本单价 |
| 后续出库找批次 | 盘盈的库存永远不在 `InventoryBatch` 表里，FIFO 永远扣不到它，但它算在 `Inventory.Quantity` 里 |

### 1.2 差异金额算法不合理

**现状**（`InventoryCheckAppService.GetPagedListAsync:91`）：

```csharp
DiffAmount = x.p.CostPrice.HasValue ? x.c.DiffQuantity * x.p.CostPrice.Value : (decimal?)null
```

- 查询时用 `Product.CostPrice`（当前成本价快照）临时计算，**不持久化**
- 后续商品调价后，历史盘点记录的差异金额会跟着变

**后果**：

| 场景 | 问题 | 例子 |
|------|------|------|
| 盘亏 | 损失的是已入库批次的实际采购库存，按当前成本价算会因近期调价而高估或低估损失 | 1月以 5 元采购 100 件，3月调价 `CostPrice=8`，4月盘亏 10 件：当前算法 80 元，真实损失 50 元 |
| 盘盈 | 没有真实采购来源，按当前成本价只是估值，且未与新增批次的 `UnitPrice` 关联 | 盘盈 10 件按当前 `CostPrice=8` 计 80 元，但实际可能是供应商赠品（真实成本 0） |
| 历史记录 | `Product.CostPrice` 调整后，历史盘点金额跟着变，无法还原当时损失 | 4月盘亏按当时 `CostPrice=8` 计 80 元，5月调价到 10 元，列表显示变成 100 元 |

### 1.3 数据一致性总览

盘点是当前唯一一个绕过批次体系的库存调整入口：

| 入口 | 是否联动批次 | 是否写 `InventoryLog.BatchNo` |
|------|--------------|-------------------------------|
| 入库（`/inbound`） | ✅ 新建批次 | ✅ |
| 出库（`/outbound`） | ✅ 扣减批次 | ✅ |
| 采购退货 | ✅ `DeductByBatchAsync` | ✅ |
| 调拨 | ✅ 双店批次联动 | ✅ |
| **盘点** | ❌ 只改汇总表 | ❌ 留空 |

## 二、设计目标

1. **盘亏**：操作员指定批次扣减（不知道是哪批少时允许 FIFO 兜底），扣减对应 `InventoryBatch`，差异金额按批次实际 `UnitPrice` 累加
2. **盘盈**：操作员手动录入批次属性（`UnitPrice` 默认取 `Product.CostPrice` 可编辑、效期可选、原因必填），系统新建盘盈批次记录
3. **差异金额持久化**：提交时由后端按真实批次单价计算并写入 `InventoryCheck.DiffAmount`，不再查询时临时算
4. **流水完整**：`InventoryLog` 补全 `BatchNo` / `UnitPrice` / `ExpirationDate`，与入库/出库流水一致
5. **保留现有状态机**：草稿 -> 已完成 / 已取消 的闭环不动，仅在提交阶段扩展批次信息

## 三、数据模型变更

### 3.1 `InventoryCheck` 实体新增字段

```csharp
/// <summary>
/// 批次号（盘亏时取首批扣减批次号；盘盈时取新建盘盈批次号；无差异时为空）
/// </summary>
public string? BatchNo { get; set; }

/// <summary>
/// 单价（盘亏时取首批扣减批次的 UnitPrice；盘盈时取录入的估值单价）
/// 用于 DiffAmount 计算，与 InventoryLog.UnitPrice 一致
/// </summary>
public decimal? UnitPrice { get; set; }

/// <summary>
/// 过期日期（盘亏时取首批扣减批次的过期日期；盘盈时取录入的过期日期）
/// 与 InventoryLog.ExpirationDate 一致
/// </summary>
public DateTime? ExpirationDate { get; set; }

/// <summary>
/// 差异金额（提交时持久化，按真实批次单价计算）
/// 盘亏 = Σ(扣减数量 × 批次 UnitPrice)，负数
/// 盘盈 = 盘盈数量 × 录入 UnitPrice，正数
/// 无差异时为 null
/// </summary>
public decimal? DiffAmount { get; set; }
```

### 3.2 数据库 migration

新增列（全部 nullable，向后兼容）：

- `InventoryChecks.BatchNo` (nvarchar, nullable)
- `InventoryChecks.UnitPrice` (decimal(18,2), nullable)
- `InventoryChecks.ExpirationDate` (datetime2, nullable)
- `InventoryChecks.DiffAmount` (decimal(18,2), nullable)

历史数据无需回填：草稿/已取消记录 `DiffAmount` 保持 null；已完成记录 `DiffAmount` 为 null 时前端列表显示"-"（与现状一致）。

### 3.3 不动的内容

- `InventoryCheck` 现有字段（`ProductId` / `BeforeQuantity` / `ActualQuantity` / `DiffQuantity` / `CheckTime` / `OperatorId` / `OperatorName` / `Status` / `Remark`）不删不改
- 不新增批次粒度的盘点单子表（避免过度设计，盘点本身仍是商品粒度的，批次信息只在提交时记录快照）
- `InventoryBatch` / `Inventory` / `InventoryLog` 表结构不变

## 四、DTO 设计

### 4.1 `SubmitCheckDto` 扩展（核心改造点）

```csharp
public class SubmitCheckDto
{
    public long Id { get; set; }

    /// <summary>实际盘点数量</summary>
    public decimal ActualQuantity { get; set; }

    /// <summary>
    /// 盘亏批次扣减明细（差异为负时使用）
    /// 为空 -> 后端按 FIFO 兜底扣减
    /// 非空 -> 按操作员指定批次扣减，校验数量匹配
    /// </summary>
    public List<BatchDeductItem>? DeductBatches { get; set; }

    /// <summary>盘盈批次号（差异为正时使用，留空后端生成 PY-时间戳）</summary>
    public string? GainBatchNo { get; set; }

    /// <summary>盘盈批次单价（差异为正时使用，留空取 Product.CostPrice）</summary>
    public decimal? GainUnitPrice { get; set; }

    /// <summary>盘盈批次生产日期（差异为正时使用，可选）</summary>
    public DateTime? GainProductionDate { get; set; }

    /// <summary>盘盈批次过期日期（差异为正时使用，可选）</summary>
    public DateTime? GainExpirationDate { get; set; }

    /// <summary>盘盈原因（差异为正时必填，强制操作员说明来源）</summary>
    public string? GainRemark { get; set; }

    /// <summary>盘点单备注（沿用现有字段）</summary>
    public string? Remark { get; set; }
}

public class BatchDeductItem
{
    /// <summary>批次ID（InventoryBatch.Id）</summary>
    public long BatchId { get; set; }

    /// <summary>该批次扣减数量，>0</summary>
    public decimal Quantity { get; set; }
}
```

**字段流向说明**：

| 差异方向 | 使用字段 | 忽略字段 |
|----------|----------|----------|
| `DiffQuantity < 0`（盘亏） | `DeductBatches` | `GainBatchNo` / `GainUnitPrice` / `GainProductionDate` / `GainExpirationDate` / `GainRemark` |
| `DiffQuantity > 0`（盘盈） | `GainBatchNo` / `GainUnitPrice` / `GainProductionDate` / `GainExpirationDate` / `GainRemark` | `DeductBatches` |
| `DiffQuantity == 0`（无差异） | 无 | 全部忽略 |

### 4.2 `InventoryCheckCreateDto` 不动

保留现有字段（`ProductId` / `BeforeQuantity` / `ActualQuantity` / `DiffQuantity` / `CheckTime` / `Remark`）。批次信息只在 `SubmitCheckDto` 传入，草稿阶段不需要。

### 4.3 `InventoryCheckDto` 输出调整

`DiffAmount` / `UnitCost` 的填充逻辑调整：

| 字段 | 现状 | 改造后 |
|------|------|--------|
| `DiffAmount` | 查询时用 `Product.CostPrice` 临时算 | 改为读 `InventoryCheck.DiffAmount` 持久化字段 |
| `UnitCost` | 读 `Product.CostPrice` | 改为读 `InventoryCheck.UnitPrice`（盘亏时是批次实际价，盘盈时是录入估值） |
| `BatchNo` | 无 | 新增，读 `InventoryCheck.BatchNo` |
| `ExpirationDate` | 无 | 新增，读 `InventoryCheck.ExpirationDate` |

### 4.4 FluentValidation 验证规则

新增 `SubmitCheckDtoValidator`：

- `ActualQuantity` >= 0
- `DeductBatches`（若非空）：
  - 每个 `BatchId` > 0
  - 每个 `Quantity` > 0
  - 不允许重复 `BatchId`
- `GainUnitPrice`（若非空）>= 0
- `GainExpirationDate`（若非空）> `GainProductionDate`（若同时填）
- `GainRemark`：当 `DiffQuantity > 0` 时必填且非空白（业务规则验证，需在服务层判断差异方向后校验，因 Validator 无法访问 `BeforeQuantity`）

## 五、后端服务逻辑

### 5.1 `SubmitCheckAsync` 改造

事务内执行（沿用现有事务边界）：

1. **加载盘点单**，校验状态为草稿
2. **计算差异**：`diffQuantity = ActualQuantity - BeforeQuantity`
3. **按差异方向分支**：

#### 分支 A：盘亏（diffQuantity < 0）

扣减量 `deductQty = -diffQuantity`

- **若 `DeductBatches` 非空**（指定批次模式）：
  1. 校验所有 `BatchId` 属于当前门店+商品且 `Status=1` 且 `Quantity > 0`
  2. 校验 `Σ DeductBatches.Quantity == deductQty`（不允许部分扣减，必须精确匹配）
  3. 按操作员指定数量扣减对应批次，扣完置 `Status=2`
  4. `DiffAmount = -Σ(item.Quantity × batch.UnitPrice)`
  5. `UnitPrice` / `BatchNo` / `ExpirationDate` 取首批次（与 `DeductByBatchAsync` 一致，用于写流水）

- **若 `DeductBatches` 为空**（FIFO 兜底模式）：
  1. 按 `CreatedTime` 升序取所有在库批次（复用 `DeductByBatchAsync:267-274` 的查询逻辑）
  2. 校验总库存充足
  3. 按 FIFO 扣减各批次
  4. `DiffAmount = -Σ(扣减数量 × 批次 UnitPrice)`
  5. `UnitPrice` / `BatchNo` / `ExpirationDate` 取首批次

- **写 `InventoryLog`**（一条汇总流水，与 `DeductByBatchAsync` 一致）：
  - `Type = 2`（出库）
  - `SourceType = CheckAdjustment`（3）
  - `Quantity = diffQuantity`（负数）
  - `BatchNo` / `UnitPrice` / `ExpirationDate` 取首批次
  - `BeforeQuantity` / `AfterQuantity` 取 `Inventory` 汇总表前后值

- **更新 `Inventory` 汇总表**：`Quantity += diffQuantity`

#### 分支 B：盘盈（diffQuantity > 0）

1. **校验 `GainRemark` 非空**（业务规则）
2. **解析 `UnitPrice`**：`GainUnitPrice ?? Product.CostPrice ?? 0`
3. **生成 `BatchNo`**：`GainBatchNo` 若为空，后端生成 `PY-yyyyMMddHHmmss`
4. **新建 `InventoryBatch`**（始终新建，不累加不覆盖，与入库策略一致）：
   - `ProductId` / `Quantity = diffQuantity` / `UnitPrice`
   - `BatchNo` / `ProductionDate` / `ExpirationDate`（来自 DTO）
   - `PurchaseDate = DateTime.Today`（与入库一致）
   - `Status = 1`（在库）
5. **更新 `Inventory` 汇总表**：`Quantity += diffQuantity`（不存在则新建）
6. **写 `InventoryLog`**：
   - `Type = 1`（入库）
   - `SourceType = CheckAdjustment`（3）
   - `Quantity = diffQuantity`（正数）
   - `BatchNo` / `UnitPrice` / `ExpirationDate` 取新建批次
7. **`DiffAmount = diffQuantity × UnitPrice`**（正数）

#### 分支 C：无差异（diffQuantity == 0）

- 不调整库存，不写批次，不写流水
- `DiffAmount = null` / `BatchNo = null` / `UnitPrice = null` / `ExpirationDate = null`

4. **更新盘点单**：写入 `DiffQuantity` / `DiffAmount` / `BatchNo` / `UnitPrice` / `ExpirationDate` / `Status = Completed` / `CheckTime` / `UpdatedTime`
5. **保存事务**
6. **盘亏后触发低库存预警**（沿用现有逻辑 `:282-292`）

### 5.2 `GetPagedListAsync` 改造

`DiffAmount` / `UnitCost` 改为读 `InventoryCheck` 持久化字段，不再联表 `Product.CostPrice` 临时算：

```csharp
// 现状（删除）
DiffAmount = x.p.CostPrice.HasValue ? x.c.DiffQuantity * x.p.CostPrice.Value : (decimal?)null

// 改造后
DiffAmount = x.c.DiffAmount,
UnitCost = x.c.UnitPrice,
BatchNo = x.c.BatchNo,
ExpirationDate = x.c.ExpirationDate
```

`Product` 联表保留（仍需 `ProductName` / `ProductCode`），但 `CostPrice` 不再用于计算差异金额。

### 5.4 与 `DeductByBatchAsync` 的关系

`InventoryAppService.DeductByBatchAsync` 是为采购退货等场景设计的"指定批次优先，否则 FIFO"扣减方法，盘点盘亏**不直接复用**，原因：

| 维度 | `DeductByBatchAsync` | 盘点盘亏 |
|------|----------------------|----------|
| 调用方 | 采购退货等已在外层事务 | 自己开启事务 |
| 差异金额 | 不计算 | 需持久化 `DiffAmount` |
| 字段持久化 | 只写 `InventoryLog` | 还要写 `InventoryCheck` |
| 多批次流水 | 只写一条汇总（首批次） | 同样写一条汇总，但需计算 `DiffAmount` 累加 |

**取舍**：在 `InventoryCheckAppService` 内部实现盘亏扣减逻辑，参考 `DeductByBatchAsync` 的查询和扣减模式但不直接调用。若后续需统一，可抽取共享的批次扣减内部方法，本期不做（避免过度设计）。

## 七、错误处理与边界场景

### 7.1 后端错误处理

| 场景 | HTTP | 错误信息 |
|------|------|----------|
| 未登录 / 无门店上下文 | 401 | "无法确定当前租户或门店" |
| 盘点单不存在 | 404 | "库存盘点记录不存在" |
| 盘点单非草稿状态 | 400 | "仅草稿状态的盘点单可提交（当前状态：{Status}）" |
| 盘亏指定批次模式：`Σ DeductBatches.Quantity ≠ deductQty` | 400 | "指定批次扣减数量合计与差异数量不匹配" |
| 盘亏指定批次：`BatchId` 不存在或不属于当前门店+商品 | 400 | "批次 {BatchId} 不存在或已用完" |
| 盘亏 FIFO 兜底：总库存不足 | 400 | "库存不足：需要 {X}，可用 {Y}" |
| 盘盈：`GainRemark` 为空 | 400 | "盘盈必须填写原因" |
| 盘盈：`GainExpirationDate ≤ GainProductionDate` | 400 | "过期日期必须晚于生产日期" |
| 数据库写入失败 | 500 | 事务回滚，抛异常 |

### 7.2 事务边界

`SubmitCheckAsync` 全程在 `IDbContextTransaction` 内执行。`InventoryCheck` / `InventoryBatch` / `Inventory` / `InventoryLog` 四张表写入要么全部成功要么全部回滚。沿用现有事务边界（`:229-300`），仅扩展事务内操作。

### 7.3 并发处理

沿用现有简单方案：事务内串行写入，依赖数据库事务隔离级别。`Inventory` 表不加乐观锁（与入库/出库一致）。若并发冲突由 `DbUpdateException` 捕获返回 500，前端提示重试。

### 7.4 边界场景

| 场景 | 处理 |
|------|------|
| 盘亏商品无任何在库批次（`InventoryBatch` 为空） | 返回 400 "无可用库存批次"（理论上 `Inventory.Quantity` 也应为 0，不该出现盘亏） |
| 盘盈商品 `Product.CostPrice` 为 null 且 `GainUnitPrice` 未填 | `UnitPrice` 取 0，`DiffAmount = 0`，记录但不算损失 |
| 同一商品多次盘亏同一批次 | 各自独立扣减，不冲突（每次扣减都更新 `InventoryBatch.Quantity`） |
| 盘亏指定批次模式：某批次 `Quantity` 不足扣减 | 返回 400 "批次 {BatchNo} 库存不足" |
| 盘盈后该商品立即出库 | FIFO 按 `CreatedTime` 排序，盘盈批次作为最新批次最后出库（合理：盘盈库存通常是"未知来源"，应优先消耗已知批次） |

## 九、待确认的设计权衡点

以下三个问题在实施前需要确认，影响代码细节：

### 9.1 盘亏是否允许 FIFO 兜底

**当前设计**：允许（`DeductBatches` 为空时走 FIFO）

**反对意见**：盘点场景需要精确知道是哪批少了，操作员应强制手选批次。

**建议**：保留 FIFO 兜底。理由：(1) 实际盘点时操作员只数总数，未必知道批次；(2) 与出库 `DeductByBatchAsync` 行为一致；(3) 强制手选会增加操作负担导致盘点流程受阻。若需强制，前端隐藏"留空走 FIFO"提示并要求必填即可，后端无需改动。

### 9.2 盘盈批次过期日期是否对有保质期商品强制必填

**当前设计**：可选

**反对意见**：有保质期的商品（食品/护肤品/药品）盘盈后若无过期日期，效期预警永远抓不到，合规风险。

**建议**：本期不强制。理由：(1) `Product` 表当前无"是否有保质期"标识字段，无法程序化判断；(2) 盘盈的库存可能确实是"找不到来源"，操作员未必知道效期；(3) 强制会导致流程卡死。后续若加 `Product.HasShelfLife` 字段，再在 Validator 里加条件必填规则。

### 9.3 跨批次盘亏的 `InventoryLog` 流水粒度

**当前设计**：写一条汇总流水（首批次 `BatchNo` / `UnitPrice` / `ExpirationDate`），与 `DeductByBatchAsync` 一致

**反对意见**：跨批次扣减时，单条流水的 `UnitPrice` 是首批次价，成本追溯不准确。

**建议**：保留单条汇总流水。理由：(1) 与现有出库/采购退货流水一致；(2) `InventoryCheck.DiffAmount` 已持久化真实累加值，成本追溯以盘点单为准；(3) 若改为多条流水，会让"一条盘点单对应多条流水"破坏现有 1:1 假设。后续若需多批次独立成本核算，可在 `InventoryCheck` 增加子表，本期不做。
