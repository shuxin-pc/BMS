# 入库功能设计

> 创建日期: 2026-07-28
>
> 背景: 入库管理页面 (`src/views/store/product/inbound/index.vue`) 当前通过 `src/api/inventory-ops/index.ts` 中的 Mock 数据实现，未对接后端。后端 `InventoryLogsController` / `InventoriesController` 已存在通用 CRUD 端点，但缺少语义化的入库端点、缺少自动库存维护逻辑、缺少前端表格需要的显示字段。本期实现入库功能完整闭环。

---

## 一、架构与端点

### 新增端点

`POST /api/store/InventoryLogs/inbound`（语义化入库，与现有通用 `POST /InventoryLogs` 并存，互不干扰）

### 请求体 `InboundCreateDto`

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `ProductId` | long | 是 | 商品ID |
| `SourceType` | int | 是 | 入库来源，取值 {1=采购, 2=退货, 3=盘点, 4=调拨, 6=其他}；销售出库类 {0, 8} 由后端拒绝 |
| `SupplierId` | long? | 否 | `SourceType=1` 时必填，其他来源忽略 |
| `Quantity` | decimal | 是 | 入库数量，>0 |
| `UnitPrice` | decimal? | 否 | 单价 |
| `BatchNo` | string? | 否 | 批次号（仅用于内部追溯，不参与扣减排序） |
| `ProductionDate` | DateTime? | 否 | 生产日期 |
| `ShelfLifeDays` | int? | 否 | 保质期天数 |
| `ExpirationDate` | DateTime? | 否 | 过期日期；未填视为"无效期限制"批次 |
| `Remark` | string? | 否 | 备注 |

### 响应

`ApiResponseDto<InventoryLogDto>`（补齐显示字段后的 DTO，见 §3）

### 后端 `InboundAppService.CreateAsync` 事务内执行

1. 校验 `SourceType` 合法且非销售出库类
2. 校验商品存在且属于当前门店
3. 采购入库（`SourceType=1`）校验供应商存在
4. 查 `Inventories` 表当前库存 -> 计算 `BeforeQuantity` / `AfterQuantity`
5. 写 `InventoryLogs`（`Type=1`，自动填 `BeforeQuantity/AfterQuantity/CreatedBy/OperatorName`）
6. 写 `InventoryBatches`（始终新建记录，不累加、不覆盖；`PurchaseDate` 由后端自动设为当前日期）
7. 更新 `Inventories`（不存在则插入，存在则累加 `Quantity`）
8. 返回带显示字段的 `InventoryLogDto`

### 与现有端点的关系

保留现有 `POST /InventoryLogs` 通用端点不动（其他业务如 `OrderAppService` 可能内部调用），仅新增 `/inbound` 端点。出库随后对称新增 `/outbound`（下一期）。

## 二、数据模型变更

### `InventoryLog` 实体新增字段

```csharp
/// <summary>
/// 操作人姓名（冗余存储，写入时取 ICurrentUser.RealName ?? UserName）
/// </summary>
public string? OperatorName { get; set; }
```

**理由**: 基类 `StoreBusinessEntityBase` 已有 `CreatedBy`（用户ID），但无姓名。查询时若要显示操作人姓名需跨服务查 System 用户表。为避免跨服务依赖，写入时冗余存储姓名。

### `InventoryLog` 实体新增 `Supplier` 导航属性

```csharp
public Supplier? Supplier { get; set; }
```

**理由**: 现有 `Product` 导航属性已存在（`InventoryLog.cs:72`），但缺 `Supplier`。补齐后查询可一次性 `Include` 两张表，避免 N+1。

### EF Core 配置

在 `StoreDbContext` 中为 `Supplier` 导航属性配置外键关系（`SupplierId` -> `Suppliers.Id`）。

### 数据库 migration

- 新增 `InventoryLogs.OperatorName` 列（nullable string）
- `SupplierId` 列已存在，无需变更
- 无需其他表结构变更（`InventoryBatches` 与 `Inventories` 字段已齐全）

### 不动的内容

- `InventoryLogCreateDto` / `InventoryLogUpdateDto` 不动（保留通用 CRUD 接口原貌）
- `InventoryLogs` 表软删除策略不变（流水表本就无软删除，继承 `StoreBusinessEntityBase`）
- `InventoryBatches` 表保持无软删除（继承 `StoreBusinessEntityBase`）

### `InventoryLogAppService.GetPagedListAsync` 改写查询逻辑

2. 追加过滤：`ProductName` 模糊、`Type`、`SourceType`、`StartDate`、`EndDate`

4. 内存中投影到 `InventoryLogDto`，填充 `ProductName/ProductCode/SupplierName/OperatorName`
   - `OperatorName` 已是实体字段，Adapt 直接映射
   - `ProductName/ProductCode/SupplierName` 手工填
5. 排序、分页、返回（已有逻辑保留）

### 新增 DTO `InboundCreateDto`

位置：`Dtos/Inventories/InboundCreateDto.cs`

字段同 §1 列出的请求体字段。验证规则用 FluentValidation：
- `ProductId` 必填
- `SourceType` 必填，且必须是 `InboundSourceTypes` 集合 {1,2,3,4,6} 之一
- `SupplierId` 当 `SourceType == 1` 时必填
- `Quantity` 必填且 > 0
- `ExpirationDate` 若填，必须晚于 `ProductionDate`（若同时填）

### Mapster 配置

在 `EntityMappingConfig.cs` 中无需额外配置（手工填充字段，不依赖 Mapster 自动映射关联实体）。

### 不动的内容

## 五、错误处理与边界场景

### 后端 `/inbound` 端点错误处理

| 场景 | HTTP 状态 | 错误信息 |
|---|---|---|
| 未登录 / 无门店上下文 | 401 | "无法确定当前租户或门店" |
| `SourceType` 不在 {1,2,3,4,6} 集合 | 400 | "入库来源类型不合法" |
| `SourceType=1`（采购入库）但未传 `SupplierId` | 400 | "采购入库必须选择供应商" |
| `ProductId` 不存在或不属于当前门店 | 400 | "商品不存在" |
| `SupplierId` 不存在 | 400 | "供应商不存在" |
| `Quantity <= 0` | 400 | "入库数量必须大于0" |
| `ExpirationDate` 早于 `ProductionDate` | 400 | "过期日期不能早于生产日期" |
| 数据库写入失败 | 500 | "入库失败" |

### 事务边界

`InboundAppService.CreateAsync` 全程在 `IDbContextTransaction` 内执行。`InventoryLog` / `InventoryBatch` / `Inventory` 三张表写入要么全部成功要么全部回滚。

### 并发处理

本期采用简单方案：事务内串行写入，依赖数据库事务隔离级别。若并发冲突由 `DbUpdateException` 捕获返回 500，前端提示重试。`Inventory` 表不加 `[Timestamp]` 乐观锁（避免额外 migration）。

### 批次写入策略（修订后）

**始终新建 `InventoryBatch` 记录，不累加、不覆盖**。

依据 `docs/通用需求规格.md:130-135` 与 `docs/效期可选需求修复方案.md:201-206`：

- `ExpirationDate` 被 FEFO 排序依赖，覆盖会让已入库数量的扣减顺序错乱
- `PurchaseDate` 被同效期 FIFO 排序依赖，覆盖会让旧数量本应先出却后出
- `CreatedTime` 被 null 批次末尾排序依赖，覆盖会破坏 null 批次的扣减顺序
- `BatchNo` 不参与扣减排序（文档明确"不暴露批次号"），仅用于内部追溯，不能作为"同批次累加"的判断依据
- `UnitPrice` 用于 FIFO 成本计算，覆盖会让已入库数量的成本失真
- 同 `BatchNo` 多条记录允许存在（`BatchNo` 不设唯一约束）

**手动入库时 `PurchaseDate` 由后端自动设为当前日期**（前端表单无此字段）。

### `Inventory` 汇总表更新策略

- 查 `Inventories` 是否存在 `ProductId + StoreId` 记录
  - 存在：`Quantity += 入库数量`
  - 不存在：新建记录，`Quantity = 入库数量`，`AlertQuantity = 0`（默认不预警）

### 前端错误提示

API 函数 `request<T>` 已自动解包 `ApiResponseDto`，`code !== 200` 时抛错。`inbound/index.vue:468` 现有 `catch` 块 `ElMessage.error(error.message)` 直接复用，无需改页面。

### 不动的内容

- 现有 `POST /InventoryLogs` 通用端点的错误处理不动
- `InboundCreateDto` 验证失败由 FluentValidation 自动收集为 400 响应
