# 跨店权益数据隔离与查询规范

> 创建日期: 2026-07-25
>
> 背景: Store 服务采用"门店隔离"原则，但部分权益对象（疗程卡、储值账户）支持跨店使用。本文档明确跨店权益相关实体的字段语义、查询过滤策略、业绩归属规则，避免门店隔离误伤跨店业务功能。
>
> 适用范围: Store 服务所有涉及疗程卡、储值账户的业务实体、应用服务、仓储层、查询接口。
>
> 关联文档: 《权限模型治理方案》、《门店管理系统大方向与应用场景纲领》

---

## 一、概述

### 1.1 文档目的

1. 明确跨店权益对象的门店字段语义，避免"跨店通用 = 无门店归属"的概念混淆
2. 规范查询过滤策略，防止门店隔离机制误伤跨店核销、跨店消费功能
3. 统一业绩归属规则，为财务对账、门店考核提供数据基础
4. 提供代码审查清单，确保实施一致性

### 1.2 核心原则

| 原则 | 说明 |
|------|------|
| 门店隔离优先 | 所有业务数据默认归属门店，按 StoreId 隔离 |
| 跨店权益例外 | 跨店通用的"权益对象"可以无单一门店归属，但必须记录"开户门店/发卡门店" |
| 交易单据必填门店 | 无论权益是否跨店，每笔交易必须明确记录"交易门店"，不可为空 |
| 审计日志同隔离粒度 | 审计日志的门店粒度应与被审计业务对象一致 |
| 门店视角与客户视角分离 | 门店报表按 StoreId 过滤；客户权益查询不按 StoreId 过滤 |

## 二、业务模型

### 2.1 跨店权益对象与交易单据的关系

```
┌─────────────────────────────────────────────────────────────────────┐
│                       跨店权益对象（账户/配置）                       │
│                                                                     │
│   StoredValueAccount（储值账户）      TreatmentCard（疗程卡配置）     │
│   ──────────────────────────         ──────────────────────────     │
│   StoreId = 开户门店（永久）          StoreId = 归属门店（永久）      │
│   余额可跨店消费                      卡配置为门店级独立维护           │
│                                                                     │
└──────────────────────────┬──────────────────────────────────────────┘
                           │
                           │ 1:N
                           ▼
┌─────────────────────────────────────────────────────────────────────┐
│                       交易单据（流水/记录）                          │
│                                                                     │
│   StoredValueLog（储值流水）          TreatmentCardSale（销售单）     │
│   ──────────────────────────         ──────────────────────────     │
│   StoreId = 实际交易门店             StoreId = 购买门店（永久）       │
│                                                                     │
│   TreatmentCardVerify（核销单）       TreatmentCardTransfer（转让单）│
│   ──────────────────────────         ──────────────────────────     │
│   StoreId = 核销门店（每次不同）     StoreId = 操作门店              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.2 跨店使用典型场景

**场景 A：疗程卡跨店核销**

客户在门店 A 购买疗程卡（实付 1000 元，10 次），到门店 B 核销使用 1 次：

| 实体 | StoreId | 业务含义 |
|------|---------|----------|
| TreatmentCard（卡配置） | 门店 A | 门店 A 维护的卡种 |
| TreatmentCardSale（销售单） | 门店 A | 在门店 A 完成购买 |
| TreatmentCardVerify（核销单） | 门店 B | 在门店 B 完成核销 |
| TreatmentCardSaleItem（销售明细） | 门店 A | 跟随销售单 |
| TreatmentCardVerifyItem（核销明细） | 门店 B | 跟随核销单 |

**场景 B：储值账户跨店消费**

客户在门店 A 充值 5000 元（含赠送 1000 元），到门店 B 消费 500 元：

| 实体 | StoreId | 业务含义 |
|------|---------|----------|
| StoredValueAccount（储值账户） | 门店 A | 开户门店永久归属 |
| StoredValueLog（充值流水） | 门店 A | 充值发生门店 |
| StoredValueLog（消费流水） | 门店 B | 消费发生门店 |

## 三、实体字段语义规范

### 3.1 疗程卡系列

| 实体 | 继承基类 | StoreId 语义 | 是否必填 | 是否可变 |
|------|---------|-------------|----------|----------|
| TreatmentCard | StoreEntity | 归属门店（卡种维护门店） | 必填 | 创建后不变 |
| TreatmentCardSale | StoreBusinessEntityBase | 购买门店（发卡门店） | 必填 | 创建后不变 |
| TreatmentCardSaleItem | StoreBusinessEntityBase | 跟随销售单 StoreId | 必填 | 跟随父单据 |
| TreatmentCardVerify | StoreBusinessEntityBase | 核销门店（实际服务门店） | 必填 | 每次核销可能不同 |
| TreatmentCardVerifyItem | StoreBusinessEntityBase | 跟随核销单 StoreId | 必填 | 跟随父单据 |
| TreatmentCardTransfer | StoreBusinessEntityBase | 操作门店（转让办理门店） | 必填 | 创建后不变 |

### 3.2 储值账户系列

| 实体 | 继承基类 | StoreId 语义 | 是否必填 | 是否可变 |
|------|---------|-------------|----------|----------|
| StoredValueAccount | StoreEntity | 开户门店（首次充值门店） | 必填 | 创建后不变 |
| StoredValueLog | StoreBusinessEntityBase | 交易发生门店 | 必填 | 每次交易确定 |
| StoredValueRule | StoreEntity | 归属门店（充值规则维护门店） | 必填 | 创建后不变 |

### 3.3 字段语义对照表（关键）

| 字段名 | 在权益对象上 | 在交易单据上 |
|--------|------------|------------|
| StoreId | 归属门店（开户/发卡/维护） | 交易发生门店 |
| StoreCode | 归属门店编码 | 交易发生门店编码 |

**重要**：权益对象的 StoreId 表示"永久归属"，交易单据的 StoreId 表示"实际发生地"。两者可以不同，这是跨店业务的合法状态。

## 四、查询过滤策略

### 4.1 查询场景分类

| 视角 | 查询目的 | 过滤策略 | 示例 |
|------|---------|---------|------|
| 门店视角 | 门店业绩、门店报表、门店运营数据 | **按 StoreId 过滤** | "门店 A 本月销售了多少疗程卡" |
| 客户视角 | 客户权益、客户历史、客户可用额度 | **不按 StoreId 过滤** | "客户 X 还能核销几次疗程卡" |
| 跨店统计视角 | 跨店核销分析、跨店消费分析 | **按 StoreId 不等关系过滤** | "门店 A 的卡在门店 B 核销了多少次" |

### 4.2 疗程卡查询矩阵

| 查询场景 | 查询实体 | 过滤条件 | 视角 |
|---------|---------|---------|------|
| 门店销售业绩报表 | TreatmentCardSale | TenantId + StoreId = 当前门店 | 门店视角 |
| 门店核销业绩报表 | TreatmentCardVerify | TenantId + StoreId = 当前门店 | 门店视角 |
| 客户可核销疗程卡列表 | TreatmentCardSale | TenantId + CustomerId + Status=有效 | **客户视角** |
| 客户核销历史 | TreatmentCardVerify | TenantId + CustomerId | **客户视角** |
| 客户购买历史 | TreatmentCardSale | TenantId + CustomerId | **客户视角** |
| 跨店核销明细报表 | TreatmentCardVerify JOIN TreatmentCardSale | Verify.StoreId ≠ Sale.StoreId | 跨店统计 |
| 门店卡种配置列表 | TreatmentCard | TenantId + StoreId = 当前门店 | 门店视角 |
| 门店转让记录 | TreatmentCardTransfer | TenantId + StoreId = 当前门店 | 门店视角 |

### 4.3 储值账户查询矩阵

| 查询场景 | 查询实体 | 过滤条件 | 视角 |
|---------|---------|---------|------|
| 门店开户业绩报表 | StoredValueAccount | TenantId + StoreId = 当前门店 | 门店视角 |
| 门店充值业绩报表 | StoredValueLog (类型=充值) | TenantId + StoreId = 当前门店 | 门店视角 |
| 门店消费业绩报表 | StoredValueLog (类型=消费) | TenantId + StoreId = 当前门店 | 门店视角 |
| 客户可用余额 | StoredValueAccount | TenantId + CustomerId | **客户视角** |
| 客户充值/消费历史 | StoredValueLog | TenantId + CustomerId | **客户视角** |
| 跨店消费明细报表 | StoredValueLog JOIN StoredValueAccount | Log.StoreId ≠ Account.StoreId | 跨店统计 |

### 4.4 通用查询原则

**原则 1：客户视角查询不按 StoreId 过滤**

```csharp
// ❌ 错误：跨店核销功能被破坏
var availableCards = await _treatmentCardSaleRepository
    .Where(x => x.TenantId == tenantId
             && x.StoreId == currentStoreId  // 错误过滤
             && x.CustomerId == customerId
             && x.Status == 1);
```

```csharp
// ✅ 正确：客户视角查询所有门店的有效卡
var availableCards = await _treatmentCardSaleRepository
    .Where(x => x.TenantId == tenantId
             && x.CustomerId == customerId
             && x.Status == 1);
```

**原则 2：门店视角查询必须按 StoreId 过滤**

```csharp
// ✅ 正确：门店销售业绩报表
var sales = await _treatmentCardSaleRepository
    .Where(x => x.TenantId == tenantId
             && x.StoreId == currentStoreId
             && x.PurchaseDate >= startDate
             && x.PurchaseDate <= endDate);
```

**原则 3：明细表跟随父单据过滤**

明细表查询时，应通过父单据的 StoreId 过滤，避免明细表与父单据门店不一致（正常情况下应一致，但出于数据完整性保护，以父单据为准）。

```csharp
// ✅ 正确：通过父单据 JOIN 过滤
var verifyItems = await _treatmentCardVerifyItemRepository
    .Join(_treatmentCardVerifyRepository,
          item => item.VerifyId,
          verify => verify.Id,
          (item, verify) => new { item, verify })
    .Where(x => x.verify.TenantId == tenantId
             && x.verify.StoreId == currentStoreId);
```

## 五、创建与更新规范

### 5.1 疗程卡销售单创建

```csharp
// TreatmentCardSaleAppService.CreateAsync
public async Task<long> CreateAsync(TreatmentCardSaleCreateDto input)
{
    var sale = new TreatmentCardSale
    {
        // StoreId 必填：当前操作门店（购买门店）
        StoreId = _currentUser.StoreId,
        StoreCode = _currentUser.StoreCode,
        TenantId = _currentUser.TenantId,
        TenantCode = _currentUser.TenantCode,
        CardId = input.CardId,
        CustomerId = input.CustomerId,
        PurchaseDate = DateTime.Now,
        Amount = input.Amount,
        // ...
    };

    foreach (var itemInput in input.Items)
    {
        sale.Items.Add(new TreatmentCardSaleItem
        {
            StoreId = sale.StoreId,        // 明细跟随父单据
            StoreCode = sale.StoreCode,
            // ...
        });
    }

    await _repository.InsertAsync(sale);
    return sale.Id;
}
```

**关键约束**：
- `Sale.StoreId` 必须等于当前操作门店，不能为空
- `SaleItem.StoreId` 必须等于 `Sale.StoreId`，保持一致

### 5.2 疗程卡核销单创建（跨店核销）

```csharp
// TreatmentCardVerifyAppService.CreateAsync
public async Task<long> CreateAsync(TreatmentCardVerifyCreateDto input)
{
    // 1. 查询客户可核销的疗程卡（客户视角，不按 StoreId 过滤）
    var cardSale = await _treatmentCardSaleRepository
        .Where(x => x.TenantId == _currentUser.TenantId
                 && x.Id == input.CardSaleId
                 && x.CustomerId == input.CustomerId
                 && x.Status == 1)  // 有效
        .FirstOrDefaultAsync();

    if (cardSale == null)
        throw new BusinessException("疗程卡不存在或已失效");

    // 2. 创建核销单：StoreId = 当前操作门店（核销门店），不是发卡门店
    var verify = new TreatmentCardVerify
    {
        StoreId = _currentUser.StoreId,        // 核销门店
        StoreCode = _currentUser.StoreCode,
        TenantId = _currentUser.TenantId,
        TenantCode = _currentUser.TenantCode,
        CardSaleId = cardSale.Id,
        VerifyTime = DateTime.Now,
        // ...
    };

    foreach (var itemInput in input.Items)
    {
        verify.Items.Add(new TreatmentCardVerifyItem
        {
            StoreId = verify.StoreId,          // 明细跟随核销单
            StoreCode = verify.StoreCode,
            // ...
        });
    }

    // 3. 扣减疗程卡剩余次数（按发卡门店单价）
    cardSale.RemainingTimes -= input.TotalTimes;
    // ...

    await _repository.InsertAsync(verify);
    return verify.Id;
}
```

**关键约束**：
- 查询可用疗程卡时**不按 StoreId 过滤**（客户视角）
- 核销单 `StoreId` = 当前操作门店（核销门店），与发卡门店 `cardSale.StoreId` 可以不同
- 核销明细 `StoreId` 必须等于核销单 `StoreId`

### 5.3 储值账户开户与跨店消费

```csharp
// StoredValueAccountAppService.RechargeAsync（充值/开户）
public async Task RechargeAsync(RechargeDto input)
{
    var account = await _accountRepository
        .Where(x => x.TenantId == _currentUser.TenantId
                 && x.CustomerId == input.CustomerId)
        .FirstOrDefaultAsync();

    if (account == null)
    {
        // 首次充值：创建账户，StoreId = 当前操作门店（开户门店）
        account = new StoredValueAccount
        {
            StoreId = _currentUser.StoreId,        // 开户门店（永久）
            StoreCode = _currentUser.StoreCode,
            TenantId = _currentUser.TenantId,
            TenantCode = _currentUser.TenantCode,
            CustomerId = input.CustomerId,
            // ...
        };
        await _accountRepository.InsertAsync(account);
    }
    // else: 已有账户，开户门店不变（即使到其他门店充值）

    // 创建充值流水：StoreId = 当前操作门店
    var log = new StoredValueLog
    {
        StoreId = _currentUser.StoreId,            // 充值发生门店
        StoreCode = _currentUser.StoreCode,
        TenantId = _currentUser.TenantId,
        AccountId = account.Id,
        LogType = StoredValueLogType.Recharge,
        Amount = input.Amount,
        // ...
    };
    await _logRepository.InsertAsync(log);

    // 更新账户余额
    account.Balance += input.Amount;
    // ...
}
```

```csharp
// StoredValueAccountAppService.ConsumeAsync（跨店消费）
public async Task ConsumeAsync(ConsumeDto input)
{
    // 1. 查询客户储值账户（客户视角，不按 StoreId 过滤）
    var account = await _accountRepository
        .Where(x => x.TenantId == _currentUser.TenantId
                 && x.CustomerId == input.CustomerId)
        .FirstOrDefaultAsync();

    if (account == null || account.Balance < input.Amount)
        throw new BusinessException("储值账户余额不足");

    // 2. 创建消费流水：StoreId = 当前操作门店（消费门店），不是开户门店
    var log = new StoredValueLog
    {
        StoreId = _currentUser.StoreId,            // 消费门店
        StoreCode = _currentUser.StoreCode,
        TenantId = _currentUser.TenantId,
        AccountId = account.Id,
        LogType = StoredValueLogType.Consume,
        Amount = input.Amount,
        // ...
    };
    await _logRepository.InsertAsync(log);

    // 3. 扣减账户余额
    account.Balance -= input.Amount;
    // ...
}
```

**关键约束**：
- 查询客户账户时**不按 StoreId 过滤**（客户视角）
- 充值流水的 `StoreId` = 当前操作门店，与账户开户门店 `account.StoreId` 可以不同
- 账户 `StoreId` 一经创建不可修改（即使跨店充值）

### 5.4 禁止操作

| 操作 | 禁止原因 |
|------|----------|
| 修改权益对象的 StoreId | 开户门店/发卡门店永久归属，不可变更 |
| 修改交易单据的 StoreId | 交易发生门店是历史事实，不可篡改 |
| 在客户视角查询中按 StoreId 过滤 | 破坏跨店核销/跨店消费功能 |
| 创建交易单据时不写入 StoreId | 违反交易单据必填门店原则 |

## 六、业绩归属规则

### 6.1 疗程卡业绩归属

| 业绩类型 | 归属门店 | 查询实体 | 过滤条件 |
|---------|---------|---------|---------|
| 卡种销售业绩 | 发卡门店 | TreatmentCardSale | StoreId = 发卡门店 |
| 核销服务业绩 | 核销门店 | TreatmentCardVerify | StoreId = 核销门店 |
| 转让手续费业绩 | 操作门店 | TreatmentCardTransfer | StoreId = 操作门店 |

### 6.2 储值账户业绩归属

| 业绩类型 | 归属门店 | 查询实体 | 过滤条件 |
|---------|---------|---------|---------|
| 开户业绩 | 开户门店 | StoredValueAccount | StoreId = 开户门店 |
| 充值业绩 | 充值发生门店 | StoredValueLog (类型=充值) | StoreId = 充值门店 |
| 消费业绩 | 消费发生门店 | StoredValueLog (类型=消费) | StoreId = 消费门店 |

### 6.3 跨店核销分账规则（推荐方案）

**场景**：客户在门店 A 购卡 1000 元（10 次），到门店 B 核销 1 次。

| 方案 | 销售业绩 | 核销业绩 | 适用场景 |
|------|---------|---------|---------|
| **方案 A（推荐）** | 全额归门店 A | 服务收入归门店 B | 销售归发卡店，服务归核销店 |
| 方案 B | 按比例分摊 | 按比例分摊 | 连锁分账 |
| 方案 C | 不分账，统一归租户 | 不分账 | 直营一体化 |

**推荐方案 A 的查询逻辑**：
- 门店 A 销售业绩：`SELECT SUM(Amount) FROM TreatmentCardSale WHERE StoreId = 门店A`
- 门店 B 核销业绩：`SELECT SUM(VerifyAmount) FROM TreatmentCardVerify WHERE StoreId = 门店B`
- 跨店核销统计：`SELECT COUNT(*) FROM TreatmentCardVerify v JOIN TreatmentCardSale s ON v.CardSaleId = s.Id WHERE v.StoreId <> s.StoreId`

### 6.4 跨店核销价格差异处理（推荐方案）

**场景**：门店 A 卡配置单价 100 元，门店 B 同项目单价 120 元。

| 方案 | 规则 | 影响 |
|------|------|------|
| **方案 A（推荐）** | 按发卡门店单价扣减次数 | 保护客户权益，体验一致 |
| 方案 B | 按核销门店单价扣减次数 | 保护门店 B 利益 |
| 方案 C | 差价补款 | 复杂，影响体验 |

## 七、应用层实现规范

### 7.1 AppService 方法命名约定

> 已按 7.5 评审意见修订：保留 `GetPagedListAsync(QueryDto)` 统一入口，避免破坏现有 Controller 路由与前端接口契约。

现有 AppService 采用统一的 `GetPagedListAsync(QueryDto)` 入口，通过 QueryDto 中的字段（如 `CustomerId` 是否传入）区分查询视角。本规范保留此风格，通过 **QueryDto XML 注释标注视角** 的方式明确语义。

| 视角 | QueryDto 字段特征 | 过滤策略 |
|------|------------------|---------|
| 门店视角 | 不包含 CustomerId（或为可选） | Where 条件显式过滤 `StoreId == _currentUser.StoreId` |
| 客户视角 | 包含 CustomerId 必填 | 禁止添加 StoreId 过滤条件 |
| 跨店统计视角 | 包含日期范围 + QueryMode 枚举 | 按 StoreId 不等关系过滤（仅报表场景） |

**例外**：对于必须区分视角的报表类查询（如跨店核销报表），可新增独立方法 `GetCrossStoreVerifiesAsync`，但不强制套用到所有 AppService。

### 7.2 AppService 层查询规范

> 已按 7.5 评审意见修订：删除 Repository 层抽象约定，改为 AppService 层查询规范。现有 Store 服务不存在 Repository 层，AppService 直接注入 `StoreDbContext` 编写 LINQ 查询。

AppService 直接使用 DbContext 时，必须遵守以下规范：

1. **方法 XML 注释必须标注查询视角**（门店视角 / 客户视角 / 跨店统计视角）
2. **门店视角查询**：必须在 Where 条件中显式过滤 `StoreId == _currentUser.StoreId`
3. **客户视角查询**：禁止添加 StoreId 过滤条件
4. **跨店统计查询**：通过 StoreId 不等关系过滤（如 `Verify.StoreId != Sale.StoreId`）

**示例**：

```csharp
/// <summary>
/// 储值账户分页查询（客户视角：不按 StoreId 过滤）
/// </summary>
public async Task<PagedResult<StoredValueAccountDto>> GetPagedListAsync(StoredValueAccountQueryDto input)
{
    var query = _dbContext.StoredValueAccounts
        .Where(x => x.TenantId == _currentUser.TenantId);

    // 客户视角：按 CustomerId 过滤，不按 StoreId 过滤
    if (input.CustomerId.HasValue)
        query = query.Where(x => x.CustomerId == input.CustomerId.Value);

    return await query
        .OrderByDescending(x => x.CreatedTime)
        .ToPagedResultAsync(input);
}
```

### 7.3 多租户中间件配合

> 已按 7.5 评审意见修订：现有 `MultiTenantMiddleware.cs:58-66` 从 `X-Store-Id` 请求头解析 StoreId，并非基于用户门店上下文自动注入。

| 字段 | 注入方式 | 是否可被覆盖 |
|------|---------|------------|
| TenantId | 中间件自动注入 | 否（强制） |
| TenantCode | 中间件自动注入 | 否（强制） |
| StoreId | 前端通过 `X-Store-Id` 请求头传入，中间件解析后存入 `HttpContext.Items["StoreId"]`，`ICurrentUser.StoreId` 从中读取 | 是（客户视角查询时不使用） |
| StoreCode | 同上，从请求头解析 | 是（客户视角查询时不使用） |

**补充说明**：
- 超级管理员（`super_admin`）跳过租户校验但仍依赖请求头传入 StoreId
- 门店切换由前端控制，切换时更新 `X-Store-Id` 请求头
- StoreId 自动注入仅适用于"创建"场景和"门店视角查询"场景
- "客户视角查询"必须显式跳过 StoreId 过滤

### 7.4 DTO 设计规范

> 已按 7.5 评审意见修订：删除 `StoreScopedQueryDto` / `CustomerScopedQueryDto` 基类约定，改为 QueryDto 字段设计约束。现有 DTO 风格是单一 `QueryDto : PagedRequestDto`，引入两个基类会破坏 40+ QueryDto 的继承链。

**QueryDto 字段设计约束**：

| 视角 | QueryDto 字段约束 | XML 注释要求 |
|------|------------------|------------|
| 门店视角 | 不包含 CustomerId（或为可选） | 标注"门店视角：按 StoreId 过滤" |
| 客户视角 | 包含 CustomerId 必填，不包含 StoreId 字段 | 标注"客户视角：不按 StoreId 过滤" |
| 双视角（仅报表） | 通过 `QueryMode` 枚举字段显式区分 | 标注两种视角的查询条件 |

**示例**：

```csharp
/// <summary>
/// 储值账户分页查询（客户视角：不按 StoreId 过滤）
/// </summary>
public class StoredValueAccountQueryDto : PagedRequestDto
{
    public long? CustomerId { get; set; }
}

/// <summary>
/// 储值账户门店业绩报表（门店视角：按 StoreId 过滤）
/// </summary>
public class StoredValueAccountStoreReportQueryDto : PagedRequestDto
{
    public DateTime? StartDate { get; set; }
    public DateTime? EndDate { get; set; }
    // 不包含 CustomerId
}

/// <summary>
/// 跨店核销报表（双视角：通过 QueryMode 区分）
/// </summary>
public class CrossStoreVerifyReportQueryDto : PagedRequestDto
{
    public CrossStoreQueryMode QueryMode { get; set; }
    public DateTime? StartDate { get; set; }
    public DateTime? EndDate { get; set; }
}

public enum CrossStoreQueryMode
{
    ByIssuingStore = 1,   // 按发卡门店统计
    ByVerifyStore = 2,    // 按核销门店统计
    CrossStoreOnly = 3    // 仅跨店记录
}
```

#### 7.5.2 与现有代码不契合的部分

**1. 7.1 节方法命名约定与现有 AppService 风格冲突**

文档建议的 `GetByStoreAsync` / `GetByCustomerAsync` / `GetCrossStoreAsync` 命名前缀，与现有 AppService 统一的 CRUD 命名风格不一致。

现有代码采用统一的 `GetPagedListAsync(QueryDto)` 入口，通过 QueryDto 中的字段（如 `CustomerId` 是否传入）区分查询视角。若强制改为 `GetByStore` / `GetByCustomer` 双方法，会导致：

- 现有 Controller 路由全部需调整
- 前端接口契约破坏性变更
- AppService 方法数量翻倍

**建议修订**：保留 `GetPagedListAsync(QueryDto)` 统一入口，通过**在 QueryDto 上添加 XML 注释标注视角**的方式明确语义，例如：

```csharp
/// <summary>
/// 储值账户分页查询（客户视角：不按 StoreId 过滤）
/// </summary>
public class StoredValueAccountQueryDto : PagedRequestDto
{
    public long? CustomerId { get; set; }
}
```

对于必须区分视角的报表类查询（如跨店核销报表），可新增独立方法 `GetCrossStoreVerifiesAsync`，但不强制套用到所有 AppService。

**2. 7.2 节仓储层规范与现有架构不符**

文档建议仓储层接口 `ITreatmentCardSaleRepository` 提供三类查询方法。但现有 Store 服务**不存在 Repository 层抽象**，所有 AppService 直接注入 `StoreDbContext` 编写 LINQ 查询（参见 `StoredValueAccountAppService.cs:18`、`TreatmentCardSaleAppService.cs:20`）。

若按文档引入 Repository 层，将带来：

- 全量 AppService 重构（80+ 文件）
- 现有 `Mapster` 映射、`FluentValidation` 校验流程需迁移
- 引入额外的抽象层，与项目"简单至上"原则冲突

**建议修订**：删除 7.2 节的 Repository 接口规范，改为**AppService 层查询规范**，明确：

- AppService 直接使用 DbContext 时，必须在方法 XML 注释中标注查询视角
- 门店视角查询必须在 Where 条件中显式过滤 `StoreId == _currentUser.StoreId`
- 客户视角查询禁止添加 StoreId 过滤条件

**3. 7.3 节中间件描述与现有实现不一致**

文档描述"中间件根据当前用户门店上下文注入 StoreId"，但 `MultiTenantMiddleware.cs:58-66` 的现有实现是从 `X-Store-Id` 请求头解析 StoreId，并存入 `context.Items["StoreId"]`。`ICurrentUser.StoreId` 也是从该请求头获取，**并非基于用户门店上下文自动注入**。

**建议修订**：更新 7.3 节表格描述为：

| 字段 | 注入方式 | 是否可被覆盖 |
|------|---------|------------|
| StoreId | 前端通过 `X-Store-Id` 请求头传入，中间件解析后存入 `HttpContext.Items["StoreId"]`，`ICurrentUser.StoreId` 从中读取 | 是（客户视角查询时不使用） |

同时补充说明：超级管理员（`super_admin`）跳过租户校验但仍依赖请求头传入 StoreId，门店切换由前端控制。

**4. 7.4 节 DTO 基类设计与现有风格冲突**

文档建议引入 `StoreScopedQueryDto` / `CustomerScopedQueryDto` 两个基类。但现有 DTO 风格是单一 `QueryDto : PagedRequestDto`（参见 `StoredValueAccountQueryDto.cs:8`），未引入视角基类。

引入两个基类会带来：

- 现有 40+ QueryDto 需调整继承关系
- QueryDto 无法同时支持门店视角和客户视角（需拆分为两个类）
- 与 `PagedRequestDto` 的继承链冲突

**建议修订**：删除 `StoreScopedQueryDto` / `CustomerScopedQueryDto` 基类约定，改为**在 QueryDto 上通过 XML 注释标注视角**，并通过**字段设计约束**实现：

- 门店视角 QueryDto：不包含 `CustomerId` 字段（或为可选）
- 客户视角 QueryDto：包含 `CustomerId` 必填字段，不包含 `StoreId` 字段
- 双视角 QueryDto：通过 `QueryMode` 枚举字段显式区分（仅在报表场景使用）

| 跨店核销单价口径 | "按发卡门店单价扣减" = **销售时锁定的折算单价**（`TreatmentCardSaleItem.折算单价`），非发卡门店当前卡配置单价（`TreatmentCard.Price`，可变） | 规则 3 |
| VerifyAmount 字段语义 | `TreatmentCardVerify.VerifyAmount` = ∑(核销次数 × 销售单折算单价)，核销门店服务业绩也以此金额统计 | 规则 1、3 |
| 储值消费业绩口径 | 跨店消费时核销门店的"消费业绩"仅按 `RealBalanceChange` 统计（赠送金额不计业绩），避免业绩虚高 | 规则 4 |
| 开户门店业绩归属 | 开户门店仅用于账户归属追溯，不享受跨店充值业绩（充值业绩归充值发生门店） | 规则 4 |
| 转让后销售业绩归属 | 销售业绩永久归发卡门店，不随转让转移。转让仅转移剩余次数，不转移历史业绩 | 规则 5 |
| 转让后有效期 | 转让不重置有效期（`ExpiryDate` 不变），避免通过转让变相续期 | 规则 5 |
| 原客户核销历史归属 | 原客户的核销历史不随卡转移给新客户，仅转移剩余次数，保持客户档案完整性 | 规则 5 |
| 跨店差价损失归属 | 核销门店单价高于发卡门店时，差价损失由核销门店承担，财务报表明确"跨店服务差价损失"科目 | 规则 3 |
| 跨店差额收益归属 | 核销门店单价低于发卡门店时，差额归核销门店作为服务利润 | 规则 3 |

### 9.1 评审意见（后端开发工程师）

> 评审日期：2026-07-25
>
> 评审范围：第九章待确认业务规则的技术可行性、与现有代码契合度、潜在风险及遗漏场景
>
> 评审结论：**推荐方案整体技术可行，但需补充关键边界规则与配置预留后再确认实施**

#### 9.1.1 规则 1：跨店核销分账规则（方案 A）

- **技术可行性**：高。`TreatmentCardSale.StoreId`（发卡门店）与 `TreatmentCardVerify.StoreId`（核销门店）天然分离，分别按 StoreId 查询即可，符合第三章字段语义。
- **业务合理性**：合理。销售归发卡店、服务归核销店符合"谁卖谁得销售业绩、谁服务谁得服务业绩"的常识。
- **待补充**：
  - **退卡业绩冲销**：跨店核销后客户申请退卡（退未核销次数），原销售业绩如何冲销？建议全额冲减发卡门店销售业绩，已发生的核销业绩不冲回（服务已实际发生）。
  - **核销单冲正**：核销单撤销或冲正时，已计入核销门店的服务业绩如何回滚？建议在 `TreatmentCardVerify` 中新增"已冲正"状态或独立冲正流水，避免物理删除。
  - **服务业绩金额口径**：规则 3 推荐按发卡门店单价扣减次数，此时核销门店的"服务业绩"金额应明确为"按发卡折算单价计算的本次核销金额"（即 `VerifyAmount` 字段值），与客户实际扣减价值一致。
  - **报表跨店标记**：跨店核销记录在发卡门店销售报表与核销门店服务报表中均会出现，建议报表层增加 `IsCrossStore` 标记字段，避免对账困惑。

#### 9.1.2 规则 2：跨店核销范围限制（MVP 全租户任意门店）

- **技术可行性**：高。客户视角查询不按 StoreId 过滤即可实现。
- **业务合理性**：MVP 阶段可接受，但加盟店场景存在利益冲突，需预留配置。
- **待补充**：
  - **租户级开关**：建议在租户配置中预留 `AllowCrossStoreVerify` 开关，默认开启，便于后续按租户特性（直营/加盟）调整，避免后续硬编码改造。
  - **客户身份验证强度**：跨店核销时客户身份验证强度应高于同店（发卡门店熟悉客户），MVP 至少要求手机号尾号核对；高价值卡建议人脸识别。
  - **同店优先逻辑**：若客户在发卡门店核销，应优先走同店逻辑，避免误走跨店分账路径产生歧义。
  - **门店黑白名单预留**：MVP 不实现，但实体设计建议预留"跨店核销白名单"字段位置，避免后续 schema 改造。

#### 9.1.3 规则 3：跨店核销价格差异处理（方案 A：按发卡门店单价扣减）

- **技术可行性**：中。关键依赖：
  - `TreatmentCardSaleItem` 注释已明确"按实际售价分摊计算折算单价并锁定"，跨店核销扣减次数应直接读取**销售单折算单价**（已锁定），而非 `TreatmentCard.Price`（发卡门店当前卡配置单价，可变）。
  - **文档需明确**："按发卡门店单价扣减"应理解为**销售时锁定的折算单价**，而非发卡门店当前卡配置单价。否则发卡门店调整单价后跨店核销口径会混乱。
- **业务合理性**：合理。保护客户权益，体验一致。
- **待补充**：
  - **VerifyAmount 字段语义**：`TreatmentCardVerify.VerifyAmount` 应记录"按发卡折算单价计算的本次核销金额"，核销门店服务业绩也以此金额统计。文档应明确此点。
  - **核销门店单价高于发卡门店时的差价**：差价损失由核销门店承担，建议在财务报表中明确"跨店服务差价损失"科目（或租户级补贴科目），不可静默忽略。
  - **核销门店单价低于发卡门店时的差额**：建议归核销门店作为服务利润，激励其接受跨店核销。

#### 9.1.4 规则 4：储值账户跨店充值是否更新开户门店（否）

- **技术可行性**：高（依赖实体改造完成）。`StoredValueAccount.StoreId` 创建后不变即可。
- **现有代码冲突**（**重要**）：
  - `StoredValueAccount.cs:6` 类注释明确写"储值账户（租户内跨店通用，**不归属单一门店**，遵循原则4跨店权益共享）"，与本规则"开户门店永久不变"语义**直接冲突**。
  - 现有 `StoredValueAccount` 继承 `StoreTenantEntity`，无显式 StoreId 字段，实际无法记录开户门店。需按文档 10.1 节改造为继承 `StoreEntity` 后，同步修正类注释，再讨论本规则实施。
- **待补充**：
  - **充值业绩归属**：跨店充值的"充值业绩"归充值发生门店（`StoredValueLog.StoreId`），不归开户门店。文档 6.2 节已明确，但规则 4 措辞易引起歧义，建议备注："开户门店仅用于账户归属追溯，不享受跨店充值业绩"。
  - **实收/赠送余额跨店消费拆分**：`StoredValueLog` 已拆分 `RealBalanceChange` / `GiftBalanceChange`，跨店消费时核销门店的"消费业绩"应明确仅按 `RealBalanceChange` 统计（赠送金额不计业绩），避免业绩虚高。
  - **跨店退款归属**：`StoredValueLog.Type=3` 退款场景下，跨店退款如何归属？建议退款金额冲减原充值发生门店充值业绩；若原充值门店已关店，冲减当前操作门店。

#### 9.1.5 规则 5：疗程卡转让是否限定同门店客户（否，租户内任意客户可转让）

- **技术可行性**：高。`TreatmentCardTransfer` 已记录 `FromCustomerId` / `ToCustomerId` / 操作门店。
- **业务合理性**：合理但风险较高。租户内任意客户可转让便于家庭/朋友间权益流转，但存在黄牛倒卖、洗钱风险。
- **待补充**：
  - **转让后销售业绩归属**：`TreatmentCardSale.StoreId` 创建后不变（发卡门店），建议明确：销售业绩永久归发卡门店，不随转让转移。转让仅转移剩余次数，不转移历史业绩。
  - **转让次数限制**：建议 MVP 阶段限制同一张卡最多 1 次转让，避免黄牛倒卖。可在 `TreatmentCardSale` 上增加 `TransferCount` 字段记录。
  - **转让时客户身份验证**：受让人需实名认证，避免匿名转让。
  - **转让审计**：转让是高风险操作，需完整审计日志（操作员、操作门店、IP、设备指纹、转让前后客户身份核验记录）。
  - **转让手续费归属**：文档 6.1 节明确归操作门店，建议在规则 5 备注中重申，避免实施时遗漏。
  - **原客户核销历史归属**：建议原客户的核销历史不随卡转移给新客户，仅转移剩余次数，保持客户档案完整性。
  - **转让后有效期**：转让不重置有效期（`ExpiryDate` 不变），避免通过转让变相续期。

#### 9.1.6 遗漏的关键业务场景

第九章列出的 5 条规则未覆盖以下关键场景，建议补充至待确认清单：

| 序号 | 遗漏业务问题 | 推荐方案 | 优先级 |
|------|------------|---------|--------|
| 6 | 跨店核销后退卡（退未核销次数）业绩冲销规则 | 全额冲减发卡门店销售业绩；已发生的核销业绩不冲回 | 高 |
| 7 | 跨店核销单冲正/撤销规则 | 新增"核销冲正"状态或独立冲正流水，冲正金额冲减原核销门店服务业绩 | 高 |
| 8 | 储值账户跨店退款归属规则 | 退款金额冲减原充值发生门店充值业绩；原充值门店关店则冲减当前操作门店 | 高 |
| 9 | 跨店核销客户身份验证强度 | 跨店核销至少要求手机号尾号核对；高价值卡需人脸识别 | 中 |

| 12 | 发卡门店关店后跨店核销处理 | 发卡门店关店后疗程卡仍可在其他门店核销，业绩归核销门店；销售业绩归租户"已关店门店"科目 | 中 |
| 13 | 储值账户跨店消费混合支付（储值+现金）归属 | 支持。储值部分按本规则归属，现金部分归核销门店 | 低 |
| 14 | 跨店权益操作审计日志粒度 | 跨店核销、跨店消费、跨店充值、转让必须记录审计日志，包含操作门店、操作员、IP | 高 |

#### 9.1.7 实施建议

1. **优先级排序**：规则 1/3/4 与跨店核销核心功能强相关，建议优先确认；规则 2/5 涉及风控与配置，可后续迭代。
2. **配置预留**：规则 2 的租户级开关、规则 5 的转让次数限制，应在实体设计中预留字段，避免后续 schema 改造。
3. **审计先行**：跨店权益操作是高风险场景，审计日志与流水必须先于业务功能实现，便于事后追溯。
4. **与文档第十章协同**：规则 4 的实施依赖 `StoredValueAccount` 实体改造（继承 `StoreEntity`），需在第十章实体修改清单完成后才能讨论本规则的具体实现。
5. **与 7.5.3 节缺陷修复协同**：现有 `StoredValueAccount` 类注释"不归属单一门店"与本规则"开户门店永久归属"冲突，需在实体改造时同步修正注释，避免开发人员误读。
6. **跨店核销单价口径统一**：规则 3 实施时，应在文档中明确"按发卡门店单价"= 销售单锁定的折算单价，避免开发人员误用 `TreatmentCard.Price`（当前卡配置单价，可变）。
