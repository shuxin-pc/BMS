| 版本 | 日期 | 状态 | 作者 |
|------|------|------|------|

## 一、设计背景与目标

### 1.1 设计背景

门店管理系统当前已有用户、角色、菜单、租户、组织、权限、系统配置、审计日志等基础模块，但缺少站内消息通知能力。各业务模块（如库存预警、采购审批、日结提醒、会员储值不足等）发生事件时，无法及时通知相关人员，用户需要主动查询才能发现待办事项，影响运营效率。

### 1.2 设计目标

在 System 服务（基础数据子系统）中新增站内信功能，实现：

1. **系统通知**：业务事件触发时自动向相关用户发送通知
2. **管理员推送**：管理员可手动向指定用户/角色/组织/全员/租户发送消息
3. **实时推送**：通过 SignalR 实现消息实时到达
4. **多租户支持**：支持租户内消息和平台跨租户消息

### 1.3 设计原则

- 遵循现有 System 服务的 DDD 四层架构和代码约定
- 遵循多租户行级隔离架构
- 不过度设计，满足当前需求即可（YAGNI）
- 消息以系统通知为主，用户只能查看和确认，不支持回复

## 二、需求分析

### 2.1 核心定位

站内信以**系统通知为主**，单向通知，用户只能查看和确认，不支持回复和对话。

### 2.2 触发场景

| 场景类别 | 说明 | 触发方式 |
|----------|------|----------|
| 系统管理事件 | 用户创建/停用、角色变更、密码过期等 | 自动触发 |
| 门店业务事件 | 库存预警、效期提醒、采购审批、日结提醒等 | 自动触发 |
| 会员相关事件 | 储值不足、疗程卡过期、积分到期等 | 自动触发 |
| 管理员手动推送 | 系统维护公告、政策变更等 | 手动推送 |

### 2.3 接收对象粒度

#### 2.3.1 单一粒度

| 粒度 | 说明 | 适用场景 |
|------|------|----------|
| 指定用户 | 推送给指定的一个或多个用户 | 审批结果通知申请人 |
| 按角色 | 推送给某个角色的所有用户 | 采购审批通知采购经理 |
| 按组织 | 推送给某个组织/部门的所有用户 | 门店通知该店全体员工 |
| 按租户 | 推送给指定租户的所有用户（仅平台管理员） | 平台向租户发通知 |
| 全员 | 推送给当前租户下的所有用户 | 系统维护公告 |

#### 2.3.2 多粒度组合

除单一粒度外，平台管理员发送跨租户消息时，支持**租户 + 角色/组织/用户**的组合筛选，即在指定租户范围内进一步按角色/组织/用户缩小接收范围。

典型场景：

| 组合方式 | 说明 | 示例 |
|----------|------|------|
| 租户 + 角色 | 向指定租户范围内拥有某角色的用户发送 | 平台向租户A、租户B的租户管理员（tenant_admin）发送通知 |
| 租户 + 组织 | 向指定租户范围内某组织的用户发送 | 平台向租户A的"总部"组织发送通知 |
| 租户 + 用户 | 向指定租户范围内的指定用户发送 | 平台向租户A的特定用户发送通知 |

> **设计支撑**：平台角色（如 tenant_admin，TenantId=1）下的用户分属不同租户。组合筛选时，系统为每个目标租户创建一条 Message 记录，在该租户范围内按角色/组织/用户解析接收者。具体实现见 4.6.3 节和 7.5 节。

### 2.4 交互行为

- 支持链接跳转：消息可携带目标链接，点击后跳转到相关业务页面
- 支持批量操作：批量标记已读、批量删除
- 支持全部已读：一键标记所有未读消息为已读
- 不支持标星收藏
- 不支持处理状态（仅已读/未读）

### 2.5 消息分类

采用固定分类，每条消息归属一个分类：

| 值 | 分类 | 说明 | 举例 |
|----|------|------|------|
| 1 | 系统 | 系统管理类通知 | 账号创建/停用、角色权限变更、密码即将过期 |
| 2 | 业务 | 门店业务类通知（含会员相关） | 库存低于阈值、商品即将过期、采购单待审批、日结待确认、储值余额不足、疗程卡即将过期、积分即将到期 |
| 3 | 公告 | 管理员发布的公告 | 系统维护通知、政策变更公告、节假日安排 |

## 三、整体架构

### 3.1 架构定位

站内信功能部署在 **System 服务**（基础数据子系统），原因：

- System 服务管理用户、角色、组织等基础数据，站内信的接收对象解析需要依赖这些数据
- 站内信属于平台级基础能力，不是门店业务功能
- 与现有审计日志、系统配置等模块同级

### 3.2 模块划分

```

├── Bms.System.Domain/Entities/
│   ├── Message.cs              # 消息发送记录表实体
│   └── MessageRecipient.cs     # 消息接收表实体

│   │   ├── IMessageAppService.cs

│   │   └── MessageNotifier.cs  # 消息发送服务（供其他模块调用）
│   └── Validators/             # 验证器
├── Bms.System.Infrastructure/
│   ├── Repositories/
```

### 3.3 依赖关系

- **内部依赖**：MessageAppService 调用 UserRepository、RoleRepository、OrganizationRepository 解析接收对象
- **外部调用**：Store 服务通过 HTTP 调用 System 服务的内部 API 触发消息发送
- **实时推送**：前端通过 SignalR 连接 MessageHub，接收实时消息推送

### 3.4 核心流程

```

  │                              │                              │

  │                    │                       │                │
  │                    ├─-> 展开为每用户记录    │                │
  │                    │                       │                │
  │                    ├─-> 保存到 DB           │                │
  │                    │                       │                │
  │                    └─-> SignalR 推送 ──────────────────────->│
  │                                              │              │
  └─ 管理员手动 ──-> MessagesController.Send() ─-> 同上流程      │
                                                    │
                              前端查询消息列表 <─────┘
```

## 四、数据模型

### 4.1 消息分发模型：展开模式（Fan-out）

发送消息时，立即解析所有接收者，为每个用户创建独立的消息接收记录。

**选择理由**：

1. 用户量可控：门店管理系统每租户用户量通常几十到几百人，全员消息展开的记录数可控
2. 查询性能最优：直接按 UserId 查询，索引高效，分页和未读统计简单
3. 状态管理清晰：每条接收记录独立管理已读/删除状态，逻辑简单
4. 实时推送友好：SignalR 推送时直接推送用户的消息记录，无需二次查询
5. 与现有架构一致：与审计日志等模块的记录模式一致，降低维护成本

### 4.2 消息发送记录表（Message）

| 字段 | 类型 | 说明 |
|------|------|------|
| Id | long | 主键（雪花ID） |
| Title | string(200) | 消息标题 |
| Content | string(2000) | 消息内容 |
| Category | int | 分类：1=系统, 2=业务, 3=公告 |
| SourceType | int | 来源类型：1=自动触发, 2=手动推送 |
| SourceModule | string(50) | 来源模块（如 Inventory、Order、DailySettlement） |
| TargetType | int | 目标类型：1=用户, 2=角色, 3=组织, 4=租户, 5=全员 |
| TargetIds | text | 目标ID列表（逗号分隔；全员时为空） |
| TargetDesc | string(1000) | 目标描述（如"租户A,租户B"或"采购经理,店长"） |
| SenderId | long? | 发送者ID（手动推送时记录，自动触发为空） |
| SenderName | string(50) | 发送者名称 |
| TargetUrl | string(500) | 跳转链接（如 /store/inventory） |
| IsCrossTenant | bool | 是否跨租户消息（平台发送时为 true） |
| IsRecalled | bool | 是否已撤回（管理端删除时为 true，默认 false） |
| TenantId | long | 消息归属租户ID。租户内消息时为发送者所在租户；跨租户消息时为**目标租户**ID（每个目标租户一条 Message） |
| TenantCode | string(20) | 消息归属租户编码。与 TenantId 对应，用于多租户数据隔离 |
| CreatedTime | DateTime | 创建时间 |
| UpdatedTime | DateTime? | 更新时间 |

> **不加软删除**：消息发送记录表作为历史记录保留，不设 IsDeleted 字段。管理端通过 IsRecalled 字段标识撤回状态，用户侧可见性通过 MessageRecipient 的 IsDeleted 字段控制。撤回时同时设置 Message.IsRecalled=true（管理端标识）和所有关联 MessageRecipient.IsDeleted=true（收件箱消失），两个字段各司其职。

### 4.3 MessageRecipient 表（消息接收表）

| 字段 | 类型 | 说明 |
|------|------|------|
| Id | long | 主键（雪花ID） |
| MessageId | long | 消息ID（外键） |
| UserId | long | 接收用户ID |
| UserName | string(50) | 接收用户名（冗余，便于排查） |
| IsRead | bool | 是否已读 |
| ReadTime | DateTime? | 已读时间 |
| IsDeleted | bool | 是否已删除（用户侧删除） |
| DeletedTime | DateTime? | 删除时间 |
| TenantId | long | 接收用户所属租户ID（与 Message.TenantId 一致，用于多租户数据隔离） |
| TenantCode | string(20) | 接收用户所属租户编码 |
| CreatedTime | DateTime | 创建时间 |

> **软删除加在此表**：用户删除消息是逻辑删除，保留数据用于审计。

### 4.5 索引设计

- MessageRecipient: `(UserId, IsRead, IsDeleted, CreatedTime DESC)` - 支撑用户收件箱查询
- MessageRecipient: `(MessageId)` - 支撑按消息查询接收记录
- Message: `(TenantId, CreatedTime DESC)` - 支撑管理端消息列表查询

### 4.6 多租户与跨租户处理

#### 4.6.1 租户内消息

- 发送者为租户内用户，Message.TenantId = 当前租户
- IsCrossTenant = false
- 展开范围为当前租户内的用户

#### 4.6.2 平台跨租户消息

- 发送者为平台管理员，IsCrossTenant = true
- 系统为**每个目标租户**创建一条 Message 记录，Message.TenantId = 目标租户ID
- 各租户可在自己的消息列表中看到平台通知

#### 4.6.3 跨租户角色筛选

**场景**：平台级角色（如 tenant_admin，TenantId=1）下的用户分属不同租户。平台需要向"指定多个租户的租户管理员"发消息。

**支撑方式**：

1. 用户与角色的关联通过 `UserRole` 关联表，不依赖 `Role.TenantId`
2. 平台选择目标租户列表 + 目标角色后，为每个目标租户创建一条 Message（TenantId=目标租户，TargetType=Role）
3. 展开查询：在该 Message.TenantId 范围内，查找拥有指定角色的用户

```sql
SELECT u.Id FROM Users u
JOIN UserRole ur ON u.Id = ur.UserId
WHERE ur.RoleId IN (@TargetRoleIds)
  AND u.TenantId = @Message.TenantId
  AND u.IsDeleted = false
```

此查询能正确找到"属于指定租户且拥有 tenant_admin 角色的用户"，即使角色本身是平台级角色（TenantId=1）。

### 4.7 TargetIds 存储说明

- 使用 `text` 类型，支持存储大量雪花ID（逗号分隔）
- TargetIds 仅用于管理端展示消息发送范围，不参与接收者查询
- 接收者查询基于 MessageRecipient 表的 UserId 字段

### 5.3 管理端 API（管理员发送/管理消息）

| 方法 | 路由 | 说明 | 权限 |
|------|------|------|------|
| GET | `/api/system/messages` | 消息发送记录列表（分页） | `system:message:send` |

### 5.7 设计说明

1. **收件箱查询基于 MessageRecipient 表**：用户看到的是自己的消息接收记录，Id 为 MessageRecipient.Id
2. **管理端查询基于 Message 表**：管理员看到的是消息发送记录，包含接收范围和撤回状态
3. **InternalMessageNotifyDto 简化**：内部服务调用时不需要 TargetTenantIds（内部服务都是租户内的，TenantId 由请求头传递）
4. **发送流程**：`SendAsync` -> 解析接收者 -> 批量插入 MessageRecipient -> SignalR 推送

## 六、实时推送方案

### 6.1 SignalR Hub 设计

```csharp
[Authorize]
public class MessageHub : Hub
{
    // 连接时，将用户加入个人组（基于 UserId）
    public override async Task OnConnectedAsync()
    {
        var userId = CurrentUser.Id;
        await Groups.AddToGroupAsync(Context.ConnectionId, $"user_{userId}");
        await base.OnConnectedAsync();
    }
}
```

**推送策略**：使用 Group 而非直接向 ConnectionId 推送，因为用户可能同时打开多个标签页（多个连接），Group 可确保该用户所有连接都收到消息。

### 6.2 消息推送格式

```json
{
  "event": "ReceiveMessage",
  "data": {
    "id": 1234567890123456789,
    "messageId": 9876543210987654321,
    "title": "库存预警",
    "content": "商品A库存不足，剩余5件",
    "category": 2,
    "categoryName": "业务通知",
    "senderName": "系统",
    "targetUrl": "/store/product/inventory",
    "createdTime": "2026-07-22T10:30:00"
  }
}
```

前端收到推送后：

1. 更新未读消息数（角标 +1）
2. 如果当前在收件箱页面，插入新消息到列表顶部
3. 可选：显示桌面通知（Notification API）

### 6.3 推送时机

- **消息发送时**：`MessageAppService.SendAsync` / `NotifyAsync` 完成 DB 写入后，调用 `IHubContext<MessageHub>` 推送
- **批量发送优化**：如果接收者超过 100 人，分批推送，避免阻塞

### 6.4 网关配置

## 七、消息触发集成方案

### 7.1 触发方式分类

| 来源 | 触发方式 | 调用方式 |
|------|----------|----------|
| System 服务内部事件 | 自动触发 | 直接调用 `IMessageAppService.NotifyAsync()` |
| Store 服务业务事件 | 自动触发 | HTTP 调用 `/api/system/internal/messages/notify` |

### 7.2 System 服务内部事件

System 服务内部直接注入 `IMessageAppService` 调用：

```csharp
// 示例：用户创建时通知
public class UserAppService
{
    private readonly IMessageAppService _messageAppService;

    public async Task<UserDto> CreateAsync(UserCreateDto dto)
    {
        // ... 创建用户逻辑 ...

        await _messageAppService.NotifyAsync(new InternalMessageNotifyDto
        {
            Title = "账号创建通知",
            Content = $"您的账号 {dto.UserName} 已创建成功，请联系管理员获取权限。",
            Category = (int)MessageCategory.System,
            SourceModule = "User",
            TargetType = (int)MessageTargetType.User,
            TargetIds = new List<long> { user.Id },
            TargetUrl = "/system/profile"
        });

        return user;
    }
}
```

### 7.3 Store 服务业务事件（跨服务调用）

Store 服务通过 HttpClient 调用 System 服务的内部 API，复用现有的内部服务认证机制（InternalServiceAuthMiddleware）：

```csharp
// Store 服务中的消息通知客户端
public interface IMessageNotifyClient
{
    Task NotifyAsync(InternalMessageNotifyDto dto);
}

public class MessageNotifyClient : IMessageNotifyClient
{
    private readonly HttpClient _httpClient;
    private readonly ITenantContext _tenantContext;

    public async Task NotifyAsync(InternalMessageNotifyDto dto)
    {
        var request = new HttpRequestMessage(HttpMethod.Post, "api/system/internal/messages/notify");
        request.Content = new StringContent(JsonSerializer.Serialize(dto), Encoding.UTF8, "application/json");
        // 传递租户上下文和内部服务认证头
        request.Headers.Add("X-Tenant-Id", _tenantContext.TenantId.ToString());
        request.Headers.Add("X-Internal-Service", "Store");

        var response = await _httpClient.SendAsync(request);
        response.EnsureSuccessStatusCode();
    }
}
```

### 7.5 接收者解析逻辑

`MessageAppService.SendAsync` / `NotifyAsync` 的展开流程：

```
1. 根据 TargetType 解析接收者
   - User:   直接使用 TargetIds 中的用户ID
   - Role:   查 UserRole 表，找 RoleId IN TargetIds 的 UserId，
             且（IsCrossTenant ? User.TenantId IN TargetTenantIds : User.TenantId = 当前租户）
   - Organization: 查 User 表，找 OrganizationId IN TargetIds 的用户
   - Tenant: 为每个 TargetId(租户ID) 创建一条 Message，TargetType 转为 All
   - All:    查 User 表，找 TenantId = 当前租户 的所有活跃用户

2. 跨租户消息（IsCrossTenant=true）：
   - 为每个 TargetTenantIds 中的租户创建一条 Message（TenantId=目标租户）
   - 在每个租户范围内按 TargetType 解析接收者

3. 批量插入 MessageRecipient 记录

4. 通过 SignalR 向每个接收者推送消息
```

### 7.6 幂等性设计

- 内部服务调用 `NotifyAsync` 时，调用方应确保不重复触发（如库存预警每次检查只触发一次）
- 不在消息服务侧做幂等去重，因为不同业务事件的去重逻辑不同，应由调用方负责

### 8.5 状态管理（stores/message.ts）

```typescript
export const useMessageStore = defineStore('message', () => {
  const unreadCount = ref(0)
  const recentMessages = ref<MessageInboxDto[]>([])

  // 获取未读数
  async function fetchUnreadCount() { ... }
  // 获取最近消息
  async function fetchRecentMessages() { ... }
  // SignalR 推送新消息时调用
  function onReceiveMessage(message: MessageInboxDto) {
    unreadCount.value++
    recentMessages.value.unshift(message)
  }
  // 标记已读
  function onMessageRead(id: number) {
    unreadCount.value = Math.max(0, unreadCount.value - 1)
  }

  return { unreadCount, recentMessages, fetchUnreadCount, ... }
})
```

#### 11.3.2 MessageAppService 核心方法实现要点

**发送消息 SendAsync（核心展开逻辑，对应 7.5 节）**：

```
1. 校验 DTO（FluentValidation）
2. 判断是否跨租户：
   - 平台管理员 + TargetType=Tenant 或 TargetTenantIds 非空 => IsCrossTenant=true
   - 否则 => IsCrossTenant=false
3. 构造 Message 记录列表：
   - 跨租户：为每个 TargetTenantIds 中的租户创建一条 Message（TenantId=目标租户）
   - 租户内：创建一条 Message（TenantId=当前租户）
4. 对每条 Message 解析接收者（ResolveRecipients）：
   - User: 直接使用 TargetIds
   - Role: JOIN UserRole 表，限定 User.TenantId = Message.TenantId
   - Organization: 查 User 表，OrganizationId IN TargetIds 且 TenantId 匹配
   - All: 查 User 表 TenantId 匹配的所有活跃用户
   - Tenant 类型已在步骤 3 转为按租户全员，此处不处理
5. 批量插入 Message + MessageRecipient
6. 通过 IHubContext<MessageHub> 向每个接收者的 Group 推送
```

**接收者解析的租户过滤**（对应 4.6.3 节）：

```sql
-- Role 类型，跨租户场景
SELECT u.Id, u.UserName FROM Users u
JOIN UserRole ur ON u.Id = ur.UserId
WHERE ur.RoleId IN @TargetRoleIds
  AND u.TenantId = @MessageTenantId
  AND u.IsDeleted = false
```

**撤回 RecallAsync**：
1. 校验消息存在且属于当前租户（或平台管理员）
2. 设置 `Message.IsRecalled = true`
3. 调用 `MessageRecipientRepository.SoftDeleteByMessageIdAsync` 批量逻辑删除所有接收记录
4. 可选：通过 SignalR 通知在线用户刷新收件箱（或依赖前端下次查询自然过滤）

**GetInboxAsync**：基于 MessageRecipient 表查询，WHERE `UserId = 当前用户 AND IsDeleted = false`，JOIN Message 获取标题/内容/分类等，排除 `Message.IsRecalled = true` 的记录。

**GetUnreadCountAsync**：`COUNT(*) WHERE UserId = 当前用户 AND IsRead = false AND IsDeleted = false`，响应需 < 50ms。

#### 11.3.3 依赖注入

MessageAppService 需注入：

- `IUserRepository`、`IRoleRepository`（或 IUserRoleRepository）、`IOrganizationRepository`

#### 11.4.4 MessageHub

```csharp
[Authorize]
public class MessageHub : Hub
{
    public override async Task OnConnectedAsync()
    {
        var userId = CurrentUser.Id; // 从 HttpContext 取 Claims
        await Groups.AddToGroupAsync(Context.ConnectionId, $"user_{userId}");
        await base.OnConnectedAsync();
    }

    public override async Task OnDisconnectedAsync(Exception? exception)
    {
        var userId = CurrentUser.Id;
        await Groups.RemoveFromGroupAsync(Context.ConnectionId, $"user_{userId}");
        await base.OnDisconnectedAsync(exception);
    }
}
```

#### 11.6.3 Pinia Store

```typescript
// src/stores/message.ts
export const useMessageStore = defineStore('message', () => {
  const unreadCount = ref(0)
  const recentMessages = ref<MessageInboxItem[]>([])

  async function fetchUnreadCount() { unreadCount.value = await getUnreadCount() }
  async function fetchRecentMessages() { recentMessages.value = (await getInbox({ pageIndex: 1, pageSize: 5 })).list }
  function onReceiveMessage(msg: MessageInboxItem) {
    unreadCount.value++
    recentMessages.value.unshift(msg)
    if (recentMessages.value.length > 5) recentMessages.value.pop()
  }
  function onMessageRead() { unreadCount.value = Math.max(0, unreadCount.value - 1) }

  return { unreadCount, recentMessages, fetchUnreadCount, fetchRecentMessages, onReceiveMessage, onMessageRead }
})
```

#### 11.6.4 SignalR 连接 composable

```typescript
// src/composables/useMessageHub.ts
import * as signalR from '@microsoft/signalr'

let connection: signalR.HubConnection | null = null

export function useMessageHub() {
  async function start() {
    connection = new signalR.HubConnectionBuilder()
      .withUrl('/api/system/hub/messages', {
        accessTokenFactory: () => localStorage.getItem('token') || ''
      })
      .withAutomaticReconnect([0, 2000, 5000, 10000, 30000])
      .build()

    connection.on('ReceiveMessage', (msg) => {
      useMessageStore().onReceiveMessage(msg)
    })

    await connection.start()
  }

  async function stop() {
    if (connection) await connection.stop()
  }

  return { start, stop }
}
```

### 11.10 关键技术决策说明

#### 11.10.1 内部 API 路由调整

**设计文档**：`/api/system/internal/messages/notify`
**实施采用**：`api/internal/messages/notify`

**理由**：与现有 `api/internal/auth`、`api/internal/tenants` 约定一致；内部服务直接调用 System 服务（不经网关），SystemApiClient 已配置 `SystemApi.BaseUrl=http://localhost:5000` 直连模式。设计文档路由可能混淆了网关路径与服务内路径。

#### 11.10.2 SignalR 网关路径

**设计文档**：前端连接 `/hub/messages`
**实施采用**：前端连接 `/api/system/hub/messages`

**理由**：前端所有请求经网关（vite 代理 `/api` -> 5020），SignalR 也需经网关。网关新增 `/api/system/hub/messages` -> System 服务 `/hub/messages` 的路由。直接连 `/hub/messages` 会绕过网关，与部署架构不一致。

#### 11.10.3 Application 层不引用 Api 层

MessageAppService 需推送消息但不能直接依赖 `IHubContext<MessageHub>`（在 Api 层）。引入 `IMessagePusher` 抽象：
- 接口定义在 Application 层
- 实现在 Api 层，注入 `IHubContext<MessageHub>`
- MessageAppService 依赖 `IMessagePusher` 抽象

保持 DDD 分层纯净。

#### 11.10.4 Message 实体不继承 TenantEntity

`TenantEntity` 的 `TenantId` 由框架自动填充为当前用户租户。但跨租户消息的 `TenantId` 应为目标租户（非发送者租户），自动填充会冲突。故 Message 手动持有 `TenantId`/`TenantCode`，由业务逻辑显式赋值。

#### 11.10.5 CORS 必须允许凭据

SignalR WebSocket 连接需携带 JWT token，CORS 必须配置 `AllowCredentials()`。当前 System.Api 的 CORS 若未配置，需补充。

### 11.11 风险与注意事项

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| Ocelot WebSocket 转发配置不当 | SignalR 无法经网关连接 | 阶段四优先验证，必要时参考 Ocelot 官方 WebSocket 文档 |
| 跨租户角色解析性能 | 平台角色下用户量大时 JOIN 慢 | 接收者解析查询加 `User.TenantId` 索引；超 1000 人分批推送 |
| EntityBase 字段重复 | 若 EntityBase 已含 IsDeleted/DeletedTime，MessageRecipient 重复声明 | 实施前核对 EntityBase 定义，避免重复 |
| 全员消息展开量 | 200 用户租户全员消息产生 200 条 MessageRecipient | 可接受；超 1000 用户时考虑异步队列（本次不实施） |
| SignalR 多实例部署 | 单实例无问题，多实例需 Redis 背板 | 本次单实例不引入 Redis；设计文档 6.5 节已标注可选 |
| 权限码未授予默认角色 | 普通用户看不到收件箱菜单 | 阶段七种子数据需将 `system:message:list` 授予所有默认角色 |
| 前端 token 刷新 | SignalR 长连接 token 过期 | withAutomaticReconnect 重连时重新取 token；token 过期需重新登录 |

### 11.12 实施顺序与依赖关系

```
阶段一（数据模型）
    │
    ▼
阶段二（应用服务） ── 依赖阶段一的实体与仓储
    │
    ▼
阶段三（API + SignalR） ── 依赖阶段二的服务；产出可独立运行的后端
    │
    ├──────────────┐
    ▼              ▼
阶段四（网关）   阶段五（前端基础） ── 两者可并行
    │              │
    └──────┬───────┘
           ▼
    阶段六（前端页面） ── 依赖阶段五的 API/Store/SignalR
           │
           ▼
    阶段七（种子数据） ── 可与阶段六并行
           │
           ▼
    阶段八（集成测试） ── 全链路验证
```

**可并行点**：
- 阶段三完成后，阶段四（网关）与阶段五（前端基础）可并行
- 阶段六（前端页面）与阶段七（种子数据）可并行

**关键路径**：阶段一 → 二 → 三 → 五 → 六 → 八
