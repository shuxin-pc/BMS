## 三、统一 FEFO 排序模式

所有 FEFO 扣减位置（修改 8b、9、10a、10b）的排序应统一为：

```csharp
.OrderBy(b => b.ExpirationDate.HasValue ? 0 : 1)  // null 批次排末尾
.ThenBy(b => b.ExpirationDate)                    // 近效期优先
.ThenBy(b => b.PurchaseDate)                      // 同效期 FIFO
.ThenBy(b => b.CreatedTime)                       // null 批次按 CreatedTime 升序，兜底稳定排序
```

**理由**:
- `OrderBy(b => b.ExpirationDate.HasValue ? 0 : 1)` 显式控制 null 排末尾，跨数据库行为一致（避免依赖 SQL Server/SQLite/PostgreSQL 各自的 NULL 默认排序）
- `ThenBy(b => b.CreatedTime)` 满足新需求"null 批次按 CreatedTime 升序"
- `ThenBy(b => b.PurchaseDate)` 满足"同效期按 PurchaseDate 升序"

## 五、需要业务确认的点

### 确认点 1: FEFO 自动扣减是否包含 null 批次

**场景**: 店员未手动选效期时，系统自动 FEFO 扣减

**当前行为**: 过滤 null 批次，仅扣减有日期批次。若商品所有批次均无到期日期，FEFO 查询返回空集，抛"库存不足"异常

**可选策略**:
- **策略 1**（现状）：严格 FEFO，null 批次不参与自动扣减 -- 风险：所有批次均无日期时订单失败
- **策略 2**：FEFO 查询为空时降级为 FIFO 兜底 -- 复杂度高
- **策略 3**（推荐）：包含 null 批次，排末尾按 CreatedTime 升序扣减 -- 兼顾安全与可用性

**建议**: 采纳策略 3，即修改 8b/9/10a/10b 的方案

### 确认点 2: InventoryAppService.DeductByBatchAsync 是否需要改为 FEFO

**场景**: 采购退货、积分兑换的库存扣减

**当前行为**: FIFO 扣减，按 `CreatedTime` 排序

**建议**: 保持 FIFO 不变。采购退货和积分兑换不涉及效期管理业务，无需改为 FEFO
